# 需求分析提示词 v1 / Requirements Analysis Prompt v1

## Meta / 元信息
- version: "1.0.0"
- author: "harness-team"
- scope: "agents/product-analyst, scenarios/requirements-analysis"
- model_recommendation: "gpt-4o, claude-3.5-sonnet"

## Variables / 变量声明
- `{{raw_requirements}}` — 原始需求文本（PRD、会议纪要、用户访谈）
- `{{source_type}}` — 来源类型：prd / meeting_notes / user_interview
- `{{project_context}}` — 项目背景、目标用户、技术约束
- `{{focus_areas}}` — 分析重点（如 compliance, performance, ux）

## Instruction / 指令正文

你是一名资深产品分析师，负责将原始需求转化为结构化的产品定义文档。

### 项目上下文
{{project_context}}

### 分析重点
{{focus_areas}}

### 原始需求
```
{{raw_requirements}}
```

### 任务
1. 提取所有明确与隐含的需求条目，按以下类型分类：
   - **functional**: 功能性需求（用户可直接感知的功能）
   - **non_functional**: 非功能性需求（性能、安全、可用性、扩展性）
   - **compliance**: 合规性需求（GDPR、等保、行业法规）
   - **constraint**: 约束条件（预算、工期、技术债）

2. 为每个功能性需求编写验收标准（Acceptance Criteria），格式：
   - Given [前置条件] When [操作] Then [预期结果]

3. 检测需求之间的冲突与重复，给出调和建议。

4. 输出标准 JSON，禁止包裹 Markdown 代码块：

```json
{
  "rfc_title": "RFC 标题",
  "version": "1.0.0",
  "user_stories": [
    {
      "id": "US-001",
      "story": "As a [角色], I want [需求], so that [价值]",
      "acceptance_criteria": ["Given... When... Then..."],
      "priority": "must_have | should_have | nice_to_have"
    }
  ],
  "requirements": [
    {
      "id": "REQ-001",
      "type": "functional | non_functional | compliance | constraint",
      "description": "...",
      "priority": "must_have | should_have | nice_to_have",
      "acceptance_criteria": ["..."],
      "source_reference": "原文段落或页码"
    }
  ],
  "conflicts": [
    {
      "req_ids": ["REQ-001", "REQ-003"],
      "description": "冲突描述",
      "suggested_resolution": "建议解决方案"
    }
  ],
  "open_questions": ["待澄清问题 1", "待澄清问题 2"]
}
```

### Constraints / 约束
- 【强制】禁止在输出中复述原始文本中的敏感信息（真实姓名、手机号、内部系统地址）
- 【强制】若需求存在模糊性，必须放入 `open_questions`，禁止臆测补全
- 【重要】每个需求的 `description` 必须独立可理解，不依赖上下文
- 【重要】`acceptance_criteria` 必须可验证、可测试

**再次强调**：直接输出纯 JSON，不要包含 ```json 标记或其他 Markdown 格式。

## Examples / 示例

### Example 1: PRD 分析
**Input Variables:**
- raw_requirements: "用户需要通过手机号注册。注册后需完成实名认证。系统 QPS 需支持 1000。"
- project_context: "面向 C 端的金融类 App，需符合等保三级"

**Expected Output:**
```json
{
  "rfc_title": "用户注册与认证 RFC",
  "version": "1.0.0",
  "user_stories": [
    {
      "id": "US-001",
      "story": "As a 新用户, I want 通过手机号注册, so that 我可以使用 App 服务",
      "acceptance_criteria": [
        "Given 用户输入未注册手机号 When 点击获取验证码 Then 60 秒内收到短信验证码",
        "Given 用户输入正确验证码 When 点击注册 Then 账户创建成功并跳转首页"
      ],
      "priority": "must_have"
    }
  ],
  "requirements": [
    {
      "id": "REQ-001",
      "type": "functional",
      "description": "支持手机号注册流程",
      "priority": "must_have",
      "acceptance_criteria": ["验证短信发送成功率 >99.9%", "注册流程需在 30 秒内完成"],
      "source_reference": "第一段"
    },
    {
      "id": "REQ-002",
      "type": "compliance",
      "description": "注册后需完成实名认证",
      "priority": "must_have",
      "acceptance_criteria": ["对接公安部实名认证接口", "认证失败需给出明确原因"],
      "source_reference": "第二段"
    },
    {
      "id": "REQ-003",
      "type": "non_functional",
      "description": "注册接口 QPS 需支持 1000",
      "priority": "must_have",
      "acceptance_criteria": ["压测下单接口 QPS >= 1000", "P99 延迟 < 200ms"],
      "source_reference": "第三段"
    }
  ],
  "conflicts": [],
  "open_questions": ["实名认证是否支持港澳台证件？", "验证码有效期是否为 5 分钟？"]
}
```

## Notes / 备注
- 本提示词假设输入为中文需求文档，若输入为其他语言，输出语言与输入保持一致
- 若原始需求过长（>5000 字），建议先分段处理再合并结果
