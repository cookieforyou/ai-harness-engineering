# 架构评审检查清单 (Architecture Review Checklist)

## Purpose

本清单用于架构设计方案的技术评审，覆盖架构决策、非功能需求覆盖、技术栈可行性和安全合规四个维度。确保方案在技术层面可行、可扩展、可维护。

## Scoring

- **PASS**: 满足要求，架构方案可行
- **PARTIAL**: 基本可行，存在需澄清或在实现阶段关注的问题
- **FAIL**: 不满足要求，需调整架构方案
- **NA**: 不适用

## 使用时机

- 系统设计阶段的架构方案评审
- 重大技术变更（引入新中间件/新框架/重构）评审
- 年度架构健康度评估

---

## 1. 架构决策 (Architecture Decisions)

- [ ] **ARC-001**: 架构模式（微服务/单体/事件驱动/分层/六边形）有明确选择依据，并匹配业务规模和团队能力
- [ ] **ARC-002**: 每个关键架构决策有 ADR（Architecture Decision Record），记录上下文、方案对比、决策理由和后果
- [ ] **ARC-003**: 模块/服务划分遵循高内聚低耦合原则：模块间依赖 ≤ 3 层（A→B→C），无循环依赖
- [ ] **ARC-004**: 组件间通信协议选择合理（同步/异步，REST/gRPC/消息队列），与数据一致性要求匹配
- [ ] **ARC-005**: 数据一致性策略已定义（强一致性/最终一致性/分布式事务方案），Saga/TCC/2PC 用于资金类场景
- [ ] **ARC-006**: 架构图完整展示：系统上下文图、容器图、组件图（C4 模型至少到 Level 2），图形化文档与文字描述配套

## 2. 非功能需求覆盖 (NFR Coverage)

- [ ] **ARN-001**: 性能需求已量化：目标吞吐量（TPS/QPS）、期望响应时间（P50/P95/P99）、并发用户数
- [ ] **ARN-002**: 可用性架构已设计：无单点故障（SPOF）、关键服务多副本部署（≥ 2 副本）、跨可用区部署（生产环境）
- [ ] **ARN-003**: 扩展性设计已明确：水平扩展方案（auto-scaling 策略/无状态设计）或垂直扩展方案
- [ ] **ARN-004**: 灾难恢复（DR）方案已定义：RTO（恢复时间目标）≤ 4 小时、RPO（恢复点目标）≤ 1 小时
- [ ] **ARN-005**: 容量规划数据支撑架构决策：峰值流量估算（平时 ×3-5 倍）、存储增长预测（月增长 ×12）、数据库连接数计算

## 3. 技术栈可行性 (Tech Stack Viability)

- [ ] **ART-001**: 技术选型评估覆盖 3 个维度：功能满足度（≥ 80%）、社区活跃度（GitHub Star ≥ 1k/最近 3 月有发布）、团队熟悉度（≥ 2 人有经验）
- [ ] **ART-002**: 核心依赖的许可证兼容（无 GPL 传染性依赖用于商业产品），许可证类型已列明
- [ ] **ART-003**: 所选技术的生命周期风险评估（非 EOL 版本、非即将停止维护的开源项目），预览版不用于生产
- [ ] **ART-004**: 核心依赖已有至少 1 个替代方案（Plan B）在评估中，非唯一依赖
- [ ] **ART-005**: 技术栈统一性考量：不引入与现有技术栈功能重叠的新组件（如已有 Redis 时不引入新缓存中间件，除非有量化依据）

## 4. 安全合规 (Security & Compliance)

- [ ] **ARS-001**: 安全架构基于纵深防御原则：网络层（防火墙/WAF）、应用层（输入校验/CSRF/XSS 防护）、数据层（加密/脱敏）
- [ ] **ARS-002**: 数据分类分级已定义：敏感数据（PII/金融/密码）有加密存储（AES-256）和传输加密（TLS 1.2+）
- [ ] **ARS-003**: 身份认证方案已设计：OAuth 2.0/OIDC/SAML 等标准协议，无自建认证协议
- [ ] **ARS-004**: 日志审计满足合规要求：谁（用户身份）、何时（时间戳）、做了什么（操作记录）、结果如何（成功/失败）
- [ ] **ARS-005**: 安全架构威胁建模已完成（STRIDE 方法覆盖：Spoofing/Tampering/Repudiation/Info Disclosure/DoS/Elevation of Privilege）

## 5. 评审结论 (Review Conclusion)

- [ ] **ARR-001**: 设计方案可追溯到需求规格（矩阵覆盖率 ≥ 95%）
- [ ] **ARR-002**: 架构评审会议纪要已记录，所有 Action Item 有负责人和截止日期
- [ ] **ARR-003**: 评审参与者包含至少 1 名架构师和 1 名非本项目组成员（新鲜视角）

## 6. 常见架构反模式 (Common Anti-Patterns)

以下列出架构设计中常见的反模式及其改进建议，评审时应注意避免：

| 反模式 | 表现 | 改进建议 |
|--------|------|----------|
| 大泥球 (Big Ball of Mud) | 模块间依赖混乱，无清晰边界，一处修改引发多处故障 | 按业务域划分限界上下文（Bounded Context），实施分层架构，逐步重构 |
| 分布式单体 (Distributed Monolith) | 微服务间同步调用链过长（> 3 跳），一个故障级联影响所有依赖 | 引入异步消息解耦，同步调用链长度不超过 2 跳，设置超时和熔断 |
| 过度设计 (Over-Engineering) | 为简单 CRUD 引入事件溯源、CQRS 等复杂模式，远超业务需要 | 遵循 YAGNI 原则，仅在有明确非功能需求驱动时引入复杂架构模式 |
| 上帝服务 (God Service) | 某服务承担过多职责（> 5 个不相关领域），成为开发和部署瓶颈 | 按单一职责原则拆分为专一服务，每个服务负责 ≤ 2 个相关业务领域 |
| 数据库即集成点 | 多个服务直接读写同一数据库，绕过服务边界，破坏封装 | 每个服务拥有独立数据存储，通过 API 或消息队列进行数据交换 |

## Scoring Examples

以下示例说明不同场景下的评分判定结果：

- **PASS 示例**: 零售订单系统采用事件驱动架构，服务拆分对齐业务域，C4 模型到 Level 3，ADR 记录完整，已完成 STRIDE 威胁建模，通过率 92%
- **PARTIAL 示例**: 采用微服务架构但服务边界划分存在争议（如"用户"与"账户"职责重叠），NFR 中灾备方案未涉及，通过率 78%
- **FAIL 示例**: 微服务迁移方案中服务拆分仅按功能层级而非业务域，无数据一致性策略，安全方面未设计，通过率 65%
