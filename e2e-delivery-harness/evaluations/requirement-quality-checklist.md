# 需求质量检查清单 (Requirement Quality Checklist)

## Overview

需求质量检查清单用于系统化评估需求文档（用户故事/业务需求/功能规格）的质量，确保需求在进入开发阶段前具备足够完整性、一致性、可测性、无歧义性和可追溯性。本清单适用于产品经理自检、团队需求评审会和 Sprint 规划前准入检查。

### 适用场景

- 需求分析阶段准出审核（Entry Criteria for Development）
- Backlog Refinement 会议中的需求质量评审
- 跨团队需求交接前的质量确认
- 季度需求质量健康度评估

---

## Evaluation Criteria

| 维度 | 权重 | 目标值 | 测量方法 |
|------|------|--------|----------|
| 完整性 (Completeness) | 30% | ≥ 90% 通过 | 逐项核查 10 项完整性要素 |
| 一致性 (Consistency) | 25% | 无已知矛盾项 | 交叉对比各章节/关联文档 |
| 可测性 (Testability) | 20% | ≥ 95% 可量化验证 | 检查验收标准是否可测试 |
| 无歧义性 (Unambiguity) | 15% | 模糊词数量 = 0 | 关键词扫描 + 术语表核查 |
| 可追溯性 (Traceability) | 10% | 追溯覆盖率 ≥ 90% | REQ ↔ OBJ ↔ AC 追溯矩阵 |

---

## Scoring Formula

```
完整性得分   = (通过项数 / 10) × 100
一致性得分   = 一致性检查通过率 × 100
可测性得分   = 可测试AC数 / AC总数 × 100
无歧义得分   = max(0, 100 - 模糊词数 × 10)
追溯得分     = 追溯覆盖率 × 100

总分 = 完整性得分 × 30% + 一致性得分 × 25% + 可测性得分 × 20% + 无歧义得分 × 15% + 追溯得分 × 10%
```

### 等级划分

| 等级 | 分数范围 | 判定 |
|------|----------|------|
| S (Excellent) | ≥ 90 | 需求质量优秀，可直接进入开发 |
| A (Good) | 80-89 | 少量改进点，修复后可进入开发 |
| B (Fair) | 70-79 | 需显著改进，返工后重新评审 |
| F (Failed) | < 70 | 质量不达标，禁止进入开发阶段 |

## Checklist

### 1. 完整性检查 (10项)

- [ ] **RQC-INT-001**: 业务目标（OBJ-*）符合 SMART 标准，有量化成功指标
- [ ] **RQC-INT-002**: 功能需求（REQ-*）使用标准的用户故事格式（As a / I want / So that）
- [ ] **RQC-INT-003**: 非功能需求（NFR-*）已识别且数值化（性能≥X，可用性≥Y%）
- [ ] **RQC-INT-004**: 验收标准（AC-*）覆盖 Happy Path + 至少 2 种异常场景
- [ ] **RQC-INT-005**: 前置条件（依赖关系）已列出：上游依赖、系统状态、数据前提
- [ ] **RQC-INT-006**: 相关方（Stakeholders）已识别：业务方、技术方、测试方、运维方
- [ ] **RQC-INT-007**: 假设与约束显式列出：技术约束、时间约束、资源约束
- [ ] **RQC-INT-008**: 风险登记（Risk Register）已创建并标注影响和概率
- [ ] **RQC-INT-009**: 优先级标注：P0/Must-have、P1/Should-have、P2/Could-have、P3/Won't-have
- [ ] **RQC-INT-010**: 需求来源可追溯：来自用户反馈/市场分析/合规要求/技术改进

### 2. 一致性检查 (5项)

- [ ] **RQC-CON-001**: 需求内部的术语使用与项目术语表一致，无同义词混用
- [ ] **RQC-CON-002**: 需求之间无相互矛盾的要求（如"所有操作 ≤ 1s" vs "批量导出 ≤ 30s"需说明）
- [ ] **RQC-CON-003**: 验收条件与非功能需求不冲突，无 AC 要求结果但 NFR 限制手段
- [ ] **RQC-CON-004**: 需求版本号一致，无不同版本的混用（V2.3 的需求描述与 V2.2 的界面不一致）
- [ ] **RQC-CON-005**: 跨功能模块的需求间没有不可满足的接口契约矛盾

### 3. 可测性检查 (5项)

- [ ] **RQC-TST-001**: 每条需求有对应的验收标准（AC），判断标准可量化
- [ ] **RQC-TST-002**: AC 的 Then 部分指向具体可观测结果（状态码/字段值/响应时间/文件）
- [ ] **RQC-TST-003**: 测试数据可构造（Given 部分不依赖不存在或无法生成的数据）
- [ ] **RQC-TST-004**: 需求未使用"系统应支持"类无边界描述（"系统应支持大量用户" → "系统应支持 10000 并发用户"）
- [ ] **RQC-TST-005**: 需求中的枚举值/状态流转图完整，测试覆盖所有状态转移路径

### 4. 无歧义性检查 (5项)

- [ ] **RQC-AMB-001**: 不使用模糊量化词：大量、少量、若干、一些、几乎、大约
- [ ] **RQC-AMB-002**: 不使用主观评价词：友好、易用、高效、快速、充分、合理
- [ ] **RQC-AMB-003**: 不使用未定义的技术简写，首次出现时给出全称
- [ ] **RQC-AMB-004**: 条件语句（如果/当/除非）的触发条件精确无歧义
- [ ] **RQC-AMB-005**: 否定需求（"系统不应..."）有明确的判定边界

### 5. 可追溯性检查 (3项)

- [ ] **RQC-TRC-001**: 每条功能需求（REQ-*）可追溯至至少一条业务目标（OBJ-*）
- [ ] **RQC-TRC-002**: 每条验收标准（AC-*）可追溯至对应需求（REQ-*）
- [ ] **RQC-TRC-003**: 追溯矩阵覆盖率 ≥ 90%（已建立并持续维护）
