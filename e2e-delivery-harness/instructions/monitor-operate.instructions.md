# Monitoring Operations Instructions

## Purpose

本文档定义了监控运维阶段的标准操作流程、质量检查标准和工作产出规范。监控运维是保障系统稳定运行、持续改进运维效率的关键阶段，通过完善的监控体系、及时的告警响应和高效的故障处理，确保系统高可用性和SLO达成。

### 核心目标
- **保障服务稳定性**: 通过完善的监控体系和快速响应机制，确保系统高可用性（≥99.5%）
- **降低故障影响**: 快速发现和定位问题，缩短MTTD（≤5min）和MTTR（≤30min）
- **提升运维效率**: 自动化监控和告警，减少人工巡检工作量，提高问题发现和处理效率
- **数据驱动决策**: 基于监控数据进行容量规划、性能优化和架构改进，支撑业务增长
- **持续改进文化**: 通过故障复盘和运维数据分析，不断优化系统稳定性和运维流程

## Investigation Flow

### 流程概览

```
[THINK] 了解系统基线和SLO 
    ↓
[SETUP] 配置监控和告警
    ↓
[WATCH] 监控系统状态
    ↓
[RESPOND] 响应告警和事件
    ↓
[IMPROVE] 优化监控体系
    ↓
[REPORT] 产出运维报告
```

### 步骤 1：[THINK] 了解系统基线和SLO

**目的**：全面理解系统架构、SLO目标和当前状态，为监控配置奠定基础

**输入**：
- 系统架构文档
- 部署完成报告
- SLO目标定义
- 历史故障记录（如有）

**操作流程**：

1. **分析系统架构**
   - 识别关键组件和服务
   - 理解组件间依赖关系
   - 确定关键路径和瓶颈点
   - 评估系统复杂度和风险点

2. **确认SLO目标**
   - 可用性目标（如 99.9%）
   - 延迟目标（P50、P99）
   - 错误率目标（如 <1%）
   - 恢复时间目标（如 <30min）
   - 月度Error Budget

3. **识别关键监控点**
   - 基础设施层：CPU、内存、磁盘、网络
   - 应用层：QPS、延迟、错误率、饱和度
   - 业务层：订单量、转化率、支付成功率
   - 依赖服务：数据库、缓存、消息队列、外部API

4. **评估当前状态**
   - 检查现有监控配置
   - 分析历史监控数据
   - 识别监控盲区
   - 评估告警有效性

**检查点**：
- [ ] 系统架构理解清晰
- [ ] SLO目标明确且可测量
- [ ] 关键监控点已识别
- [ ] 当前监控状态已评估

**产出**：
- 系统架构分析报告
- SLO目标清单
- 关键监控点列表
- 当前监控状态评估

**质量标准**：
- 架构分析覆盖所有关键组件和依赖
- SLO目标与业务方对齐
- 监控点覆盖黄金指标（Latency, Traffic, Errors, Saturation）

### 步骤 2：[SETUP] 配置监控和告警

**目的**：建立完善的三层监控体系和智能告警机制

**输入**：
- 系统架构分析报告
- SLO目标清单
- 关键监控点列表
- 告警通知渠道配置

**操作流程**：

1. **设计基础设施层监控**
   - CPU使用率和负载（1min/5min/15min）
   - 内存使用率和Swap使用情况
   - 磁盘使用率、I/O性能、inode使用率
   - 网络带宽、连接数、丢包率
   - 文件系统监控

2. **设计应用层监控（黄金指标）**
   - **Latency**: 请求延迟分布（P50, P90, P95, P99）
   - **Traffic**: 请求流量（QPS、并发数、吞吐量）
   - **Errors**: 错误率（HTTP 5xx、异常抛出率、超时率）
   - **Saturation**: 饱和度（线程池、连接池、队列长度、GC频率）

3. **设计业务层监控**
   - 核心业务KPI（订单量、交易额、用户数）
   - 业务转化率（注册转化、购买转化、支付转化）
   - 业务异常指标（订单失败、支付失败、登录失败）
   - 用户行为指标（日活、留存、访问路径）

4. **设置告警规则**
   - 基于历史数据分析设置合理阈值
   - 定义告警级别（P0/P1/P2/P3）
   - 配置告警通知渠道（钉钉、邮件、短信、电话）
   - 设置告警升级策略和静默期
   - 实施告警聚合和去重机制

5. **创建监控仪表盘**
   - 系统总览仪表盘（整体健康状态、核心指标）
   - 服务详情仪表盘（各微服务性能指标）
   - 业务指标仪表盘（业务数据和转化漏斗）
   - 容量视图仪表盘（资源使用和趋势）
   - SLO追踪仪表盘（SLO达成情况和Error Budget）

6. **验证监控配置**
   - 测试数据采集是否正常
   - 验证告警触发和通知
   - 确认仪表盘数据显示正确
   - 检查监控覆盖度（目标≥95%）

**检查点**：
- [ ] 黄金指标全覆盖（Latency, Traffic, Errors, Saturation）
- [ ] 三层监控完整（基础设施、应用、业务）
- [ ] 告警阈值基于历史数据设置
- [ ] 告警通知渠道已测试畅通
- [ ] 监控覆盖度 ≥95%
- [ ] 仪表盘布局合理，信息清晰

**产出**：
- 监控配置文档（YAML/JSON格式）
- 告警规则配置
- 仪表盘定义文件
- 监控指标字典
- 监控验证报告

**质量标准**：
- 监控配置语法正确，可正常加载
- 告警规则经过测试验证
- 仪表盘可正常渲染，数据准确
- 监控覆盖度达到95%以上

### 步骤 3：[WATCH] 监控系统状态

**目的**：定期巡检系统运行状态，及时发现潜在问题

**输入**：
- 监控仪表盘
- 巡检检查清单
- 历史巡检记录
- 告警历史记录

**操作流程**：

1. **系统健康检查**
   - 检查所有服务是否正常运行
   - 检查关键进程状态和存活情况
   - 检查系统负载和响应时间
   - 检查日志是否有异常（ERROR、WARN）
   - 检查健康检查端点（/health）

2. **资源使用情况检查**
   - CPU使用率及趋势（当前值、峰值、平均值）
   - 内存使用率及Swap情况（使用率、GC频率）
   - 磁盘使用率和I/O性能（使用率、IOPS、延迟）
   - 网络带宽和连接数（入站、出站、连接数）
   - 数据库连接池使用情况（活跃连接、等待连接）

3. **业务指标检查**
   - 核心业务KPI是否正常（订单量、交易额、用户数）
   - 与历史同期对比分析（同比、环比）
   - 识别异常波动和趋势（突增、突降、周期性）
   - 检查业务异常率（失败率、超时率）

4. **告警情况分析**
   - 查看未处理告警数量和级别
   - 分析告警趋势和模式（高频告警、重复告警）
   - 识别重复告警和误报
   - 检查告警响应时效（MTTD、MTTR）

5. **SLO合规性检查**
   - 计算当前SLO达成情况（可用性、延迟、错误率）
   - 检查Error Budget剩余量和消耗速率
   - 分析SLO趋势和预测
   - 识别SLO风险和潜在违反

6. **生成巡检报告**
   - 汇总巡检结果和关键发现
   - 标记异常和关注项
   - 提出改进建议和行动计划
   - 归档巡检记录

**检查点**：
- [ ] 巡检项目完整率 100%
- [ ] 异常识别准确率 ≥95%
- [ ] 巡检记录可追溯
- [ ] 改进建议具体可执行
- [ ] 巡检周期符合要求（至少每日一次）

**产出**：
- 巡检报告（Markdown格式）
- 异常情况清单
- 改进建议列表
- 巡检记录归档

**质量标准**：
- 巡检覆盖所有关键指标和组件
- 异常识别及时准确
- 巡检记录完整可追溯
- 改进建议具有可操作性

### 步骤 4：[RESPOND] 响应告警和事件

**目的**：及时响应和处理告警，确保系统稳定运行

**输入**：
- 告警通知
- 告警处理流程和Runbook
- 相关监控数据和日志
- 应急预案

**操作流程**：

1. **告警接收和分类**
   - 接收告警通知（钉钉、邮件、短信、电话）
   - 判断告警级别（P0/P1/P2/P3）
   - 评估影响范围和紧急程度
   - 确定响应时限（P0立即，P1 15min，P2 1h，P3下一工作日）

2. **告警验证**
   - 确认告警真实性（排除误报）
   - 检查相关监控指标和趋势
   - 查看系统日志和事件
   - 验证告警触发条件和阈值

3. **告警分级响应**
   - **P0 (Critical)**: 
     - 立即响应（<5min）
     - 电话+短信+钉钉通知全员
     - 启动应急响应流程
     - 成立应急小组
   
   - **P1 (Major)**: 
     - 15分钟内响应
     - 短信+钉钉通知相关人员
     - 值班人员立即处理
     - 必要时升级
   
   - **P2 (Minor)**: 
     - 1小时内响应
     - 钉钉通知值班人员
     - 按计划处理
     - 记录跟踪
   
   - **P3 (Warning)**: 
     - 下一个工作日处理
     - 邮件通知
     - 记录并纳入改进计划

4. **问题定位和分析**
   - 收集相关信息（日志、监控、调用链路）
   - 分析问题根因（使用5 Whys方法）
   - 识别受影响的服务和用户
   - 评估故障持续时间和影响范围
   - 查找类似历史案例

5. **执行处理措施**
   - **优先快速止血**：
     - 重启故障服务
     - 回滚到上一个稳定版本
     - 启用降级方案
     - 实施限流保护
     - 切换流量到备用系统
   
   - **执行Runbook操作**：
     - 按照标准操作流程处理
     - 必要时启动应急预案
     - 通知相关方和利益相关者
     - 每15-30分钟更新进展

6. **验证和闭环**
   - 验证处理效果（监控指标恢复正常）
   - 确认告警消除
   - 更新告警记录和状态
   - 通知相关方故障已恢复
   - 关闭告警工单

7. **后续跟进**
   - 记录告警处理过程和决策
   - 分析告警根因（5 Whys）
   - 制定预防措施和改进计划
   - 更新Runbook和文档
   - 分享经验和教训

**检查点**：
- [ ] 告警响应时效符合级别要求
- [ ] 告警级别判断准确
- [ ] 处理措施得当有效
- [ ] 告警记录完整准确
- [ ] 告警闭环率 100%
- [ ] MTTD ≤5min, MTTR ≤30min

**产出**：
- 告警处理记录（含响应时间、处理过程、结果）
- 根因分析报告
- 改进措施清单
- 更新的Runbook

**质量标准**：
- 告警响应及时，符合SLA要求
- 处理措施有效，问题得到解决
- 记录完整，便于追溯和复盘
- MTTD和MTTR达标

### 步骤 5：[IMPROVE] 优化监控体系

**目的**：持续优化监控体系和运维流程，提升效率和质量

**输入**：
- 运维数据分析报告
- 告警统计和有效性分析
- 故障记录和复盘报告
- 团队反馈和建议

**操作流程**：

1. **运维数据分析**
   - 分析告警统计数据（数量、级别、响应时间、处理时间）
   - 分析故障频率、类型和趋势
   - 分析MTTD和MTTR趋势
   - 计算告警噪声率（无效告警占比）
   - 识别常见问题和模式

2. **识别优化机会**
   - 识别监控盲区和覆盖不足
   - 识别告警噪声和误报问题
   - 识别流程瓶颈和低效环节
   - 识别自动化的机会
   - 收集团队反馈和建议

3. **监控优化**
   - **调整告警阈值**：
     - 基于历史数据分析优化阈值
     - 减少误报和漏报
     - 实施动态阈值或基线告警
   
   - **增加缺失监控**：
     - 补充监控盲区的指标
     - 增加业务层监控
     - 完善分布式追踪
   
   - **优化告警机制**：
     - 实施告警聚合和去重
     - 优化告警路由和升级
     - 设置合理的静默期
   
   - **改进仪表盘**：
     - 优化可视化效果
     - 增加关键指标展示
     - 提高查询性能

4. **流程优化**
   - 简化告警响应流程
   - 优化故障处理流程
   - 改进交接班流程
   - 标准化常见操作
   - 完善升级机制

5. **自动化实施**
   - 自动化常见运维操作（重启、扩容、备份）
   - 实现自动扩缩容（HPA、VPA）
   - 自动化告警分类和路由
   - 自动化故障检测和恢复
   - 自动化报告生成

6. **知识沉淀和分享**
   - 更新运维文档和Runbook
   - 完善故障案例库
   - 编写最佳实践指南
   - 组织培训和分享
   - 建立知识库

**检查点**：
- [ ] 优化建议可操作性 100%
- [ ] 优化措施实施率 ≥80%
- [ ] 优化效果可量化
- [ ] 文档更新及时
- [ ] 团队能力提升

**产出**：
- 优化建议报告
- 优化实施计划
- 更新的运维文档
- 最佳实践指南
- 培训材料

**质量标准**：
- 优化建议具体可执行
- 优化效果可量化（告警噪声率降低、MTTD/MTTR缩短）
- 文档更新及时准确
- 团队成员掌握新技能

### 步骤 6：[REPORT] 产出运维报告

**目的**：生成综合运维报告，总结运维工作，准备交接

**输入**：
- 巡检报告
- 告警处理记录
- 故障报告
- 容量评估报告
- 优化建议报告

**操作流程**：

1. **汇总运维数据**
   - 收集本周期内的所有运维数据
   - 统计告警数量、级别、响应时间
   - 统计故障数量、持续时间、影响范围
   - 计算SLO达成情况和Error Budget剩余

2. **生成综合运维报告**
   - **监控概览**：系统整体状态、监控覆盖度、告警噪声率
   - **告警统计**：告警数量、级别分布、响应时效、Top告警
   - **故障分析**：故障数量、MTTD、MTTR、根因分析、改进措施
   - **容量评估**：资源使用情况、趋势分析、扩容建议
   - **SLO合规**：SLO达成情况、Error Budget分析、风险提示
   - **优化进展**：已实施的优化、效果评估、待优化项

3. **更新Global Context**
   - 更新系统健康状态
   - 更新SLO达成情况
   - 更新遗留问题和待处理事项
   - 更新容量状态和风险

4. **准备交接信息**
   - 重点关注事项和待处理告警
   - 下一班次注意事项
   - 值班人员和联系方式
   - 升级联系人和 escalation policy

5. **归档和分享**
   - 归档运维报告和相关文档
   - 分享给相关团队和利益相关者
   - 在团队会议上讨论关键发现
   - 更新知识库和最佳实践

**检查点**：
- [ ] 报告内容完整准确
- [ ] 数据计算和统计正确
- [ ] 分析和结论合理
- [ ] 建议具体可执行
- [ ] 交接信息清晰

**产出**：
- 综合运维报告（Markdown格式）
- Global Context更新
- 交接信息
- 归档的文档

**质量标准**：
- 报告完整性 100%
- 数据准确性 100%
- 分析深度和洞察力
- 可读性和可理解性

## What To Check

### 必检项

| 检查项 | 标准 | 检查方法 | 通过条件 |
|--------|------|----------|----------|
| 监控完整 | 黄金指标全覆盖 | 配置检查 | 覆盖度 ≥95% |
| 告警有效 | 告警阈值合理，无误报 | 历史分析 | 噪声率 ≤20% |
| 响应及时 | 告警按规定时效响应 | 响应记录 | MTTD≤5min, MTTR≤30min |
| 故障闭环 | 故障及时处理并复盘 | 故障记录 | 闭环率 100% |
| SLO达标 | SLO目标达成 | SLO监控 | 合规率 ≥99.5% |
| 文档完善 | 运维文档完整更新 | 文档检查 | 更新及时率 100% |

### 建议检查项

| 检查项 | 标准 | 检查方法 | 建议值 |

## Quality Standards

### 质量维度

| 维度 | 要求 | 权重 | 验收标准 |
|------|------|------|----------|
| 稳定性 | 系统稳定运行，SLO达标 | 30% | SLO合规率≥99.5% |
| 响应性 | 告警和故障及时响应 | 25% | MTTD≤5min, MTTR≤30min |
| 可观测性 | 监控完善有效 | 25% | 监控覆盖度≥95%，告警噪声率≤20% |
| 持续改进 | 运维持续优化 | 20% | 优化措施实施率≥80% |

### Key Performance Indicators (KPIs)

| KPI ID | 指标名称 | 目标值 | 计算公式 | 验证方法 | 权重 |
|--------|----------|--------|----------|----------|------|
| KPI-001 | MTTD | ≤5min | 异常发生到告警触发的平均时间 | 告警日志分析 | 25% |
| KPI-002 | MTTR | ≤30min | 告警触发到问题修复的平均时间 | 故障记录统计 | 25% |
| KPI-003 | ALERT-NOISE | ≤20% | (无效告警数/总告警数) × 100% | 告警有效性分析 | 20% |
| KPI-004 | SLO-COMPLY | ≥99.5% | (SLO达标时间/总时间) × 100% | SLO监控面板 | 30% |

**综合评分计算**: 
```
Quality Score = (KPI-001得分 × 0.25) + (KPI-002得分 × 0.25) + (KPI-003得分 × 0.20) + (KPI-004得分 × 0.30)

KPI得分计算:
- MTTD: ≤5min=100分, 5-10min=80分, 10-15min=60分, >15min=0分
- MTTR: ≤30min=100分, 30-60min=80分, 60-120min=60分, >120min=0分
- ALERT-NOISE: ≤20%=100分, 20-30%=80分, 30-40%=60分, >40%=0分
- SLO-COMPLY: ≥99.5%=100分, 99-99.5%=80分, 98-99%=60分, <98%=0分

合格: ≥70分 | 优秀: ≥85分 | 卓越: ≥95分
```

## Error Handling

### Error Scenario 1: 告警风暴 (P1)

**触发条件**: 短时间内大量告警同时触发（>10个/分钟）

**处理流程**:
```
IF 检测到告警风暴
THEN
  1. 立即识别根本告警（触发其他告警的根源）
  2. 暂时抑制次要告警（避免干扰，保留关键告警）
  3. 优先处理核心问题（恢复核心服务可用性）
  4. 通知相关团队（开发、运维、DBA）协同处理
  5. 记录告警风暴详情（触发时间、告警数量、影响范围）
  6. 事后优化告警规则（调整阈值、增加依赖关系、设置静默期）
END
```

**降级方案**: 暂时关闭非关键告警，聚焦核心服务恢复

**升级条件**: 核心服务不可用或影响超过50%用户

### Error Scenario 2: 告警误报 (P2)

**触发条件**: 告警触发但系统实际运行正常，误报率>30%

**处理流程**:
```
IF 检测到告警误报
THEN
  1. 确认系统实际状态（检查监控数据和日志）
  2. 分析误报原因（阈值过低、数据采集异常、瞬时波动）
  3. 调整告警阈值（基于历史数据统计分析）
  4. 增加告警条件（如持续时间、多次确认）
  5. 标记该告警为误报，更新告警规则
  6. 记录误报案例，用于后续优化
END
```

**降级方案**: 临时降低告警级别或延长触发时间窗口

**升级条件**: 误报率持续高于30%，影响运维效率

### Error Scenario 3: SLO即将违反 (P1)

**触发条件**: Error Budget消耗速度过快或关键指标趋势显示即将违反SLO

**处理流程**:
```
IF SLO即将违反
THEN
  1. 立即升级告警到P0级别
  2. 启动应急响应流程，通知所有相关方
  3. 分析SLO违反风险（哪个指标、何时违反、影响范围）
  4. 采取紧急措施（限流、降级、扩容）
  5. 每小时更新SLO状态和剩余Error Budget
  6. 准备事后复盘材料
END
```

**降级方案**: 暂停非核心功能，优先保障核心服务SLO

**升级条件**: SLO已违反或预计1小时内违反

### Error Scenario 4: 监控数据缺失 (P2)

**触发条件**: 关键指标无数据或数据中断超过5分钟

**处理流程**:
```
IF 检测到监控数据缺失
THEN
  1. 检查采集Agent状态（是否运行、资源是否正常）
  2. 检查网络连通性（Agent到监控服务器的连接）
  3. 验证指标定义是否正确（指标名称、标签、单位）
  4. 检查数据存储和查询服务
  5. 标记为 [数据缺失] 并通知相关人员
  6. 启动备用监控方案或手动巡检
END
```

**降级方案**: 启用备用监控源或增加手动巡检频率

**升级条件**: 核心指标数据缺失超过15分钟

## Constraints

1. **语言**：输出使用中文，技术术语可使用英文
2. **及时性**：告警需按规定时效响应（P0立即，P1 15min，P2 1h）
3. **完整性**：监控需覆盖核心指标，运维记录需完整
4. **可追溯**：所有操作需有记录，便于审计和复盘
5. **持续改进**：需持续优化监控体系和运维流程
6. **数据安全**：不得泄露敏感信息（密码、密钥、用户数据）
