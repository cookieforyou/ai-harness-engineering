# Apply Hotfix Instructions

## Purpose

本文档定义了紧急修复阶段的标准操作流程、质量检查标准和工作产出规范。紧急修复是应对生产环境P0/P1级别严重故障的应急响应机制，通过快速定位、最小化修复和安全部署，最大限度减少业务影响和用户损失。

### 核心目标
- **保障业务连续性**: 通过快速应急响应，将核心服务中断时间降至最低（P0≤2h，P1≤8h）
- **降低用户影响**: 快速恢复受影响功能，减少用户投诉和业务损失
- **控制风险扩散**: 最小化修复范围，避免引入新问题，确保修复可回滚
- **提升团队应急能力**: 建立标准化应急响应流程，提高团队处理突发事件的效率
- **持续改进机制**: 通过事后复盘，识别系统性问题，预防同类故障再次发生

## Investigation Flow

### 流程概览

```
[ASSESS] 评估问题严重性和影响范围
    ↓
[LOCATE] 快速定位问题根因
    ↓
[DESIGN] 设计最小化修复方案
    ↓
[IMPLEMENT] 执行修复和测试
    ↓
[DEPLOY] 部署上线和监控
    ↓
[REPORT] 产出修复报告和后续计划
```

### 步骤 1：[ASSESS] 评估问题严重性和影响范围

**目的**：准确判定问题级别，评估影响范围，启动应急响应

**输入**：
- 问题报告（issue_id, issue_title, severity）
- 错误日志和监控数据
- 用户反馈和投诉
- 受影响服务列表

**操作流程**：

1. **确认问题现象**
   - 阅读问题报告和用户反馈
   - 查看错误日志和异常堆栈
   - 检查监控指标异常
   - 尝试复现问题（如可能）

2. **判定问题级别**
   - **P0 (Critical)**: 
     - 标准：核心服务不可用，影响>50%用户或核心功能完全不可用
     - 响应时限：15分钟内
     - 修复时限：2小时内
     - 示例：支付系统完全不可用、数据库宕机、全站500错误
   
   - **P1 (Major)**: 
     - 标准：重要功能受损，影响10-50%用户或重要功能部分不可用
     - 响应时限：30分钟内
     - 修复时限：8小时内
     - 示例：订单查询失败、部分用户无法登录、性能严重退化
   
   - **P2 (Minor)**: 
     - 标准：一般问题，影响<10%用户或非核心功能异常
     - 响应时限：1小时内
     - 修复时限：24小时内
     - 示例：UI显示异常、非核心功能bug、轻微性能问题

3. **评估影响范围**
   - 识别受影响的服务和组件
   - 估算受影响的用户数量
   - 评估业务影响（收入损失、用户流失、品牌损害）
   - 确定优先级和紧急程度

4. **启动应急响应**
   - 根据问题级别启动相应流程
   - 通知相关人员（开发、运维、DBA、业务方）
   - 建立应急沟通渠道（微信群、Slack频道）
   - 指定应急指挥官

**检查点**：
- [ ] 问题级别判定准确
- [ ] 影响范围评估完整
- [ ] 应急响应流程已启动
- [ ] 相关人员已通知

**产出**：
- 问题评估报告
- 应急响应计划
- 沟通渠道建立

**质量标准**：
- 问题级别判定准确率≥95%
- 影响范围评估误差≤20%
- 响应时间符合级别要求

### 步骤 2：[LOCATE] 快速定位问题根因

**目的**：在30分钟内使用系统化方法定位问题根本原因

**输入**：
- 错误日志和异常堆栈
- 监控数据和指标
- 最近变更列表
- 系统架构图

**操作流程**：

1. **收集证据**
   - **日志分析**:
     - 查看应用日志（ERROR、WARN级别）
     - 查看系统日志（syslog、dmesg）
     - 查看访问日志（access log）
     - 提取关键错误信息和堆栈跟踪
   
   - **监控数据分析**:
     - 检查错误率趋势
     - 分析响应时间变化
     - 观察QPS波动
     - 检查资源使用情况（CPU、内存、磁盘、网络）
   
   - **最近变更排查**:
     - 列出最近24小时内的代码变更
     - 检查配置变更
     - 审查基础设施变更（部署、扩容、网络调整）
     - 识别可能的触发因素

2. **分析问题**
   - **时间关联分析**: 将问题发生时间与变更时间对比
   - **模式识别**: 识别问题的模式和规律
   - **影响链分析**: 追踪问题的传播路径
   - **假设验证**: 提出假设并通过证据验证

3. **使用5 Whys方法深入分析**
   ```
   问题现象 → Why? → 原因1 → Why? → 原因2 → Why? → 原因3 → Why? → 原因4 → Why? → 根本原因
   ```
   
   示例：
   - Why? 支付接口返回500错误
     → 因为PaymentService抛出NullPointerException
   - Why? 抛出NullPointerException
     → 因为user对象为null
   - Why? user对象为null
     → 因为getUserById()返回null
   - Why? getUserById()返回null
     → 因为数据库中用户记录被删除
   - Why? 用户记录被删除
     → **根本原因**: 数据清理脚本误删了活跃用户记录

4. **确认根因**
   - 验证根因是否能解释所有现象
   - 确认根因与证据一致
   - 排除其他可能性
   - 获得团队共识

**检查点**：
- [ ] 30分钟内定位根因
- [ ] 根因分析有充分证据支持
- [ ] 使用5 Whys方法深度分析
- [ ] 根因能解释所有现象

**产出**：
- 根因分析报告
- 证据清单
- 5 Whys分析过程

**质量标准**：
- 定位时间≤30分钟
- 根因准确率≥90%
- 分析过程有完整证据链

### 步骤 3：[DESIGN] 设计最小化修复方案

**目的**：设计最小化改动且有效的修复方案，确保可回滚

**输入**：
- 根因分析报告
- 系统架构和依赖关系
- 代码仓库访问权限
- 测试环境

**操作流程**：

1. **制定修复策略**
   - **直接修复**: 修改代码修复根本原因（首选）
   - **临时止血**: 通过配置、开关、限流等手段暂时缓解
   - **回滚版本**: 回滚到上一个稳定版本
   - **降级服务**: 关闭非核心功能，保障核心功能

2. **设计修复方案**
   - **代码修改**:
     - 识别需要修改的文件和函数
     - 设计具体的代码变更
     - 确保修改最小化（只改必要部分）
     - 考虑边界条件和异常情况
   
   - **风险评估**:
     - 评估修复的影响范围
     - 识别潜在风险点
     - 评估修复失败的可能性
     - 制定风险缓解措施
   
   - **回滚方案**:
     - 设计详细的回滚步骤
     - 准备回滚脚本或命令
     - 验证回滚方案的可行性
     - 预估回滚所需时间

3. **制定测试策略**
   - **单元测试**: 覆盖修复的代码路径
   - **集成测试**: 验证模块间交互
   - **回归测试**: 确保不引入新问题
   - **性能测试**: 验证修复不影响性能
   - **预发验证**: 在预发环境完整验证

4. **方案评审**
   - 组织快速代码审查（至少1人review）
   - 评估方案的可行性和风险
   - 确认测试计划的完整性
   - 获得必要的审批

**检查点**：
- [ ] 修复方案最小化（只修改必要部分）
- [ ] 风险评估完整
- [ ] 回滚方案可行
- [ ] 测试计划覆盖关键场景
- [ ] 方案经过评审

**产出**：
- 修复方案设计文档
- 风险评估报告
- 回滚方案
- 测试计划

**质量标准**：
- 修复方案简洁明了
- 风险评估覆盖所有关键点
- 回滚方案可执行
- 测试计划完整

### 步骤 4：[IMPLEMENT] 执行修复和测试

**目的**：高质量实施修复并通过全面测试，确保无新问题

**输入**：
- 修复方案设计文档
- 代码仓库
- 测试环境
- CI/CD流水线

**操作流程**：

1. **编写修复代码**
   - 按照设计方案编写代码
   - 遵循编码规范和最佳实践
   - 添加必要的注释说明
   - 保持代码简洁清晰

2. **代码审查**
   - 提交代码进行review
   - 至少1人审查通过
   - 重点关注：
     - 修复是否正确
     - 是否有遗漏的边界条件
     - 是否引入新的风险
     - 代码质量和可读性

3. **编写测试**
   - **单元测试**:
     - 覆盖修复的代码路径
     - 测试正常情况和异常情况
     - 测试边界条件
     - 目标覆盖率≥90%
   
   - **集成测试**:
     - 验证模块间交互
     - 测试API调用和数据流
     - 验证依赖服务的兼容性
   
   - **回归测试**:
     - 执行受影响功能的回归测试
     - 重点测试核心业务流程
     - 验证无新问题引入

4. **预发环境验证**
   - 部署到预发环境
   - 执行完整的测试套件
   - 验证修复效果
   - 观察系统稳定性
   - 模拟真实流量测试

**检查点**：
- [ ] 代码审查通过
- [ ] 单元测试覆盖率≥90%
- [ ] 回归测试通过
- [ ] 预发环境验证成功
- [ ] 无新问题引入

**产出**：
- 修复代码
- 测试报告
- 预发环境验证结果

**质量标准**：
- 代码质量高，无明显的code smell
- 测试覆盖全面
- 预发验证通过
- 无回归问题

### 步骤 5：[DEPLOY] 部署上线和监控

**目的**：安全部署修复并验证生效，确保系统稳定

**输入**：
- 修复代码和配置
- 部署系统和权限
- 监控平台
- 紧急发布审批（如需要）

**操作流程**：

1. **准备部署**
   - 打包修复代码和配置
   - 准备部署脚本
   - 确认回滚方案就绪
   - 获得紧急发布审批（如需要）

2. **执行部署**
   - **灰度发布**（推荐）:
     - 先部署到少量实例（5-10%）
     - 观察监控指标
     - 验证修复效果
     - 逐步扩大范围（25% → 50% → 100%）
   
   - **全量发布**（紧急情况）:
     - 一次性部署到所有实例
     - 密切监控指标
     - 准备好快速回滚

3. **监控验证**
   - **实时监控**:
     - 错误率是否恢复正常
     - 响应时间是否正常
     - QPS是否稳定
     - 资源使用是否正常
   
   - **业务指标**:
     - 核心业务流程是否正常
     - 用户投诉是否减少
     - 业务数据是否恢复
   
   - **观察期**:
     - 至少观察30分钟
     - 确认无异常波动
     - 验证修复持久有效

4. **确认修复完成**
   - 所有监控指标正常
   - 用户反馈正面
   - 业务数据恢复
   - 宣布修复完成

**检查点**：
- [ ] 部署过程顺利
- [ ] 修复生效后系统稳定
- [ ] 监控指标正常
- [ ] 观察期≥30分钟无异常
- [ ] 用户反馈正面

**产出**：
- 部署记录
- 监控报告
- 修复验证结果

**质量标准**：
- 部署成功率100%
- 修复有效性100%
- 系统稳定性≥99.9%
- 用户满意度提升

### 步骤 6：[REPORT] 产出修复报告和后续计划

**目的**：完整记录修复过程，制定后续改进计划，安排事后复盘

**输入**：
- 修复全过程记录
- 测试和部署结果
- 监控数据
- 用户反馈

**操作流程**：

1. **编写紧急修复报告**
   - **问题概要**: 问题描述、影响范围、持续时间
   - **根因分析**: 5 Whys分析过程和根本原因
   - **修复方案**: 采取的修复措施和技术细节
   - **测试验证**: 测试过程和结果
   - **部署上线**: 部署过程和监控验证
   - **时间线**: 从发现到修复完成的详细时间线

2. **记录关键决策**
   - 记录修复过程中的关键决策点
   - 说明决策的理由和依据
   - 记录备选方案和选择原因

3. **制定后续计划**
   - **短期行动**（1周内）:
     - 清理临时方案
     - 补充缺失的测试
     - 修复相关的技术问题
   
   - **长期改进**（1个月内）:
     - 架构优化
     - 流程改进
     - 工具建设
     - 能力提升
   
   - **技术债务**:
     - 识别修复过程中发现的技术债务
     - 制定清理计划
     - 排入开发计划

4. **安排事后复盘**
   - P0/P1故障必须在1周内进行复盘
   - 邀请相关人员参加
   - 准备复盘材料
   - 制定改进措施

5. **更新Global Context**
   - 更新故障状态为resolved
   - 记录修复信息
   - 更新系统健康状态
   - 记录残留风险和待办事项

**检查点**：
- [ ] 修复报告完整准确
- [ ] 时间线清晰
- [ ] 后续计划具体可执行
- [ ] 复盘会议已安排（P0/P1）
- [ ] Global Context已更新

**产出**：
- 紧急修复报告
- 后续行动计划
- 复盘会议安排
- Global Context更新

**质量标准**：
- 报告完整性100%
- 数据准确性100%
- 后续计划可操作性强
- 复盘会议按时举行

## Quality Standards

### 质量维度

| 维度 | 要求 | 权重 | 验收标准 |
|------|------|------|----------|
| 响应性 | 按规定时效响应 | 25% | P0≤15min, P1≤30min |
| 准确性 | 根因分析正确 | 25% | 30min内定位，准确率≥90% |
| 有效性 | 问题彻底解决 | 30% | 修复后无复发，回归率≤5% |
| 安全性 | 部署过程可控 | 20% | 可回滚，观察期≥30min无异常 |

### Key Performance Indicators (KPIs)

| KPI ID | 指标名称 | 目标值 | 计算公式 | 验证方法 | 权重 |
|--------|----------|--------|----------|----------|------|
| KPI-001 | HOTFIX-TIME-P0 | ≤2h | P0问题从发现到修复上线的时间 | 故障时间线统计 | 30% |
| KPI-002 | HOTFIX-TIME-P1 | ≤8h | P1问题从发现到修复上线的时间 | 故障时间线统计 | 25% |
| KPI-003 | REGRESSION-RATE | ≤5% | (修复引入新问题数/总修复数) × 100% | 回归测试统计 | 25% |
| KPI-004 | VERIFY-COVERAGE | 100% | 关键场景回归测试覆盖率 | 测试覆盖率报告 | 20% |

**综合评分计算**: 
```
Quality Score = (KPI-001得分 × 0.30) + (KPI-002得分 × 0.25) + (KPI-003得分 × 0.25) + (KPI-004得分 × 0.20)

KPI得分计算:
- HOTFIX-TIME-P0: ≤2h=100分, 2-4h=80分, 4-6h=60分, >6h=0分
- HOTFIX-TIME-P1: ≤8h=100分, 8-12h=80分, 12-24h=60分, >24h=0分
- REGRESSION-RATE: ≤5%=100分, 5-10%=80分, 10-15%=60分, >15%=0分
- VERIFY-COVERAGE: 100%=100分, 90-99%=80分, 80-89%=60分, <80%=0分

合格: ≥70分 | 优秀: ≥85分 | 卓越: ≥95分
```

## Error Handling

### Error Scenario 1: 根因不明 (P1)

**触发条件**: 30分钟内无法定位问题根因

**处理流程**:
```
IF 30分钟内无法定位根因
THEN
  1. 扩大日志收集范围（增加调试日志、启用详细追踪）
  2. 排查最近24小时内的所有变更
  3. 尝试临时止血方案（功能开关、限流降级、回滚版本）
  4. 升级到专家团队（架构师、资深开发、DBA）
  5. 组织战时会议，集体排查
END
```

**降级方案**: 实施临时止血措施，优先恢复服务

**升级条件**: 60分钟仍无法定位，或影响超过50%用户

### Error Scenario 2: 修复失败 (P1)

**触发条件**: 修复后问题仍然存在或引入新问题

**处理流程**:
```
IF 修复失败
THEN
  1. 立即回滚修复
  2. 重新分析问题根因
  3. 收集更多证据
  4. 制定新的修复方案
  5. 在小范围环境验证新方案
END
```

**降级方案**: 保持回滚状态，使用临时方案维持服务

**升级条件**: 3次修复尝试均失败，或问题持续恶化

### Error Scenario 3: 修复引发回归 (P0)

**触发条件**: 修复后其他功能出现异常

**处理流程**:
```
IF 检测到回归问题
THEN
  1. 立即评估回归问题的严重程度
  2. IF 回归问题≥原问题 THEN 立即回滚全部修复
  3. IF 回归问题<原问题 THEN 评估是否接受权衡
  4. 分析回归原因
  5. 制定修复回归的方案
END
```

**降级方案**: 回滚到修复前状态，重新评估修复方案

**升级条件**: 回归问题影响核心功能或超过原问题影响

### Error Scenario 4: 部署失败 (P0)

**触发条件**: 部署过程中出现错误或部署后服务无法启动

**处理流程**:
```
IF 部署失败
THEN
  1. 立即停止部署流程
  2. 自动或手动回滚到上一版本
  3. 验证回滚后系统恢复正常
  4. 分析部署失败原因
  5. 修复部署问题后重新部署
END
```

**降级方案**: 保持旧版本运行，寻找其他修复途径

**升级条件**: 多次部署失败，或无法回滚

## Constraints

1. **快速响应**: P0问题15分钟内响应，P1问题30分钟内响应
2. **最小化修复**: 只修复必要部分，避免大范围重构
3. **可回滚**: 修复必须可回滚，回滚方案必须提前准备
4. **完整测试**: 必须进行回归测试，确保无新问题
5. **详细记录**: 所有操作和决策必须有记录，便于复盘
6. **及时沟通**: 及时向相关方通报进展，每30分钟更新一次状态
