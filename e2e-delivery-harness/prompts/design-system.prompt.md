# Design System Architecture

> **版本**: 1.1.0 | **适用阶段**: 系统设计 | **预计工时**: 4-8小时

## Input Variables

| 变量名 | 类型 | 必填 | 说明 | 示例 |
|--------|------|------|------|------|
| `requirements_spec` | string | 是 | 需求规格说明书内容 | (需求文档) |
| `tech_stack_preference` | string[] | 否 | 技术栈偏好 | ["Java", "Spring Boot"] |
| `team_capabilities` | string[] | 否 | 团队技术能力 | ["微服务经验"] |
| `budget` | string | 否 | 预算限制 | "100万以内" |
| `timeline` | string | 否 | 时间限制 | "3个月内完成" |

## Chain of Thought

```
1. [THINK] 分析需求约束 → 技术要求是什么？
2. [THINK] 选择架构风格 → monolith/microservices/event-driven？
3. [THINK] 划分组件边界 → 组件职责是否单一？
4. [THINK] 设计数据模型 → 数据流是否清晰？
5. [THINK] 定义接口协议 → 服务间如何通信？
6. [THINK] 评估风险备选 → 有什么风险？如何应对？
7. [VALIDATE] 验证设计方案 → 是否满足所有需求？
8. [OUTPUT] 生成设计文档
```

## Error Handling

### 情况 1：需求与设计不匹配

```
IF 发现需求无法通过设计实现
THEN
  1. 明确指出不匹配的需求
  2. 分析原因（需求冲突、技术限制、资源不足）
  3. 提出替代方案或需要调整的需求
  4. 标记为 [设计冲突-需确认]
END
```

### 情况 2：技术选型不确定

```
IF 多个技术选项都可接受
THEN
  1. 列出各选项的优缺点
  2. 根据团队能力和项目约束给出建议
  3. 选择最优方案并说明理由
  4. 记录备选方案
END
```

### 情况 3：组件边界不清晰

```
IF 组件职责重叠或划分不合理
THEN
  1. 重新分析业务边界
  2. 按单一职责原则重新划分
  3. 明确组件间的契约
  4. 更新架构图
END
```

## Task Steps

### 步骤 1：架构概述设计

**任务**：
- 确定架构风格（单体/微服务/分层等）
- 划分系统边界
- 确定技术栈
- 定义设计原则

**产出**：架构概述

### 步骤 2：组件架构设计

**任务**：
- 识别核心组件
- 定义组件职责
- 设计组件交互
- 绘制组件架构图

**产出**：组件架构文档

### 步骤 3：数据架构设计

**任务**：
- 设计数据模型
- 确定数据存储策略
- 设计数据流
- 考虑数据安全

**产出**：数据架构文档

### 步骤 4：接口设计

**任务**：
- 识别对外接口
- 定义接口规范（REST/gRPC等）
- 设计接口协议
- 制定错误处理规范

**产出**：接口设计文档

### 步骤 5：部署架构设计

**任务**：
- 设计部署拓扑
- 确定部署策略
- 设计容灾方案
- 规划扩容机制

**产出**：部署架构文档

### 步骤 6：风险与决策

**任务**：
- 识别技术风险
- 制定应对策略
- 记录关键决策

**产出**：风险分析报告

## Constraints

1. **语言**：输出使用中文
2. **格式**：严格遵循上述输出格式
