# Monitoring & Operations Skill

## Use When

使用此技能的场景：

### 主要场景
- ✅ 应用上线后需要配置完整的监控体系
- ✅ 收到告警通知需要进行处理和排查
- ✅ 需要进行日常巡检和系统健康检查
- ✅ 发生系统故障需要应急响应和修复
- ✅ 需要进行容量评估和扩容规划
- ✅ 需要优化监控告警配置和降低噪声
- ✅ 需要编写运维手册和应急预案
- ✅ 需要进行SLO分析和Error Budget管理
- ✅ 需要进行故障复盘和持续改进

### 前置条件
- 系统已部署完成并运行
- 有基本的监控基础设施（Prometheus、Grafana等）
- 有明确的SLO目标和业务指标定义

### SLO Targets Structure

```typescript
interface SLOTargets {
  availability: number;          // 可用性目标 (如 99.9%)
  latency_p50: number;           // 延迟 P50 目标 (ms)
  latency_p99: number;           // 延迟 P99 目标 (ms)
  error_rate: number;            // 错误率目标 (%)
  recovery_time: number;         // 恢复时间目标 (分钟)
  error_budget_monthly: number;  // 月度错误预算 (分钟)
}
```

### OnCall Structure

```typescript
interface OnCall {
  primary: string;               // 主值班人员
  secondary: string;             // 备值班人员

  handover_time: string;         // 交接班时间 (如 "09:00 UTC+8")
}
```

## Instructions

### 步骤 1：监控方案设计

**目标**：设计完整的三层监控指标体系

**操作流程**：

1. **理解系统和SLO**
   - 分析系统架构和关键组件
   - 确认SLO目标和业务优先级
   - 识别关键监控点和依赖关系

2. **设计基础设施层监控**
   - CPU使用率和负载
   - 内存使用率和Swap
   - 磁盘使用率和I/O
   - 网络带宽和连接数
   - 文件系统inode使用率

3. **设计应用层监控（黄金指标）**
   - **Latency**: 请求延迟（P50, P90, P95, P99）
   - **Traffic**: 请求流量（QPS、并发数）
   - **Errors**: 错误率（HTTP 5xx、异常抛出率）
   - **Saturation**: 饱和度（线程池、连接池、队列长度）

4. **设计业务层监控**
   - 核心业务指标（订单量、转化率、支付成功率）
   - 用户行为指标（日活、留存、访问路径）
   - 业务异常指标（订单失败、支付失败、登录失败）

5. **设置告警规则**
   - 基于历史数据分析设置阈值
   - 定义告警级别（P0/P1/P2/P3）
   - 配置告警通知渠道和升级策略
   - 设置告警静默期和防抖机制

6. **创建监控仪表盘**
   - 系统总览仪表盘（整体健康状态）
   - 服务详情仪表盘（各微服务性能）
   - 业务指标仪表盘（业务数据和转化）
   - 容量视图仪表盘（资源使用和趋势）

**检查点**：
- [ ] 黄金指标全覆盖（Latency, Traffic, Errors, Saturation）
- [ ] 三层监控完整（基础设施、应用、业务）
- [ ] 告警阈值基于历史数据设置
- [ ] 告警通知渠道已测试畅通
- [ ] 监控覆盖度 ≥95%
- [ ] 仪表盘布局合理，信息清晰

**产出**：
- 监控配置文档（YAML/JSON格式）
- 告警规则配置
- 仪表盘定义文件
- 监控指标字典

### 步骤 2：日常巡检执行

**目标**：定期检查系统运行状态，及时发现潜在问题

**操作流程**：

1. **系统健康检查**
   - 检查所有服务是否正常运行
   - 检查关键进程状态
   - 检查系统负载和响应时间
   - 检查日志是否有异常

2. **资源使用情况检查**
   - CPU使用率及趋势
   - 内存使用率及Swap情况
   - 磁盘使用率和I/O性能
   - 网络带宽和连接数
   - 数据库连接池使用情况

3. **业务指标检查**
   - 核心业务KPI是否正常
   - 与历史同期对比分析
   - 识别异常波动和趋势
   - 检查业务异常率

4. **告警情况分析**
   - 查看未处理告警
   - 分析告警趋势和模式
   - 识别重复告警和误报
   - 检查告警响应时效

5. **SLO合规性检查**
   - 计算当前SLO达成情况
   - 检查Error Budget剩余量
   - 分析SLO趋势和预测
   - 识别SLO风险

6. **生成巡检报告**
   - 汇总巡检结果
   - 标记异常和关注项
   - 提出改进建议
   - 归档巡检记录

**检查点**：
- [ ] 巡检项目完整率 100%
- [ ] 异常识别准确率 ≥95%
- [ ] 巡检记录可追溯
- [ ] 改进建议具体可执行
- [ ] 巡检周期符合要求

**产出**：
- 巡检报告（Markdown格式）
- 异常情况清单
- 改进建议列表

### 步骤 3：告警响应处理

**目标**：及时响应和处理告警，确保系统稳定运行

**操作流程**：

1. **告警接收和分类**
   - 接收告警通知
   - 判断告警级别（P0/P1/P2/P3）
   - 评估影响范围和紧急程度
   - 确定响应时限

2. **告警验证**
   - 确认告警真实性（排除误报）
   - 检查相关监控指标
   - 查看系统日志和事件
   - 验证告警触发条件

3. **告警分级响应**
   - **P0 (Critical)**: 立即响应，电话+短信通知，全员待命
   - **P1 (Major)**: 15分钟内响应，短信+钉钉通知，相关人员处理
   - **P2 (Minor)**: 1小时内响应，钉钉通知，值班人员处理
   - **P3 (Warning)**: 下一个工作日处理，邮件通知，记录跟踪

4. **问题定位和分析**
   - 收集相关信息（日志、监控、调用链路）
   - 分析问题根因（使用5 Whys方法）
   - 识别受影响的服务和用户
   - 评估故障持续时间

5. **执行处理措施**
   - 优先快速止血（重启、回滚、降级、限流）
   - 执行Runbook中的标准操作
   - 必要时启动应急预案
   - 通知相关方和利益相关者

6. **验证和闭环**
   - 验证处理效果
   - 确认告警消除
   - 更新告警记录和状态
   - 通知相关方故障已恢复

7. **后续跟进**
   - 记录告警处理过程
   - 分析告警根因
   - 制定预防措施
   - 更新Runbook和文档

**检查点**：
- [ ] 告警响应时效符合级别要求
- [ ] 告警级别判断准确
- [ ] 处理措施得当有效
- [ ] 告警记录完整准确
- [ ] 告警闭环率 100%
- [ ] MTTD ≤5min, MTTR ≤30min

**产出**：
- 告警处理记录
- 根因分析报告
- 改进措施清单

### 步骤 4：故障排查修复

**目标**：快速定位和解决系统故障，最小化影响

**操作流程**：

1. **故障确认和定级**
   - 确认故障现象和影响范围
   - 评估故障严重程度
   - 确定故障级别（P0/P1）
   - 启动相应应急响应流程

2. **快速止血（优先）**
   - 重启故障服务
   - 回滚到上一个稳定版本
   - 启用降级方案
   - 实施限流保护
   - 切换流量到备用系统

3. **信息收集**
   - 收集系统日志（应用日志、系统日志、访问日志）
   - 收集监控数据（CPU、内存、延迟、错误率）
   - 收集调用链路追踪信息
   - 收集数据库查询和慢查询日志
   - 记录故障时间线

4. **根因分析**
   - 使用5 Whys方法深入分析
   - 分析代码变更和配置变更
   - 检查依赖服务和外部系统
   - 分析资源使用和性能瓶颈
   - 识别根本原因和触发因素

5. **制定修复方案**
   - 评估多个修复方案的可行性
   - 选择最优修复方案
   - 制定详细修复步骤
   - 评估修复风险和影响
   - 准备回滚方案

6. **执行修复**
   - 按步骤执行修复操作
   - 实时监控修复效果
   - 验证系统功能恢复
   - 确认性能指标正常
   - 观察一段时间确保稳定

7. **故障总结和复盘**
   - 编写详细的故障报告
   - 组织故障复盘会议
   - 分析故障根因和教训
   - 制定改进措施和行动计划
   - 更新应急预案和Runbook

**检查点**：
- [ ] 故障定位准确率 ≥90%
- [ ] 故障修复成功率 100%
- [ ] 故障报告包含完整时间线
- [ ] 根因分析使用5 Whys方法
- [ ] 改进措施具体可执行
- [ ] MTTR ≤30min

**产出**：
- 故障报告（含时间线、根因、改进措施）
- 故障复盘会议纪要
- 改进行动计划
- 更新的应急预案

### 步骤 5：容量管理评估

**目标**：评估当前容量，预测未来需求，制定扩容计划

**操作流程**：

1. **当前容量评估**
   - 分析CPU使用率和负载趋势
   - 分析内存使用率和GC情况
   - 分析磁盘使用率和I/O性能
   - 分析网络带宽和连接数
   - 分析数据库容量和性能

2. **资源使用趋势分析**
   - 收集至少30天的历史数据
   - 分析资源使用增长率
   - 识别周期性模式和峰值
   - 预测资源耗尽时间
   - 识别容量瓶颈

3. **业务增长预测**
   - 分析业务增长趋势
   - 预测未来用户量和交易量
   - 考虑季节性因素和促销活动
   - 评估新功能对容量的影响
   - 与市场和产品团队对齐预期

4. **容量需求预测**
   - 基于业务预测计算资源需求
   - 考虑冗余和缓冲（通常预留30-50%）
   - 评估不同场景下的容量需求（正常、峰值、灾难）
   - 制定多时间维度的预测（短期1个月、中期3个月、长期6-12个月）

5. **制定扩容计划**
   - 确定扩容时机（预防性扩容 vs 紧急扩容）
   - 选择扩容方案（垂直扩容 vs 水平扩容）
   - 评估成本和收益
   - 制定详细实施时间表
   - 准备自动化扩缩容策略

6. **成本优化**
   - 分析资源使用效率
   - 识别闲置和低效资源
   - 优化资源配置（rightsizing）
   - 考虑预留实例或节省计划
   - 平衡性能和成本

**检查点**：
- [ ] 容量评估准确性 ≥90%
- [ ] 扩容计划可行性 100%
- [ ] 成本优化建议合理
- [ ] 趋势分析基于充分数据（≥30天）
- [ ] 预留足够的缓冲空间（30-50%）

**产出**：
- 容量评估报告
- 容量趋势分析图表
- 扩容计划和 Timeline
- 成本优化建议

## Quality Criteria

### 质量维度

| 维度 | 标准 | 权重 | 检查方法 |
|------|------|------|----------|
| 稳定性 | 系统稳定运行，SLO达标 | 30% | SLO合规率≥99.5% |
| 响应性 | 告警和故障及时响应 | 25% | MTTD≤5min, MTTR≤30min |
| 可观测性 | 监控完善有效 | 25% | 监控覆盖度≥95% |

### Key Performance Indicators (KPIs)

| KPI ID | 指标名称 | 目标值 | 计算公式 | 验证方法 | 权重 |
|--------|----------|--------|----------|----------|------|
| KPI-001 | MTTD | ≤5min | 异常发生到告警触发的平均时间 | 告警日志分析 | 25% |
| KPI-002 | MTTR | ≤30min | 告警触发到问题修复的平均时间 | 故障记录统计 | 25% |
| KPI-003 | ALERT-NOISE | ≤20% | (无效告警数/总告警数) × 100% | 告警有效性分析 | 20% |
| KPI-004 | SLO-COMPLY | ≥99.5% | (SLO达标时间/总时间) × 100% | SLO监控面板 | 30% |

**综合评分计算**: 
```
Quality Score = (KPI-001得分 × 0.25) + (KPI-002得分 × 0.25) + (KPI-003得分 × 0.20) + (KPI-004得分 × 0.30)

KPI得分计算:
- MTTD: ≤5min=100分, 5-10min=80分, 10-15min=60分, >15min=0分
- MTTR: ≤30min=100分, 30-60min=80分, 60-120min=60分, >120min=0分
- ALERT-NOISE: ≤20%=100分, 20-30%=80分, 30-40%=60分, >40%=0分
- SLO-COMPLY: ≥99.5%=100分, 99-99.5%=80分, 98-99%=60分, <98%=0分

合格: ≥70分 | 优秀: ≥85分 | 卓越: ≥95分
```

## Troubleshooting

### Issue 1: 告警风暴
**Symptom**: 短时间内大量告警同时触发（>10个/分钟），告警通知渠道被淹没

**Cause**: 
- 核心组件故障引发级联效应
- 告警规则设置不合理，缺乏聚合
- 网络分区或基础设施故障

**Resolution**:
1. 立即识别根本告警（触发其他告警的根源）
2. 暂时抑制次要告警，保留关键告警
3. 优先处理核心问题，恢复核心服务
4. 通知相关团队协同处理
5. 事后优化告警规则（调整阈值、增加依赖关系、设置静默期）

### Issue 2: 告警误报频繁
**Symptom**: 告警触发但系统实际运行正常，误报率>30%

**Cause**: 
- 告警阈值设置过于敏感
- 未考虑业务的周期性波动
- 数据采集异常或瞬时波动

**Resolution**:
1. 分析历史数据，了解正常波动范围
2. 调整告警阈值，增加合理的缓冲
3. 增加告警条件（如持续时间、多次确认）
4. 使用动态阈值或基线告警
5. 实施告警聚合和去重

### Issue 3: 监控数据缺失
**Symptom**: 关键指标无数据或数据中断超过5分钟

**Cause**: 
- 监控Agent离线或崩溃
- 网络连通性问题
- 数据存储或查询服务故障
- 指标定义错误

**Resolution**:
1. 检查采集Agent状态（是否运行、资源是否正常）
2. 检查网络连通性（Agent到监控服务器的连接）
3. 验证指标定义是否正确（指标名称、标签、单位）
4. 检查数据存储和查询服务
5. 启动备用监控方案或增加手动巡检频率
6. 修复后验证数据恢复正常

### Issue 4: SLO持续违反
**Symptom**: SLO连续多天不达标，Error Budget快速消耗

**Cause**: 
- SLO目标设置不合理（过于严格）
- 系统存在持续性性能问题
- 频繁发布引入不稳定因素
- 容量不足导致性能下降

**Resolution**:
1. 分析SLO违反的具体指标和原因
2. 评估SLO目标的合理性，必要时调整
3. 暂停非紧急发布，稳定系统
4. 识别和修复性能瓶颈
5. 实施限流、降级保护措施
6. 考虑扩容或架构优化
7. 与业务方沟通，对齐期望

### Issue 5: 故障定位困难
**Symptom**: 故障发生后难以快速定位根因，MTTR超标

**Cause**: 
- 监控覆盖不全，缺少关键指标
- 日志记录不完整或不清晰
- 缺少分布式追踪
- 系统复杂度高，依赖关系不清

**Resolution**:
1. 补充缺失的监控指标和日志
2. 实施分布式追踪（如Jaeger、Zipkin）
3. 绘制系统依赖关系图
4. 建立故障排查手册和Checklist
5. 定期进行故障演练
6. 加强团队技术培训

## Core Knowledge

### Domain Fundamentals

#### 1. SRE核心理念
- **SLO (Service Level Objective)**: 服务水平目标，定义系统应达到的可靠性标准
- **SLI (Service Level Indicator)**: 服务水平指标，用于衡量SLO达成情况的具体指标
- **Error Budget**: 错误预算，允许的系统不可用时间，用于平衡创新和稳定性
- ** Toil Reduction**: 减少重复性手工劳动，提高自动化水平

#### 2. 黄金指标 (Golden Signals)
- **Latency**: 请求延迟，包括P50、P90、P95、P99等百分位值
- **Traffic**: 请求流量，如QPS、并发数、吞吐量
- **Errors**: 错误率，如HTTP 5xx比例、异常抛出率
- **Saturation**: 饱和度，如线程池使用率、连接池使用率、队列长度

#### 3. 三层监控体系
- **基础设施层**: CPU、内存、磁盘、网络等硬件资源监控
- **应用层**: 应用性能、服务健康、中间件状态等
- **业务层**: 业务KPI、用户行为、交易数据等

#### 4. 告警分级标准
- **P0 (Critical)**: 核心服务不可用，影响大部分用户，需立即响应
- **P1 (Major)**: 重要功能受影响，影响部分用户，15分钟内响应
- **P2 (Minor)**: 非核心功能异常，影响少量用户，1小时内响应
- **P3 (Warning)**: 潜在风险或预警，下一个工作日处理

### Key Principles

1. **稳定性优先原则**: 在任何决策中，系统稳定性始终是最高优先级
2. **数据驱动原则**: 所有决策和优化都应基于数据和事实，而非直觉
3. **快速响应原则**: 对告警和故障保持高敏感度，按规定时效快速响应
4. **预防为主原则**: 通过监控、预警、容量规划提前识别和规避风险
5. **持续改进原则**: 定期复盘和优化，不断提升系统稳定性和运维效率
6. **自动化优先原则**: 优先寻求自动化解决方案，减少人工干预
7. **透明沟通原则**: 及时向相关方通报系统状态、故障进展和改进措施
8. **闭环管理原则**: 所有告警和故障必须形成闭环，有始有终

## Best Practices

### 监控配置最佳实践

1. **分层监控，全面覆盖**: 基础设施层、应用层、业务层三层监控缺一不可，确保监控覆盖度≥95%

2. **黄金指标优先**: 始终确保Golden Signals（Latency, Traffic, Errors, Saturation）全覆盖，这是监控的基础

3. **智能告警，动态阈值**: 基于历史数据动态调整阈值，使用基线告警和异常检测，避免固定阈值的局限性

4. **告警去重和聚合**: 使用告警聚合、依赖关系、静默期等机制，减少重复告警，目标告警噪声率≤20%

5. **渐进式告警**: 从Warning到Critical逐步升级，给系统自愈时间，避免过度反应

6. **告警必须有Action**: 每个告警都应有明确的处理流程和责任人，避免无效告警

7. **定期审查监控配置**: 每月审查监控覆盖度和告警有效性，及时优化和调整

### 故障处理最佳实践

1. **快速止血优先**: 优先恢复服务（重启、回滚、降级、限流），再分析根因，目标是缩短MTTR

2. **并行处理**: 同时进行调查、沟通、修复，提高效率，不要串行等待

3. **透明沟通**: 及时向相关方通报故障状态和进展，每15-30分钟更新一次

4. **完整记录**: 详细记录时间线、操作、决策，便于复盘和学习

5. **5 Whys深度分析**: 使用5 Whys方法深入分析根因，不止于表面现象

6. **事后复盘**: 所有P0/P1故障必须进行复盘，制定具体的改进措施和时间表

7. **故障演练**: 定期进行故障演练和混沌工程测试，验证应急预案的有效性

### 容量管理最佳实践

1. **预防性扩容**: 资源使用率达到70%时开始规划扩容，不要等到80%以上

2. **基于数据的趋势分析**: 基于至少30天数据进行趋势预测，考虑季节性和周期性

3. **弹性设计**: 优先使用自动扩缩容（HPA、VPA），应对突发流量

4. **预留缓冲**: 通常预留30-50%的缓冲空间，应对突发情况和业务增长

5. **成本优化**: 定期评估资源使用效率，优化配置，考虑预留实例或节省计划

6. **压力测试验证**: 定期进行压力测试，验证容量规划的准确性和系统极限

### SLO管理最佳实践

1. **合理的SLO**: SLO应具有挑战性但可实现，通常99%-99.99%，根据业务重要性调整

2. **Error Budget驱动决策**: 将Error Budget作为发布决策的重要依据，Budget不足时暂停发布

3. **多维度SLO**: 同时关注可用性、延迟、错误率等多个维度，全面评估系统健康

4. **定期回顾**: 每月回顾SLO达成情况，分析趋势，必要时调整SLO

5. **利益相关方参与**: 与产品、开发、业务团队共同定义SLO，确保对齐业务目标

### 运维自动化最佳实践

1. **Infrastructure as Code**: 使用Terraform、Ansible等工具管理基础设施

2. **ChatOps**: 通过聊天机器人执行常见运维操作，提高效率和透明度

3. **自动化告警路由**: 根据告警类型和级别自动路由到合适的处理人

4. **自动化故障恢复**: 对已知问题实现自动化检测和恢复（自愈系统）

5. **自动化报告**: 自动生成运维报告、SLO报告、容量报告，减少手工工作

## Anti-patterns (反模式)

> 与 Common Pitfalls 同义，执行时合并检查。

## Common Pitfalls

### Pitfall 1: 告警疲劳
**Risk**: 告警过多导致运维人员对告警麻木，忽略真正重要的告警

**Prevention**: 
- 严格控制告警阈值，确保每个告警都有明确的Action
- 定期分析告警数据，消除无效告警和误报
- 实施告警分级、聚合和去重机制
- 目标：告警噪声率 ≤20%，每人每天告警<10条

**Impact**: 如果未避免，可能导致重要告警被忽略，延长故障发现和修复时间，甚至造成严重业务损失

### Pitfall 2: 监控盲区
**Risk**: 关键指标未被监控，故障发生时无法及时发现

**Prevention**: 
- 使用黄金指标框架确保覆盖全面
- 定期审查监控覆盖率，识别盲区
- 从历史故障中学习，补充监控盲点
- 进行混沌工程测试，验证监控有效性
- 目标：监控覆盖度 ≥95%

**Impact**: 如果未避免，可能导致故障发现延迟，MTTD超标，影响用户体验和业务

### Pitfall 3: 过度依赖自动化
**Risk**: 完全依赖自动化告警和修复，忽视人工判断和经验

**Prevention**: 
- 自动化与人工判断相结合，保持人工干预能力
- 定期人工巡检，发现自动化可能遗漏的问题
- 建立完善的升级机制，复杂问题及时升级到人
- 保持应急预案和手动操作能力
- 定期演练手动操作流程

**Impact**: 如果未避免，可能在自动化失效时无法及时响应，造成系统长时间不可用

### Pitfall 4: 忽视Error Budget
**Risk**: 不关注Error Budget消耗情况，导致SLO违反而不自知

**Prevention**: 
- 实时监控Error Budget剩余量和消耗速率
- 当Error Budget消耗过快时主动采取措施（限流、降级、暂停发布）
- 将Error Budget作为发布决策的重要依据
- 定期（每周）回顾Error Budget使用情况
- 设置Error Budget预警（剩余50%、30%、10%时告警）

**Impact**: 如果未避免，可能导致SLO违反，影响用户体验和业务，损害公司信誉

### Pitfall 5: 故障复盘不彻底
**Risk**: 故障处理后不进行深度复盘，同类故障反复发生

**Prevention**: 
- 所有P0/P1故障必须在1周内进行复盘
- 使用5 Whys方法深入分析根因，不止于表面现象
- 制定具体的改进措施、责任人和时间表
- 跟踪改进措施落实情况，确保闭环
- 建立故障案例库，分享经验和教训

**Impact**: 如果未避免，同类故障可能反复发生，影响系统稳定性，团队无法从故障中学习成长

### Pitfall 6: 容量规划不足
**Risk**: 容量规划不及时或不准确，导致资源耗尽引发故障

**Prevention**: 
- 基于至少30天数据进行趋势分析
- 预留30-50%的缓冲空间
- 考虑业务增长、季节性、促销活动等因素
- 定期进行压力测试验证容量
- 实施自动扩缩容应对突发流量
- 提前1-2个月规划扩容

**Impact**: 如果未避免，可能导致资源耗尽引发系统故障，影响业务连续性

### Pitfall 7: 文档滞后
**Risk**: 运维文档、Runbook、应急预案未及时更新，故障时无法有效指导处理

**Prevention**: 
- 每次变更后立即更新相关文档
- 每月定期审查文档准确性和完整性
- 故障复盘后更新应急预案和Runbook
- 建立文档更新的责任制和检查机制
- 定期演练验证文档有效性

**Impact**: 如果未避免，可能导致故障处理效率低下，延长MTTR，甚至错误操作加剧故障
