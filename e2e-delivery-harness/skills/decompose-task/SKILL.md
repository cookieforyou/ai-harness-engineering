# Task Decomposition Skill

## Skill Overview

这是一个**任务分解与规划专业技能包**，提供将复杂架构设计转换为可执行开发任务的系统化方法、最佳实践和工具。

### Core Competencies

- **任务分解技术**: INVEST原则、功能点分析、WBS工作分解结构
- **依赖分析方法**: 依赖图绘制、关键路径识别、并行优化
- **工作量估算**: 三点估算法、Planning Poker、历史数据参考
- **迭代规划**: Sprint计划、里程碑管理、容量平衡
- **风险管理**: 风险识别、影响评估、应对策略制定

## Use When (使用场景)

### 主要场景
- ✅ **架构设计完成后**: 需要将架构转换为可执行任务
- ✅ **Sprint规划前**: 需要制定详细的迭代计划
- ✅ **需求变更时**: 需要重新评估和调整任务分解
- ✅ **团队规模变化**: 需要重新分配任务和调整计划

### 次要场景
- ⚠️ **项目进度不理想**: 需要重新规划和优化
- ⚠️ **风险评估**: 需要识别关键路径和风险点

### 不适用场景
- ❌ 需求尚未明确（应先进行需求分析）
- ❌ 技术方案未确定（应先完成技术设计）

## Instructions (执行指令)

### 步骤 1：任务识别

**目标**: 从架构设计中识别需要完成的开发任务

**操作方法**:
1. **按模块拆解**: 将每个功能模块拆分为具体任务
2. **基础设施任务**: 识别服务器、数据库、CI/CD等基础设施任务
3. **公共模块任务**: 识别共享组件、工具类、框架封装任务
4. **集成任务**: 识别API对接、第三方系统集成任务
5. **测试任务**: 识别单元测试、集成测试、性能测试任务
6. **文档任务**: 识别技术文档、API文档、用户手册任务

**检查清单**:
- [ ] 所有功能模块都有对应任务
- [ ] 基础设施任务已识别
- [ ] 任务分类清晰（功能/基础设施/测试/文档）

**输出**: 初步任务列表

---

### 步骤 2：任务细化

**目标**: 将大任务拆分为符合INVEST原则的小任务

**操作方法**:
1. **粒度评估**: 检查每个任务的估算工作量
2. **拆分过粗任务**: 将>5天的任务拆分为子任务
3. **合并过细任务**: 将<0.5天的相关任务合并
4. **定义验收标准**: 为每个任务制定可量化的验收标准
5. **标注任务类型**: 标记功能/技术债务/基础设施/测试

**INVEST原则检查**:
- ✅ **Independent**: 任务是否独立？
- ✅ **Negotiable**: 任务是否可协商？
- ✅ **Valuable**: 任务是否有价值？
- ✅ **Estimable**: 任务是否可估算？
- ✅ **Small**: 任务是否足够小（1-3天）？
- ✅ **Testable**: 任务是否可测试？

**检查清单**:
- [ ] 90%任务在1-3天范围内
- [ ] 每个任务有明确的验收标准
- [ ] 所有任务符合INVEST原则

**输出**: 细化后的任务清单

---

### 步骤 3：依赖分析

**目标**: 分析任务间的依赖关系并绘制依赖图

**操作方法**:
1. **硬依赖识别**: 识别必须先完成的技术依赖
2. **软依赖识别**: 识别建议顺序的逻辑依赖
3. **并行机会**: 识别可并行执行的任务组
4. **绘制依赖图**: 使用Mermaid或绘图工具可视化
5. **关键路径识别**: 找出决定总工期的关键路径

**检查清单**:
- [ ] 所有依赖关系已标注
- [ ] 无循环依赖
- [ ] 关键路径已识别
- [ ] 并行任务组已分组

**输出**: 任务依赖图和关键路径分析

---

### 步骤 4：工作量估算

**目标**: 基于历史数据和团队能力进行准确估算

**操作方法**:
1. **历史数据参考**: 查找类似任务的历史估算和实际工时
2. **三点估算法**: 
   - 乐观估算 (O): 一切顺利的情况
   - 悲观估算 (P): 遇到各种问题的情况
   - 最可能估算 (M): 正常情况
   - 最终估算 = (O + 4M + P) / 6
3. **考虑学习曲线**: 新技术预留20-30%学习时间
4. **风险缓冲**: 高风险任务增加10-20%缓冲
5. **汇总迭代工时**: 计算每个Sprint的总工时

**检查清单**:
- [ ] 每个任务都有估算
- [ ] 估算有依据支撑（历史数据或专家判断）
- [ ] 已预留10-20%缓冲时间
- [ ] 总工时不超过团队产能

**输出**: 带估算的任务清单

---

### 步骤 5：优先级排序

**目标**: 基于业务价值、技术风险和依赖关系确定优先级

**操作方法**:
1. **业务价值评估**: 高价值功能优先
2. **技术依赖考虑**: 被依赖多的任务优先
3. **风险因素评估**: 高风险任务安排在早期
4. **干系人期望**: 考虑客户和管理层的优先级
5. **优先级分级**: P0(紧急重要)、P1(重要不紧急)、P2(其他)

**优先级矩阵**:
| 优先级 | 业务价值 | 技术风险 | 依赖程度 | 示例 |
|--------|----------|----------|----------|------|
| P0 | 高 | 高 | 高 | 核心认证模块 |
| P1 | 高 | 中 | 中 | 主要功能模块 |
| P2 | 中 | 低 | 低 | 辅助功能 |

**检查清单**:
- [ ] 所有任务都有优先级
- [ ] 优先级与业务价值匹配
- [ ] P0任务已确认并获得干系人认可

**输出**: 带优先级的任务清单

---

### 步骤 6：迭代规划

**目标**: 将任务分配到Sprint并制定里程碑计划

**操作方法**:
1. **确定Sprint周期**: 通常1-2周（7-14天）
2. **设定Sprint目标**: 每个Sprint有明确的可交付成果
3. **分配任务到Sprint**: 
   - 优先安排P0任务
   - 考虑依赖关系
   - 平衡负载（不超过产能90%）
4. **制定里程碑**: 识别关键的交付节点
5. **预留缓冲**: 最后一个Sprint预留20%缓冲

**容量计算公式**:
```
可用工时 = 团队人数 × 每日有效工时 × Sprint天数
计划工时 = 可用工时 × 90% （预留10%缓冲）
```

**检查清单**:
- [ ] 每个Sprint有明确目标
- [ ] Sprint负载平衡（≤90%产能）
- [ ] 里程碑已确定并与业务目标对齐

**输出**: 迭代计划和里程碑

---

### 步骤 7：资源分配

**目标**: 基于技能匹配和负载均衡分配任务给团队成员

**操作方法**:
1. **技能匹配**: 根据成员技能分配对应任务
2. **负载平衡**: 确保每个成员工作量均衡
3. **成长机会**: 适当分配挑战性任务促进成长
4. **标注负责人**: 明确每个任务的负责人
5. **确认可用性**: 确认成员在Sprint期间可用

**检查清单**:
- [ ] 任务已分配给具体成员
- [ ] 技能匹配度≥80%
- [ ] 负载均衡（最大差异≤20%）

**输出**: 任务分配方案

## Core Knowledge (核心知识)

### Domain Fundamentals

- **INVEST原则**: Independent, Negotiable, Valuable, Estimable, Small, Testable
- **WBS工作分解结构**: 将项目逐层分解为可管理的工作包
- **关键路径法(CPM)**: 识别决定项目总工期的任务序列
- **三点估算法**: PERT估算技术，考虑不确定性
- **敏捷迭代**: Sprint规划、每日站会、回顾会议

### Key Principles

1. **系统化拆解**: 从整体到局部，确保无遗漏
2. **数据驱动决策**: 基于历史数据和量化指标
3. **协作导向**: 考虑团队能力和技能匹配
4. **风险管理**: 早期识别并应对高风险任务
5. **持续优化**: 根据反馈调整分解策略

---

## Best Practices (最佳实践)

1. **先粗后细**: 先识别大模块，再逐步细化到具体任务
2. **参考历史**: 充分利用历史项目的估算数据
3. **团队参与**: 让团队成员参与估算和规划过程
4. **预留缓冲**: 每个Sprint预留10-20%缓冲时间
5. **可视化依赖**: 使用图表清晰展示依赖关系
6. **定期回顾**: 每个Sprint后回顾估算准确性并改进

## Common Pitfalls (常见陷阱)

### Pitfall 1: 任务粒度过粗
**风险**: 任务>5天，难以跟踪进度，风险隐藏
**预防**: 严格执行INVEST原则，拆分到1-3天
**影响**: 进度不透明，延期风险高

### Pitfall 2: 忽略依赖关系
**风险**: 任务执行时发现未预见的依赖，导致阻塞
**预防**: 仔细分析技术依赖，绘制依赖图
**影响**: 开发中断，返工成本高

### Pitfall 3: 估算过于乐观
**风险**: 未考虑学习曲线和风险，估算偏小
**预防**: 使用三点估算，预留缓冲时间
**影响**: Sprint无法完成，团队压力大

### Pitfall 4: 忽视非功能任务
**风险**: 忘记测试、文档、部署等任务
**预防**: 使用检查清单，确保全覆盖
**影响**: 交付质量差，后期补救成本高
