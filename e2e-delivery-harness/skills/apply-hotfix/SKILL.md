# Hotfix Skill

## Use When

使用此技能的场景：

### 主要场景
- ✅ 生产环境发生P0级别故障（核心服务不可用）
- ✅ 生产环境发生P1级别故障（重要功能受损）
- ✅ 监控系统检测到严重异常需要紧急处理
- ✅ 用户大量投诉某个功能需要快速修复
- ✅ 安全漏洞需要紧急修补
- ✅ 数据一致性错误需要紧急修正
- ✅ 性能严重退化影响用户体验

### 前置条件
- 有访问生产环境日志和监控的权限
- 有代码仓库的写权限
- 有部署系统的访问权限
- 有相关技术栈的知识储备

## Instructions

### 步骤 1：[ASSESS] 评估问题严重性和影响范围

**目标**：准确判定问题级别，评估影响范围，启动应急响应

**操作流程**：

1. **确认问题现象**
   - 阅读问题报告和用户反馈
   - 查看错误日志和异常堆栈
   - 检查监控指标异常
   - 尝试复现问题（如可能）

2. **判定问题级别**
   - **P0 (Critical)**: 核心服务不可用，影响大部分用户，需立即响应
     - 标准：影响>50%用户或核心功能完全不可用
     - 响应时限：15分钟内
     - 修复时限：2小时内
   
   - **P1 (Major)**: 重要功能受损，影响部分用户
     - 标准：影响10-50%用户或重要功能部分不可用
     - 响应时限：30分钟内
     - 修复时限：8小时内
   
   - **P2 (Minor)**: 一般问题，影响少量用户
     - 标准：影响<10%用户或非核心功能异常
     - 响应时限：1小时内
     - 修复时限：24小时内

3. **评估影响范围**
   - 识别受影响的服务和组件
   - 估算受影响的用户数量
   - 评估业务影响（收入损失、用户流失、品牌损害）
   - 确定优先级和紧急程度

4. **启动应急响应**
   - 根据问题级别启动相应流程
   - 通知相关人员（开发、运维、DBA、业务方）
   - 建立应急沟通渠道（微信群、Slack频道）
   - 指定应急指挥官

**检查点**：
- [ ] 问题级别判定准确
- [ ] 影响范围评估完整
- [ ] 应急响应流程已启动
- [ ] 相关人员已通知

**产出**：
- 问题评估报告
- 应急响应计划
- 沟通渠道建立

**质量标准**：
- 问题级别判定准确率≥95%
- 影响范围评估误差≤20%
- 响应时间符合级别要求

### 步骤 2：[LOCATE] 快速定位问题根因

**目标**：在30分钟内定位问题根本原因

**操作流程**：

1. **收集证据**
   - **日志分析**:
     - 查看应用日志（ERROR、WARN级别）
     - 查看系统日志（syslog、dmesg）
     - 查看访问日志（access log）
     - 提取关键错误信息和堆栈跟踪
   
   - **监控数据分析**:
     - 检查错误率趋势
     - 分析响应时间变化
     - 观察QPS波动
     - 检查资源使用情况（CPU、内存、磁盘、网络）
   
   - **最近变更排查**:
     - 列出最近24小时内的代码变更
     - 检查配置变更
     - 审查基础设施变更（部署、扩容、网络调整）
     - 识别可能的触发因素

2. **分析问题**
   - **时间关联分析**: 将问题发生时间与变更时间对比
   - **模式识别**: 识别问题的模式和规律
   - **影响链分析**: 追踪问题的传播路径
   - **假设验证**: 提出假设并通过证据验证

3. **使用5 Whys方法深入分析**
   ```
   问题现象 → Why? → 原因1 → Why? → 原因2 → Why? → 原因3 → Why? → 原因4 → Why? → 根本原因
   ```
   
   示例：
   - Why? 支付接口返回500错误
     → 因为PaymentService抛出NullPointerException
   - Why? 抛出NullPointerException
     → 因为user对象为null
   - Why? user对象为null
     → 因为getUserById()返回null
   - Why? getUserById()返回null
     → 因为数据库中用户记录被删除
   - Why? 用户记录被删除
     → **根本原因**: 数据清理脚本误删了活跃用户记录

4. **确认根因**
   - 验证根因是否能解释所有现象
   - 确认根因与证据一致
   - 排除其他可能性
   - 获得团队共识

**检查点**：
- [ ] 30分钟内定位根因
- [ ] 根因分析有充分证据支持
- [ ] 使用5 Whys方法深度分析
- [ ] 根因能解释所有现象

**产出**：
- 根因分析报告
- 证据清单
- 5 Whys分析过程

**质量标准**：
- 定位时间≤30分钟
- 根因准确率≥90%
- 分析过程有完整证据链

### 步骤 3：[DESIGN] 设计最小化修复方案

**目标**：设计最小化改动且有效的修复方案

**操作流程**：

1. **制定修复策略**
   - **直接修复**: 修改代码修复根本原因（首选）
   - **临时止血**: 通过配置、开关、限流等手段暂时缓解
   - **回滚版本**: 回滚到上一个稳定版本
   - **降级服务**: 关闭非核心功能，保障核心功能

2. **设计修复方案**
   - **代码修改**:
     - 识别需要修改的文件和函数
     - 设计具体的代码变更
     - 确保修改最小化（只改必要部分）
     - 考虑边界条件和异常情况
   
   - **风险评估**:
     - 评估修复的影响范围
     - 识别潜在风险点
     - 评估修复失败的可能性
     - 制定风险缓解措施
   
   - **回滚方案**:
     - 设计详细的回滚步骤
     - 准备回滚脚本或命令
     - 验证回滚方案的可行性
     - 预估回滚所需时间

3. **制定测试策略**
   - **单元测试**: 覆盖修复的代码路径
   - **集成测试**: 验证模块间交互
   - **回归测试**: 确保不引入新问题
   - **性能测试**: 验证修复不影响性能
   - **预发验证**: 在预发环境完整验证

4. **方案评审**
   - 组织快速代码审查（至少1人review）
   - 评估方案的可行性和风险
   - 确认测试计划的完整性
   - 获得必要的审批

**检查点**：
- [ ] 修复方案最小化（只修改必要部分）
- [ ] 风险评估完整
- [ ] 回滚方案可行
- [ ] 测试计划覆盖关键场景
- [ ] 方案经过评审

**产出**：
- 修复方案设计文档
- 风险评估报告
- 回滚方案
- 测试计划

**质量标准**：
- 修复方案简洁明了
- 风险评估覆盖所有关键点
- 回滚方案可执行
- 测试计划完整

### 步骤 4：[IMPLEMENT] 执行修复和测试

**目标**：高质量实施修复并通过全面测试

**操作流程**：

1. **编写修复代码**
   - 按照设计方案编写代码
   - 遵循编码规范和最佳实践
   - 添加必要的注释说明
   - 保持代码简洁清晰

2. **代码审查**
   - 提交代码进行review
   - 至少1人审查通过
   - 重点关注：
     - 修复是否正确
     - 是否有遗漏的边界条件
     - 是否引入新的风险
     - 代码质量和可读性

3. **编写测试**
   - **单元测试**:
     - 覆盖修复的代码路径
     - 测试正常情况和异常情况
     - 测试边界条件
     - 目标覆盖率≥90%
   
   - **集成测试**:
     - 验证模块间交互
     - 测试API调用和数据流
     - 验证依赖服务的兼容性
   
   - **回归测试**:
     - 执行受影响功能的回归测试
     - 重点测试核心业务流程
     - 验证无新问题引入

4. **预发环境验证**
   - 部署到预发环境
   - 执行完整的测试套件
   - 验证修复效果
   - 观察系统稳定性
   - 模拟真实流量测试

**检查点**：
- [ ] 代码审查通过
- [ ] 单元测试覆盖率≥90%
- [ ] 回归测试通过
- [ ] 预发环境验证成功
- [ ] 无新问题引入

**产出**：
- 修复代码
- 测试报告
- 预发环境验证结果

**质量标准**：
- 代码质量高，无明显的code smell
- 测试覆盖全面
- 预发验证通过
- 无回归问题

### 步骤 5：[DEPLOY] 部署上线和监控

**目标**：安全部署修复并验证生效

**操作流程**：

1. **准备部署**
   - 打包修复代码和配置
   - 准备部署脚本
   - 确认回滚方案就绪
   - 获得紧急发布审批（如需要）

2. **执行部署**
   - **灰度发布**（推荐）:
     - 先部署到少量实例（5-10%）
     - 观察监控指标
     - 验证修复效果
     - 逐步扩大范围（25% → 50% → 100%）
   
   - **全量发布**（紧急情况）:
     - 一次性部署到所有实例
     - 密切监控指标
     - 准备好快速回滚

3. **监控验证**
   - **实时监控**:
     - 错误率是否恢复正常
     - 响应时间是否正常
     - QPS是否稳定
     - 资源使用是否正常
   
   - **业务指标**:
     - 核心业务流程是否正常
     - 用户投诉是否减少
     - 业务数据是否恢复
   
   - **观察期**:
     - 至少观察30分钟
     - 确认无异常波动
     - 验证修复持久有效

4. **确认修复完成**
   - 所有监控指标正常
   - 用户反馈正面
   - 业务数据恢复
   - 宣布修复完成

**检查点**：
- [ ] 部署过程顺利
- [ ] 修复生效后系统稳定
- [ ] 监控指标正常
- [ ] 观察期≥30分钟无异常
- [ ] 用户反馈正面

**产出**：
- 部署记录
- 监控报告
- 修复验证结果

**质量标准**：
- 部署成功率100%
- 修复有效性100%
- 系统稳定性≥99.9%
- 用户满意度提升

### 步骤 6：[REPORT] 产出修复报告和后续计划

**目标**：完整记录修复过程，制定后续改进计划

**操作流程**：

1. **编写紧急修复报告**
   - **问题概要**: 问题描述、影响范围、持续时间
   - **根因分析**: 5 Whys分析过程和根本原因
   - **修复方案**: 采取的修复措施和技术细节
   - **测试验证**: 测试过程和结果
   - **部署上线**: 部署过程和监控验证
   - **时间线**: 从发现到修复完成的详细时间线

2. **记录关键决策**
   - 记录修复过程中的关键决策点
   - 说明决策的理由和依据
   - 记录备选方案和选择原因

3. **制定后续计划**
   - **短期行动**（1周内）:
     - 清理临时方案
     - 补充缺失的测试
     - 修复相关的技术问题
   
   - **长期改进**（1个月内）:
     - 架构优化
     - 流程改进
     - 工具建设
     - 能力提升
   
   - **技术债务**:
     - 识别修复过程中发现的技术债务

     - 排入开发计划

4. **安排事后复盘**
   - P0/P1故障必须在1周内进行复盘
   - 邀请相关人员参加
   - 准备复盘材料
   - 制定改进措施

5. **更新Global Context**
   - 更新故障状态为resolved
   - 记录修复信息
   - 更新系统健康状态
   - 记录残留风险和待办事项

**检查点**：

- [ ] 后续计划具体可执行
- [ ] 复盘会议已安排（P0/P1）

## Troubleshooting

### Issue 1: 根因不明
**Symptom**: 30分钟内无法定位问题根因，日志信息不足或模糊

**Cause**: 
- 日志记录不完整
- 问题无法稳定复现
- 多个疑似原因但无法确认
- 缺乏足够的监控数据

**Resolution**:
1. 扩大日志收集范围（增加调试日志、启用详细追踪）
2. 排查最近24小时内的所有变更
3. 尝试临时止血方案（功能开关、限流降级、回滚版本）
4. 升级到专家团队（架构师、资深开发、DBA）
5. 组织战时会议，集体排查

### Issue 2: 修复引发回归
**Symptom**: 修复后其他功能出现异常，回归测试发现新问题

**Cause**: 
- 修复影响了共享代码或依赖
- 未充分考虑边界条件
- 测试覆盖不全
- 隐藏的逻辑依赖

**Resolution**:
1. 立即评估回归问题的严重程度
2. IF 回归问题≥原问题 THEN 立即回滚全部修复
3. 分析回归原因（依赖关系、边界条件、副作用）
4. 制定修复回归的方案
5. 扩大测试范围，确保无其他回归

### Issue 3: 部署失败
**Symptom**: 部署过程中出现错误或部署后服务无法启动

**Cause**: 
- 配置错误或遗漏
- 依赖缺失或版本不兼容
- 数据库迁移失败
- 环境问题

**Resolution**:
1. 立即停止部署流程
2. 自动或手动回滚到上一版本
3. 验证回滚后系统恢复正常
4. 分析部署失败原因
5. 修复部署问题（修正配置、补充依赖）
6. 在预发环境重新验证部署流程
7. 重新执行部署

### Issue 4: 修复无效
**Symptom**: 修复后问题仍然存在，或短时间内再次出现

**Cause**: 
- 根因分析错误
- 修复方案不完整
- 只修复了症状而非根本原因
- 外部因素导致问题持续

**Resolution**:
1. 立即回滚修复
2. 重新分析问题根因
3. 收集更多证据（生产日志、用户反馈、监控数据）
4. 制定新的修复方案（考虑不同approach）
5. 在小范围环境验证新方案
6. 必要时寻求外部支持（社区、供应商、专家）

## Core Knowledge

### Domain Fundamentals

#### 1. 紧急修复原则
- **速度优先但不牺牲质量**: 快速响应的同时保证修复质量
- **最小化改动**: 只修复必要部分，避免大范围重构
- **可回滚性**: 所有修复必须可回滚
- **数据驱动**: 基于日志、监控数据和证据做决策
- **透明沟通**: 及时向相关方通报进展

#### 2. 问题定级标准
- **P0 (Critical)**: 核心服务不可用，影响>50%用户，需立即响应（15min内），2h内修复
- **P1 (Major)**: 重要功能受损，影响10-50%用户，30min内响应，8h内修复
- **P2 (Minor)**: 一般问题，影响<10%用户，1h内响应，24h内修复

#### 3. 5 Whys分析方法
通过连续问5次"为什么"，深入挖掘问题的根本原因，不止于表面现象。

#### 4. 修复策略选择
- **直接修复**: 修改代码修复根本原因（首选）
- **临时止血**: 通过配置、开关、限流等手段暂时缓解
- **回滚版本**: 回滚到上一个稳定版本
- **降级服务**: 关闭非核心功能，保障核心功能

### Key Principles

1. **快速响应原则**: P0问题15分钟内响应，P1问题30分钟内响应
2. **精准定位原则**: 30分钟内使用5 Whys方法定位问题根因
3. **最小化修复原则**: 只修改必要的代码，避免引入新问题
4. **安全部署原则**: 确保修复可回滚，部署过程可控
5. **完整记录原则**: 详细记录修复过程和决策依据
6. **持续改进原则**: 通过复盘识别系统性问题，预防复发

## Best Practices

### 快速定位最佳实践

1. **日志优先**: 首先查看错误日志和异常堆栈，通常能快速定位问题
2. **最近变更**: 重点排查最近24小时内的代码、配置、基础设施变更
3. **监控数据**: 分析监控指标的异常波动，识别问题发生时间点
4. **二分法排查**: 通过逐步缩小范围，快速定位问题模块
5. **复现问题**: 尽可能在测试环境复现问题，便于调试

### 修复设计最佳实践

1. **最小化改动**: 只修改必要的代码，避免大范围重构
2. **单一职责**: 修复只解决当前问题，不要顺便优化其他代码
3. **向后兼容**: 确保修复不破坏现有功能和API契约
4. **可回滚性**: 所有修复必须可回滚，回滚方案提前准备
5. **防御性编程**: 增加边界检查和异常处理，提高健壮性

### 测试验证最佳实践

1. **针对性测试**: 重点测试受影响的代码路径和功能
2. **回归测试**: 确保修复不引入新问题
3. **边界条件**: 测试极端情况和边界条件
4. **预发验证**: 在预发环境充分验证后再上线
5. **自动化测试**: 优先使用自动化测试提高效率

### 部署上线最佳实践

1. **灰度发布**: 优先使用灰度发布，降低风险
2. **健康检查**: 部署后立即进行健康检查
3. **监控观察**: 观察至少30分钟，确认系统稳定
4. **快速回滚**: 发现问题立即回滚，不要犹豫
5. **分批部署**: 大规模系统分批部署，控制影响范围

### 沟通协作最佳实践

1. **及时通报**: 每30分钟向相关方通报进展
2. **透明公开**: 所有决策和操作公开透明
3. **明确分工**: 战时明确分工，避免重复工作
4. **集中指挥**: 指定统一指挥官，协调各方资源
5. **记录完整**: 详细记录所有操作和决策

## Common Pitfalls

### Pitfall 1: 过度修复
**Risk**: 修复时顺便重构或优化其他代码，引入新问题

**Prevention**: 
- 严格遵守"最小化修复"原则
- 只修改与问题直接相关的代码
- 其他优化和改进留到正式修复时进行
- 代码审查时重点关注是否有不必要的改动

**Impact**: 如果未避免，可能引入新的bug，延长修复时间，甚至导致更严重的故障

### Pitfall 2: 测试不充分
**Risk**: 为了赶时间省略测试，导致修复引入回归问题

**Prevention**: 
- 即使时间紧迫也必须执行关键测试
- 优先测试受影响的核心功能
- 使用自动化测试提高效率
- 预发环境验证不可省略

**Impact**: 如果未避免，可能引入新问题，需要再次修复，反而浪费更多时间

### Pitfall 3: 忽视回滚方案
**Risk**: 没有准备回滚方案，修复失败时无法快速恢复

**Prevention**: 
- 修复前必须准备回滚方案
- 回滚方案必须经过验证
- 确保回滚操作简单快速
- 部署前确认回滚步骤

**Impact**: 如果未避免，修复失败时无法快速恢复，延长故障时间，加剧业务损失

### Pitfall 4: 根因分析不深入
**Risk**: 只修复表面症状，未解决根本原因，问题会再次发生

**Prevention**: 
- 使用5 Whys方法深入分析根因
- 不只关注"是什么"，更要关注"为什么"
- 区分直接原因和根本原因
- 事后复盘时验证根因分析的准确性

**Impact**: 如果未避免，同类问题可能反复发生，治标不治本

### Pitfall 5: 沟通不及时
**Risk**: 未及时通报进展，导致相关方焦虑或做出错误决策

**Prevention**: 
- 建立固定的沟通节奏（每30分钟更新一次）
- 使用统一的沟通渠道（如应急群）
- 通报内容包含：当前状态、下一步计划、预计完成时间
- 重大决策前征求相关方意见

**Impact**: 如果未避免，可能导致信息不对称，影响决策效率，甚至引发信任危机

### Pitfall 6: 忽视事后复盘
**Risk**: 修复完成后不进行复盘，错失改进机会

**Prevention**: 
- P0/P1故障必须在1周内进行复盘
- 复盘要深入，不止于表面现象
- 制定具体的改进措施和时间表
- 跟踪改进措施落实情况

**Impact**: 如果未避免，同类问题可能反复发生，团队无法从故障中学习成长
