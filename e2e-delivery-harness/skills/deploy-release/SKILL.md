# Deploy Release Skill

## Skill Overview

本技能包提供部署发布的专业知识、最佳实践和常见陷阱，指导AI高质量地完成从部署规划到执行、验证和交接的全流程工作。

### Core Competencies

- **部署策略设计**: 根据业务需求和技术架构选择合适的部署策略（蓝绿/滚动/灰度）
- **自动化部署**: 编写和维护自动化部署脚本，提高部署效率和可靠性
- **回滚管理**: 设计和测试回滚方案，确保在异常情况下能快速恢复
- **监控告警配置**: 设置完善的监控指标和告警规则，及时发现和处理问题
- **质量验证**: 执行功能、性能、集成、数据等多维度验证，确保部署质量

## Use When

使用此技能的场景：

- ✅ 测试验证通过后，需要将软件部署到生产环境
- ✅ 需要规划和执行部署流程，确保服务连续性
- ✅ 需要准备回滚方案，应对可能的异常情况
- ✅ 需要配置监控告警，持续监控系统状态
- ✅ 需要进行环境迁移或升级（数据库迁移、中间件升级）

## Instructions

### Step 1: 发布确认和计划制定

**目标**: 确认发布范围、获得授权、制定详细计划

**操作**:
1. 检查前置条件：
   - 测试报告已通过，无P0/P1级别缺陷
   - 发布已获得产品经理和技术负责人批准
   - 回滚方案已准备并测试验证
2. 确认发布范围：
   - 版本号（语义化版本格式）
   - 变更清单（新功能、Bug修复、性能优化）
   - 目标环境（prod/staging/dev）
   - 发布时间窗口（低峰期/维护窗口）
3. 选择部署策略：
   - **蓝绿部署**: 零停机，适合关键业务，需要双倍资源
   - **滚动部署**: 逐步替换实例，资源利用率高，有短暂降级
   - **灰度发布**: 小流量验证，风险最低，适合大规模系统
   - **直接部署**: 快速但风险高，仅用于非关键环境
4. 制定详细计划：
   - 部署步骤分解（每步预计时间、责任人）
   - 验证点设置（健康检查、功能测试、性能测试）
   - 回滚触发条件（错误率>阈值、响应时间>阈值）
   - 沟通计划（通知对象、通知渠道、通知时机）

**检查点**:
- [ ] 发布已获得正式批准
- [ ] 回滚方案已测试验证
- [ ] 部署策略符合业务需求
- [ ] 计划详细且可行

**输出**: 发布确认清单和部署计划文档

---

### Step 2: 环境检查和资源准备

**目标**: 确保目标环境就绪，资源配置充足

**操作**:
1. 环境检查：
   - 服务器状态（CPU、内存、磁盘空间）
   - 网络连通性（内网、外网、DNS解析）
   - 依赖服务健康状态（数据库、缓存、消息队列、第三方API）
   - 防火墙和安全组规则（端口开放、IP白名单）
2. 资源评估：
   - 计算资源是否充足（CPU核心数、内存容量）
   - 存储资源是否充足（磁盘空间、IOPS）
   - 网络带宽是否充足（入口带宽、出口带宽）
   - 是否需要临时扩容（部署期间增加实例数）
3. 配置准备：
   - 环境变量配置（数据库连接、API密钥、功能开关）
   - 配置文件更新（application.yml、nginx.conf等）
   - 敏感信息处理（使用Vault或Secrets Manager）
   - 配置差异对比（与上一版本的配置变更）
4. 备份准备：
   - 数据库备份（全量备份或增量备份）
   - 配置文件备份（当前版本的配置快照）
   - 应用备份（上一版本的制品保留）
   - 验证备份可用性（测试恢复流程）

**检查点**:
- [ ] 环境检查全部通过
- [ ] 资源配置充足或有扩容计划
- [ ] 配置已更新并验证
- [ ] 备份已完成且可用

**输出**: 环境准备报告和备份记录

---

### Step 3: 部署执行和实时监控

**目标**: 按计划执行部署，实时监控状态，及时处理异常

**操作**:
1. 执行前最后检查：
   - 确认人员就位（开发、运维、DBA）
   - 确认通知已发送（产品、运营、客服、管理层）
   - 确认回滚方案就绪（回滚脚本、回滚数据）
   - 确认监控告警已启用
2. 按步骤执行部署：
   - 上传部署包到目标服务器或容器仓库
   - 执行部署脚本（停止旧版本、启动新版本）
   - 等待服务启动和健康检查通过
   - 执行冒烟测试验证核心功能
3. 实时监控状态：
   - 监控服务状态（实例数、重启次数、健康状态）
   - 监控资源使用（CPU、内存、磁盘IO、网络流量）
   - 监控应用指标（响应时间、吞吐量、错误率）
   - 监控日志输出（错误日志、异常堆栈）
4. 异常处理：
   - 如检测到异常，立即分析原因
   - IF 可快速修复（<5分钟）THEN 尝试修复并重试
   - ELSE 立即执行回滚
   - 记录详细的异常信息和处理过程

**检查点**:
- [ ] 每步部署执行成功
- [ ] 健康检查全部通过
- [ ] 无异常告警或已及时处理
- [ ] 部署日志完整记录

**输出**: 部署执行日志和实时监控快照

---

### Step 4: 部署后验证

**目标**: 全面验证部署结果，确保功能和性能符合预期

**操作**:
1. 功能验证：
   - 执行冒烟测试（核心功能快速验证）
   - 执行回归测试（确保未引入回归问题）
   - 验证用户界面和交互（UI测试、端到端测试）
   - 验证API接口（接口契约测试、集成测试）
2. 性能验证：
   - 对比部署前后的性能基线（响应时间、吞吐量、错误率）
   - 执行压力测试（高并发场景下的表现）
   - 检查资源使用是否正常（CPU、内存、磁盘IO）
   - 识别性能瓶颈（应用层、数据库、网络、缓存）
3. 集成验证：
   - 验证与依赖服务的集成（数据库、缓存、消息队列）
   - 验证与第三方服务的集成（支付网关、短信服务、邮件服务）
   - 验证数据流是否正确（数据采集、处理、存储）
4. 数据验证：
   - 验证数据完整性（无数据丢失或损坏）
   - 验证数据一致性（主从同步、缓存一致性）
   - 验证数据库迁移是否成功（表结构变更、数据迁移）
   - 验证关键业务数据（订单、用户、库存等）

**检查点**:
- [ ] 功能验证全部通过
- [ ] 性能指标在基线范围内（±10%）
- [ ] 集成验证通过
- [ ] 数据验证通过

**输出**: 部署验证报告

---

### Step 5: 监控配置和告警设置

**目标**: 配置完善的监控和告警，确保持续监控系统状态

**操作**:
1. 监控指标配置：
   - 基础设施监控（CPU、内存、磁盘、网络）
   - 应用性能监控（响应时间、吞吐量、错误率）
   - 业务指标监控（订单量、用户活跃度、转化率）
   - 自定义指标（业务特定的关键指标）
2. 告警规则设置：
   - 错误率告警（错误率>0.1%持续5分钟）
   - 响应时间告警（P95响应时间>SLA阈值）
   - 资源使用告警（CPU>80%、内存>90%）
   - 服务可用性告警（健康检查失败）
3. 告警通知配置：
   - 通知渠道（Slack、邮件、短信、电话）
   - 通知对象（on-call工程师、技术负责人、值班经理）
   - 告警分级（P0立即电话、P1 Slack+邮件、P2邮件）
   - 告警抑制（避免告警风暴，设置静默期）
4. 监控面板创建：
   - 创建部署专用监控面板（Grafana、Datadog）
   - 展示关键指标趋势（响应时间、错误率、资源使用）
   - 设置自动刷新（每30秒或1分钟）
   - 分享监控面板链接给相关干系人

**检查点**:
- [ ] 监控指标配置完整
- [ ] 告警规则合理且已测试
- [ ] 通知渠道正常工作
- [ ] 监控面板已创建并分享

**输出**: 监控配置文件和监控面板链接

---

### Step 6: Handover Context生成和交接

**目标**: 生成完整的Handover Context，便于运维监控阶段顺利接手

**操作**:
1. 收集所有交付物：
   - 部署执行日志
   - 部署验证报告
   - 监控配置文件
   - 发布总结报告
   - 回滚方案文档
2. 填写Handover Context模板：
   - 部署统计（部署时长、停机时间、验证通过率）
   - 交付物清单（含版本号和校验和）
   - 决策记录（部署策略选择、回滚触发判断等）
   - 遗留问题和风险
   - 监控重点和告警配置
   - 建议事项（优化建议、后续工作）
   - 质量指标（KPIs结果、综合评分）
   - 下一步行动（监控计划、回顾安排）
3. 更新Global Context：
   - 发布状态（success/partial/failed_rolled_back）
   - 监控重点（需要特别关注的指标和问题）
   - 应急联系人（技术负责人、DBA、运维值班）
4. 通知Monitor Operate Agent：
   - 发送Handover Context
   - 确认接收并开始持续监控
   - 约定监控周期（至少24小时）

**检查点**:
- [ ] Handover Context所有字段完整
- [ ] 交付物清单准确，版本号正确
- [ ] 遗留问题和风险已明确标注
- [ ] Monitor Operate Agent已收到通知并确认

**输出**: Handover Context（YAML格式）

## Core Knowledge

### Deployment Strategies (部署策略)

#### 1. Blue-Green Deployment (蓝绿部署)
- **原理**: 维护两套相同的生产环境（蓝和绿），一套运行当前版本，另一套部署新版本
- **优点**: 零停机、快速回滚（切换流量即可）、降低风险
- **缺点**: 需要双倍资源、成本高、数据库迁移复杂
- **适用场景**: 关键业务系统、对停机零容忍的场景

#### 2. Rolling Deployment (滚动部署)
- **原理**: 逐步替换旧版本实例，每次替换一部分，直到全部替换完成
- **优点**: 资源利用率高、无需额外基础设施、实现简单
- **缺点**: 部署期间存在版本混合、可能有短暂降级
- **适用场景**: 资源受限、可接受短暂降级的场景

#### 3. Canary Deployment (灰度发布)
- **原理**: 先将新版本部署到少量实例，小流量验证，逐步扩大比例
- **优点**: 风险最低、真实用户验证、可快速发现问题
- **缺点**: 部署时间长、需要复杂的流量控制、监控要求高
- **适用场景**: 大规模系统、对稳定性要求极高的场景

#### 4. Direct Deployment (直接部署)
- **原理**: 直接停止旧版本，启动新版本
- **优点**: 简单快速、无需复杂工具
- **缺点**: 有停机时间、回滚慢、风险高
- **适用场景**: 非关键环境、开发/测试环境、可接受停机的场景

### Rollback Strategies (回滚策略)

#### 1. Version Rollback (版本回滚)
- **方法**: 重新部署上一稳定版本的制品
- **适用**: 应用代码问题导致的故障
- **时间**: 通常5-15分钟（取决于部署策略）

#### 2. Database Rollback (数据库回滚)
- **方法**: 从备份恢复数据库或执行反向迁移脚本
- **适用**: 数据库迁移导致的数据问题
- **时间**: 可能较长（取决于数据量和备份方式）
- **注意**: 需谨慎评估，可能导致数据丢失

#### 3. Configuration Rollback (配置回滚)
- **方法**: 恢复到上一版本的配置文件
- **适用**: 配置错误导致的故障
- **时间**: 通常很快（几分钟）

#### 4. Traffic Rollback (流量回滚)
- **方法**: 将流量切回旧版本（蓝绿部署或灰度发布）
- **适用**: 蓝绿部署或灰度发布场景
- **时间**: 几乎即时（秒级）

### Health Check Types (健康检查类型)

#### 1. Liveness Probe (存活检查)
- **目的**: 检查应用是否正在运行
- **失败处理**: 重启容器或实例
- **示例**: HTTP GET /health/live，返回200表示存活

#### 2. Readiness Probe (就绪检查)
- **目的**: 检查应用是否准备好接收流量
- **失败处理**: 从负载均衡器移除，不接收新请求
- **示例**: HTTP GET /health/ready，检查依赖服务连接

#### 3. Startup Probe (启动检查)
- **目的**: 检查应用是否已完成启动
- **失败处理**: 给予更多启动时间，避免过早重启
- **示例**: 检查初始化任务是否完成

### Monitoring Metrics (监控指标)

#### Infrastructure Metrics (基础设施指标)
- CPU使用率（%）
- 内存使用率（%）
- 磁盘使用率（%）
- 网络流量（入站/出站，Mbps）
- 磁盘IOPS（读写操作数/秒）

#### Application Metrics (应用指标)
- 响应时间（平均、P50、P95、P99，ms）
- 吞吐量（请求数/秒）
- 错误率（错误请求数/总请求数，%）
- 活跃连接数
- JVM GC次数和时间（Java应用）

#### Business Metrics (业务指标)
- 订单量（订单数/分钟）
- 用户活跃度（在线用户数、DAU、MAU）
- 转化率（注册转化率、购买转化率）
- 收入（GMV、ARPU）

## Best Practices

### 1. Automate Everything (全面自动化)
- **原则**: 将部署流程完全自动化，减少人工干预
- **理由**: 自动化提高可靠性、可重复性，减少人为错误
- **实践**: 
  - 使用CI/CD流水线（Jenkins、GitLab CI、GitHub Actions）
  - 编写自动化部署脚本（Ansible、Terraform、Kubernetes manifests）
  - 自动化测试验证（冒烟测试、回归测试）
  - 自动化回滚（基于监控指标自动触发）

### 2. Test Rollback Regularly (定期测试回滚)
- **原则**: 定期演练回滚流程，确保回滚方案可靠
- **理由**: 未经测试的回滚方案可能在紧急情况下失效
- **实践**:
  - 每月进行一次回滚演练
  - 在非生产环境测试回滚流程
  - 记录回滚时间和遇到的问题
  - 更新回滚文档 based on lessons learned

### 3. Monitor Before, During, and After (全程监控)
- **原则**: 在部署前、中、后三个阶段都进行监控
- **理由**: 及时发现问题，快速响应，降低影响
- **实践**:
  - 部署前：建立性能基线，记录正常状态
  - 部署中：实时监控部署进度和系统状态
  - 部署后：持续监控至少24小时，关注异常趋势

### 4. Communicate Proactively (主动沟通)
- **原则**: 及时向干系人通报部署进度和状态
- **理由**: 建立信任，管理期望，协调资源
- **实践**:
  - 部署前发送通知（时间、影响范围、联系人）
  - 部署中实时更新状态（Slack频道、状态页面）
  - 部署后发送总结报告（成功/失败、问题、后续计划）

### 5. Document Everything (完整文档)
- **原则**: 详细记录部署过程、决策、问题和解决方案
- **理由**: 便于追溯、学习和改进
- **实践**:
  - 编写部署计划文档
  - 记录部署执行日志
  - 编写事故报告（如发生故障）
  - 定期更新部署最佳实践文档

### 6. Learn from Failures (从失败中学习)
- **原则**: 每次部署失败都要进行复盘，找出根本原因
- **理由**: 避免重复犯错，持续改进部署流程
- **实践**:
  - 召开事后回顾会议（Post-Mortem）
  - 使用5 Whys方法找出根本原因
  - 制定改进行动计划
  - 跟踪行动计划执行情况

## Common Pitfalls

### Pitfall 1: Insufficient Rollback Testing (回滚测试不足)
**Risk**: 紧急情况下回滚失败，导致服务长时间中断  
**Prevention**: 
- 定期演练回滚流程（至少每月一次）
- 在 staging 环境测试回滚
- 记录回滚时间和遇到的问题  
**Impact**: 服务中断时间延长，用户投诉，业务损失

---

### Pitfall 2: Inadequate Monitoring (监控不足)
**Risk**: 无法及时发现部署后的问题，导致故障扩大  
**Prevention**: 
- 配置完善的监控指标和告警规则
- 部署前建立性能基线
- 部署后持续监控至少24小时  
**Impact**: 问题发现延迟，影响范围扩大，修复成本增加

---

### Pitfall 3: Poor Communication (沟通不畅)
**Risk**: 干系人不知道部署状态，产生误解和恐慌  
**Prevention**: 
- 部署前发送通知（时间、影响、联系人）
- 部署中实时更新状态
- 部署后发送总结报告  
**Impact**: 信任度下降，团队协作效率降低，用户满意度受损

---

### Pitfall 4: Skipping Verification Steps (跳过验证步骤)
**Risk**: 带病上线，生产环境出现故障  
**Prevention**: 
- 严格执行验证清单
- 自动化验证流程，减少人工疏漏
- 验证不通过时坚决回滚  
**Impact**: 生产环境故障，用户受影响，紧急修复压力大
