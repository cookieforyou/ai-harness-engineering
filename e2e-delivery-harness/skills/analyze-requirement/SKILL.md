# Requirement Analysis Skill

## Skill Overview

本技能包提供需求分析的专业知识、最佳实践和常见陷阱，指导AI高质量地完成从原始需求到结构化规格说明书的转换。

### Core Competencies

- **需求 Elicitation**: 通过访谈、工作坊、文档分析等方式收集和澄清需求
- **干系人管理**: 全面识别和分析各类干系人的诉求、期望和影响力
- **业务建模**: 构建业务流程图、用例模型，可视化业务逻辑和数据流
- **需求规范化**: 使用用户故事格式和SMART原则编写清晰、可测试的需求
- **冲突解决**: 协调不同干系人的矛盾诉求，寻求共赢方案
- **非功能需求定义**: 识别和定义性能、安全、可用性等质量属性需求

## Use When

使用此技能的场景：

- 新项目启动，需要进行需求调研和分析
- 业务方提出新需求，需要结构化澄清
- 现有需求文档不完整，需要梳理重构
- 需求变更频繁，需要重新评估影响

## Instructions

### 步骤 1：业务目标理解

**目标**：识别需求背后的业务触发点和期望达成的目标

**操作方法**:
1. **背景分析**: 理解业务现状、痛点和机会
2. **目标提取**: 从原始需求中提取3-5条核心业务目标
3. **SMART检查**: 确保每个目标都是具体、可衡量、可达成、相关、有时限的
4. **价值关联**: 将目标与业务价值（收入增长、成本降低、效率提升等）关联

**检查点**:
- [ ] 业务目标清晰定义，无模糊表述
- [ ] 每个目标都有可衡量的KPI或指标
- [ ] 目标与业务价值明确关联
- [ ] 目标之间无矛盾或重复

---

### 步骤 2：干系人分析

**目标**：识别所有相关干系人，理解其诉求和期望

**操作方法**:
1. **角色识别**: 列出所有利益相关方，分类为决策者、使用者、影响者、监管者
2. **影响力评估**: 评估每个干系人的影响力（高/中/低）和优先级
3. **诉求收集**: 通过访谈、问卷等方式收集各干系人的核心诉求
4. **冲突识别**: 识别不同干系人之间的潜在冲突点
5. **沟通计划**: 制定与各干系人的沟通频率和方式

**检查点**:
- [ ] 关键干系人已全部识别（至少覆盖决策者、使用者、影响者）
- [ ] 每个干系人的核心诉求已记录
- [ ] 冲突点已标注并制定解决策略
- [ ] 沟通计划已明确

---

### 步骤 3：业务流程建模

**目标**：构建业务流程和用例模型，可视化业务逻辑

**操作方法**:
1. **流程识别**: 识别主要业务流程，确定起点和终点
2. **参与者映射**: 标注流程中的角色和系统
3. **流程描述**: 使用流程图描述业务流转，标注关键决策点
4. **异常处理**: 定义异常场景和处理策略
5. **用例编写**: 为每个主要功能编写用例（前置条件、主流程、备选流程、后置条件）

**检查点**:
- [ ] 主要业务流程已完整描述
- [ ] 关键决策点和分支已标注
- [ ] 异常处理流程已定义
- [ ] 用例覆盖主要场景和边界情况

---

### 步骤 4：功能需求定义

**目标**：将需求转换为结构化的功能需求规格

**操作方法**:
1. **用户故事格式**: 使用 "As a [角色], I want [功能], so that [价值]" 格式描述每条需求
2. **验收标准**: 为每个需求定义Given-When-Then格式的验收标准
3. **优先级标注**: 根据业务价值和紧急程度标注P0/P1/P2/P3优先级
4. **依赖识别**: 识别需求间的依赖关系（技术依赖、业务依赖）
5. **追溯建立**: 建立需求与业务目标的追溯关系

**检查点**:
- [ ] 所有需求都使用标准用户故事格式
- [ ] 每个需求都有明确的验收标准
- [ ] 优先级标注合理，与业务价值一致
- [ ] 依赖关系已识别并记录
- [ ] 每条需求都可追溯到业务目标

---

### 步骤 5：非功能需求定义

**目标**：定义系统的非功能性需求

**操作方法**:
1. **性能需求**: 定义响应时间、吞吐量、并发用户数等指标
2. **安全需求**: 定义认证、授权、数据加密、审计等要求
3. **可用性需求**: 定义可用率、RTO（恢复时间目标）、RPO（恢复点目标）
4. **可维护性需求**: 定义监控、日志、配置管理等要求
5. **兼容性需求**: 定义浏览器、设备、操作系统等兼容性要求
6. **合规性需求**: 确认行业标准和法规要求（如GDPR、PCI DSS等）

**检查点**:
- [ ] 性能指标具体且可衡量
- [ ] 安全需求覆盖认证、授权、数据保护
- [ ] 可用性目标明确，有恢复策略
- [ ] 合规性要求已识别并满足

---

### 步骤 6：约束与假设整理

**目标**：整理已知约束条件和假设

**操作方法**:
1. **技术约束**: 记录技术栈、集成要求、兼容性限制
2. **时间约束**: 记录交付节点、里程碑、关键日期
3. **资源约束**: 记录预算上限、人力配置、基础设施限制
4. **法规约束**: 记录法律法规、行业标准、合规要求
5. **假设列表**: 列出当前做出的所有假设，评估假设不成立的风险
6. **未解决问题**: 记录需要进一步澄清的问题

**检查点**:
- [ ] 所有已知约束已记录
- [ ] 假设已明确标注并评估风险
- [ ] 未解决问题已列出并指定负责人

---

### 步骤 7：需求评审确认

**目标**：与干系人评审需求，确保理解一致

**操作方法**:
1. **评审准备**: 提前发送评审材料，准备评审议程
2. **评审执行**: 逐项讲解需求，收集反馈意见
3. **冲突解决**: 现场解决发现的冲突和问题
4. **修订完善**: 根据评审意见修订需求文档
5. **签字确认**: 获得关键干系人的签字确认
6. **基线锁定**: 锁定需求基线，后续变更走变更流程

**检查点**:
- [ ] 评审会议已完成
- [ ] 所有反馈已处理或记录
- [ ] 关键干系人已签字确认
- [ ] 需求基线已锁定

## Core Knowledge

### Domain Fundamentals

**需求工程基础**:
- **需求类型**: 功能需求（做什么）vs 非功能需求（做得多好）
- **需求层次**: 业务需求 → 用户需求 → 系统需求
- **需求属性**: 完整性、一致性、可追溯性、可测试性
- **SMART原则**: Specific, Measurable, Achievable, Relevant, Time-bound

**干系人管理**:
- **干系人分类**: 决策者（Decision Maker）、使用者（User）、影响者（Influencer）、监管者（Regulator）
- **影响力评估**: Power-Interest Grid（权力-利益矩阵）
- **沟通策略**: 根据干系人类型制定不同的沟通频率和方式

**业务建模技术**:
- **流程图**: 描述业务流程的输入、处理、输出、决策点
- **用例图**: 展示系统与外部参与者的交互
- **数据流图**: 描述数据在系统中的流动和处理
- **状态图**: 描述对象在不同条件下的状态变化

**需求编写标准**:
- **用户故事格式**: "As a [角色], I want [功能], so that [价值]"
- **验收标准格式**: Given-When-Then (GWT) 或 Should-Shall-Must
- **优先级分级**: P0(核心)、P1(重要)、P2(次要)、P3(可选)

### Key Principles

1. **业务目标驱动**: 每条需求都必须能够追溯到明确的业务目标
2. **干系人参与**: 确保所有关键干系人的诉求都被捕获和考虑
3. **明确无歧义**: 使用清晰、具体的语言，避免模糊词汇
4. **可测试可验证**: 每个需求都有明确的验收标准和验证方法
5. **渐进明细**: 从高层次需求逐步细化到具体实现细节
6. **变更可控**: 建立需求变更流程，控制范围蔓延

## Best Practices

### 1. 主动澄清，避免假设

**实践描述**: 遇到模糊需求时，主动向业务方提出澄清问题，而不是基于假设继续工作。

**理由**: 假设往往是错误的根源，会导致后期返工和成本增加。

**操作方法**:
- 列出所有可能的理解方式
- 为每种理解生成示例场景
- 向业务方提出具体的澄清问题
- 记录最终决策和依据

---

### 2. 使用标准化格式

**实践描述**: 始终使用用户故事格式描述功能需求，使用Given-When-Then格式定义验收标准。

**理由**: 标准化格式提高需求的可读性、一致性和可测试性。

**示例**:
```
As a 注册用户
I want 能够通过微信快捷登录
So that 我可以快速访问系统而无需记住密码

Acceptance Criteria:
Given 我已经在系统中绑定微信账号
When 我点击“微信登录”按钮
And 我在微信中确认授权
Then 我应该成功登录系统
And 我应该被重定向到首页
```

---

### 3. 全面识别干系人

**实践描述**: 不仅关注直接使用者，还要识别决策者、影响者、监管者等所有相关方。

**理由**: 遗漏关键干系人会导致需求不完整或后期冲突。

**检查清单**:
- 谁是最终买单的人？（决策者）
- 谁会日常使用这个系统？（使用者）
- 谁的工作会受到系统影响？（影响者）
- 是否有法规或合规要求？（监管者）

---

### 4. 平衡功能与非功能需求

**实践描述**: 在定义功能需求的同时，充分关注性能、安全、可用性等非功能需求。

**理由**: 非功能需求往往决定系统的整体质量和用户体验。

**操作方法**:
- 参考行业标准和类似项目经验值
- 与架构师和技术负责人协商确定合理指标
- 考虑未来扩展性和维护成本

---

### 5. 建立清晰的追溯关系

**实践描述**: 为每条需求标注其对应的业务目标，建立双向追溯矩阵。

**理由**: 追溯关系帮助验证需求的必要性，便于后续调整和优化。

**追溯矩阵示例**:
| Business Objective | Related Requirements | Priority |
|--------------------|----------------------|----------|
| OBJ-001: 提升用户转化率 | FR-001, FR-003, FR-007 | P0 |
| OBJ-002: 降低运营成本 | FR-002, FR-005 | P1 |

---

### 6. 迭代式需求细化

**实践描述**: 先完成高层次的需求框架，再逐步细化具体细节，避免一次性过度设计。

**理由**: 迭代式细化降低认知负荷，便于及时调整方向。

**操作流程**:
1. 第一轮：识别主要功能模块和业务目标
2. 第二轮：细化每个模块的核心需求
3. 第三轮：补充边界情况和异常处理
4. 第四轮：完善验收标准和非功能需求

## Common Pitfalls

### Pitfall 1: 需求粒度过粗或过细

**风险**: 粒度过粗导致无法准确估算和实现；粒度过细限制创新空间，增加维护成本。

**预防方法**:
- 遵循INVEST原则（Independent, Negotiable, Valuable, Estimable, Small, Testable）
- 单个需求应在1-3天内可实现
- 避免将多个独立功能合并为一个需求
- 避免将一个功能拆分为过多微任务

**影响**: 粒度不当会导致估算不准确、进度延误、团队困惑

---

### Pitfall 2: 忽视非功能需求

**风险**: 只关注功能实现，忽略性能、安全、可用性等质量属性，导致系统上线后问题频发。

**预防方法**:
- 在需求分析初期就识别非功能需求
- 参考行业标准和最佳实践设定合理指标
- 与架构师和技术负责人共同评审非功能需求
- 将非功能需求纳入验收标准

**影响**: 可能导致系统性能瓶颈、安全漏洞、用户体验差、运维成本高

---

### Pitfall 3: 干系人覆盖不全

**风险**: 遗漏关键干系人，导致需求不完整或后期出现重大变更。

**预防方法**:
- 使用干系人识别检查清单（决策者、使用者、影响者、监管者）
- 访谈现有系统的用户和管理员
- 咨询业务专家和行业顾问
- 定期审查干系人列表，确保无遗漏

**影响**: 可能导致需求返工、项目延期、干系人不满

---

### Pitfall 4: 验收标准不可测试

**风险**: 验收标准模糊或主观，导致无法验证需求是否完成，引发争议。

**预防方法**:
- 使用Given-When-Then格式编写验收标准
- 避免使用“快速”、“友好”、“高效”等主观词汇
- 使用可量化的指标（如“响应时间 < 2秒”）
- 与测试团队一起评审验收标准的可测试性

**影响**: 可能导致交付物不符合期望、验收困难、返工成本高
