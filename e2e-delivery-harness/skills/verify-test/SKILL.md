# Test Verification Skill

## Skill Overview

本技能包提供测试验证的专业知识、最佳实践和常见陷阱，指导AI高质量地完成从测试设计到执行、缺陷管理和质量评估的全流程工作。

### Core Competencies

- **测试策略设计**: 根据需求特点和风险评估制定最优测试策略（黑盒/白盒/灰盒）
- **测试用例设计**: 运用等价类划分、边界值分析、决策表等方法设计高质量测试用例
- **缺陷管理**: 准确识别、分类和报告缺陷，确保描述清晰可复现
- **质量评估**: 基于KPIs计算质量评分，提供数据驱动的发布建议
- **自动化测试**: 编写和维护自动化测试脚本，提高测试效率和覆盖率

## Use When

使用此技能的场景：

- ✅ 功能开发完成后，需要进行全面的功能测试和回归测试
- ✅ 需要设计测试用例和测试方案，确保覆盖所有验收标准
- ✅ 需要执行系统化的测试流程，发现并跟踪缺陷
- ✅ 需要提供客观的质量评估和发布建议
- ✅ 需要进行性能测试和安全测试

## Instructions

### Step 1: 测试范围分析和目标定义

**目标**: 明确测试边界、重点和验收标准

**操作**:
1. 阅读需求规格说明书，提取所有验收标准
2. 与产品经理确认测试范围和优先级
3. 识别核心功能、边界场景、异常处理点
4. 确定非功能需求（性能、安全、可用性）的测试要求
5. 评估测试风险和约束条件

**检查点**:
- [ ] 所有验收标准已提取并编号
- [ ] 测试范围已与干系人确认
- [ ] 核心功能和高风险区域已识别
- [ ] 非功能需求测试要求已明确

**输出**: 测试范围定义文档

---

### Step 2: 测试策略和方法选择

**目标**: 制定最优测试策略，平衡覆盖率和效率

**操作**:
1. 根据需求特点选择测试方法：
   - **黑盒测试**: 关注功能行为，不考虑内部实现（适用于功能测试）
   - **白盒测试**: 基于代码结构设计用例（适用于单元测试、集成测试）
   - **灰盒测试**: 结合黑盒和白盒（适用于API测试、数据库测试）
2. 确定测试类型组合：
   - 功能测试（必选）
   - 边界测试（必选）
   - 异常测试（必选）
   - 性能测试（如需要）
   - 安全测试（如需要）
   - 兼容性测试（如需要）
3. 决定手动测试和自动化测试的比例
4. 规划测试资源和时间安排

**检查点**:
- [ ] 测试方法选择合理，符合需求特点
- [ ] 测试类型覆盖全面，无遗漏
- [ ] 手动/自动化比例符合成本效益原则
- [ ] 资源安排和时间计划可行

**输出**: 测试策略文档

---

### Step 3: 测试用例设计

**目标**: 设计覆盖完整的高质量测试用例

**操作**:
1. 运用测试设计技术：
   - **等价类划分**: 将输入域划分为有效和无效等价类
   - **边界值分析**: 测试边界值和略超边界的值
   - **决策表测试**: 处理多条件组合的逻辑
   - **状态转换测试**: 测试状态之间的转换路径
   - **用例场景法**: 基于用户操作流程设计用例
2. 为每个验收标准设计至少3个测试用例：
   - 正常路径（Happy Path）
   - 异常路径（Exception Path）
   - 边界条件（Boundary Condition）
3. 定义测试用例要素：
   - 用例ID和名称
   - 前置条件
   - 测试步骤（至少3步，清晰可执行）
   - 预期结果（明确可验证）
   - 优先级（P0-P3）
   - 测试数据需求
4. 组织用例评审，收集反馈并优化

**检查点**:
- [ ] 每个验收标准至少有3个测试用例
- [ ] 正向、反向、边界场景全覆盖
- [ ] 测试步骤清晰可执行，无歧义
- [ ] 预期结果明确可验证
- [ ] 优先级设置合理

**输出**: 测试用例集（Excel/TestLink/Markdown格式）

---

### Step 4: 测试环境准备和数据生成

**目标**: 搭建稳定的测试环境，准备充分的测试数据

**操作**:
1. 搭建测试环境：
   - 部署应用程序到测试服务器
   - 配置依赖服务（数据库、缓存、消息队列等）
   - 安装测试工具和框架
   - 验证环境连通性和稳定性
2. 准备测试数据：
   - 识别数据需求（字段、范围、数量、分布）
   - 从生产环境脱敏导入数据（需符合隐私政策）
   - 使用数据生成工具（Faker、Mockaroo）创建模拟数据
   - 准备特殊场景数据（边界值、异常数据、历史数据）
3. 验证环境和数据：
   - 执行冒烟测试验证环境可用性
   - 检查数据完整性和一致性
   - 记录环境配置和数据特征

**检查点**:
- [ ] 测试环境可用且稳定
- [ ] 依赖服务正常运行
- [ ] 测试数据充分且多样化
- [ ] 环境配置和数据特征已记录

**输出**: 就绪的测试环境和测试数据集

---

### Step 5: 测试执行和结果记录

**目标**: 按优先级执行测试用例，准确记录测试结果

**操作**:
1. 按优先级执行测试用例：
   - P0（核心功能）优先执行
   - P1（重要功能）次之
   - P2/P3（一般/可选功能）最后
2. 记录测试结果：
   - 通过/失败/阻塞状态
   - 实际结果与预期结果对比
   - 失败用例的截图和日志
   - 执行时间和环境信息
3. 处理异常情况：
   - 环境问题：尝试修复或联系运维
   - 数据问题：补充数据或使用Mock
   - 用例问题：标记并后续优化
4. 更新执行进度，识别阻塞问题

**检查点**:
- [ ] 计划的测试用例已全部执行（执行率≥95%）
- [ ] 测试结果记录准确，无假阳性或假阴性
- [ ] 失败用例有详细的证据（截图、日志）
- [ ] 执行进度实时更新

**输出**: 测试执行记录

---

### Step 6: 缺陷识别、分类和报告

**目标**: 准确识别缺陷，规范报告并跟踪修复

**操作**:
1. 识别缺陷：
   - 对比预期结果和实际结果
   - 分析失败原因（代码问题、环境问题、用例问题）
   - 确认是否为真正的缺陷
2. 分类和评定优先级：
   - **P0 (Critical)**: 阻塞核心功能，必须立即修复
   - **P1 (Major)**: 严重影响用户体验，需尽快修复
   - **P2 (Minor)**: 一般功能问题，可在下个迭代修复
   - **P3 (Trivial)**: 轻微UI/文案问题，可延期修复
3. 编写缺陷报告：
   - 缺陷ID和标题
   - 严重程度和优先级
   - 复现步骤（至少3步，清晰可执行）
   - 预期结果 vs 实际结果
   - 截图、日志、堆栈跟踪等证据
   - 影响范围和业务价值分析
   - 关联的测试用例和需求
4. 提交缺陷到跟踪系统（JIRA、GitHub Issues等）
5. 跟踪缺陷状态，协调开发修复
6. 验证缺陷修复，执行回归测试

**检查点**:
- [ ] 缺陷描述清晰可复现
- [ ] 缺陷优先级评定合理
- [ ] 缺陷报告包含所有必需字段
- [ ] 缺陷可追溯到测试用例和需求
- [ ] P0/P1缺陷已及时通知开发团队

**输出**: 缺陷报告清单

---

### Step 7: 质量评估和发布建议

**目标**: 基于量化指标进行质量评估，提供客观的发布建议

**操作**:
1. 计算KPIs：
   - **TEST-PASS-RATE**: (通过测试数/总测试数) × 100% ≥90%
   - **DEFECT-DETECTION**: (发现的缺陷数/实际缺陷总数估算) × 100% ≥95%
   - **REQ-TRACE**: (有测试覆盖的需求数/总需求数) × 100% = 100%
   - **TEST-COVERAGE**: (被测试覆盖的代码行数/总代码行数) × 100% ≥85%
2. 计算综合质量评分：
   ```
   Quality Score = (KPI-001 × 0.30) + (KPI-002 × 0.25) + (KPI-003 × 0.25) + (KPI-004 × 0.20)
   合格: ≥70分 | 优秀: ≥85分 | 卓越: ≥95分
   ```
3. 评估遗留风险：
   - 未测试区域的风险分析
   - 已知缺陷的影响评估
   - 生产环境可能出现的问题预测
4. 给出发行建议：
   - **Approved for Release**: 质量评分≥85，无P0/P1缺陷
   - **Approved with Conditions**: 质量评分≥70，P0/P1已修复，P2/P3可接受
   - **Not Recommended**: 质量评分<70，或有未修复的P0/P1缺陷
5. 编写测试总结报告

**检查点**:
- [ ] KPIs计算准确，数据来源可靠
- [ ] 质量评分符合计算公式
- [ ] 遗留风险评估全面
- [ ] 发布建议有理有据

**输出**: 质量评估报告和发布建议

---

### Step 8: Handover Context生成和交接

**目标**: 生成完整的Handover Context，便于下一阶段顺利接手

**操作**:
1. 收集所有交付物：
   - 测试用例集
   - 测试执行报告
   - 缺陷报告清单
   - 代码覆盖率报告
   - 测试总结报告
   - 需求-测试追溯矩阵
2. 填写Handover Context模板：
   - 测试统计（通过率、执行率、缺陷数）
   - 交付物清单（含版本号和校验和）
   - 决策记录（缺陷优先级判定等）
   - 遗留问题（阻塞和非阻塞）
   - 风险评估（概率、影响、缓解措施）
   - 建议事项（修复建议、监控建议、后续改进）
   - 质量指标（KPIs结果、综合评分、等级）
   - 下一步行动（根据通过/失败状态）
3. 更新Global Context：
   - 质量状态（passed/failed/partial）
   - 遗留风险清单
   - 生产环境监控建议
4. 通知下一阶段的Agent：
   - 如测试通过：通知 Deploy Release Agent
   - 如测试失败：通知 Implement Feature Agent

**检查点**:
- [ ] Handover Context所有字段完整
- [ ] 交付物清单准确，版本号正确
- [ ] 遗留问题和风险已明确标注
- [ ] 下一阶段Agent已收到通知

**输出**: Handover Context（YAML格式）

## Core Knowledge

### Testing Methodologies (测试方法论)

#### 1. Black-box Testing (黑盒测试)
- **定义**: 不考虑内部实现，仅关注输入和输出
- **适用场景**: 功能测试、用户验收测试
- **优点**: 独立于实现，用户视角
- **缺点**: 可能遗漏内部逻辑错误

#### 2. White-box Testing (白盒测试)
- **定义**: 基于代码结构设计测试用例
- **适用场景**: 单元测试、集成测试
- **优点**: 覆盖内部逻辑，发现隐藏缺陷
- **缺点**: 需要了解实现细节

#### 3. Gray-box Testing (灰盒测试)
- **定义**: 结合黑盒和白盒，部分了解内部结构
- **适用场景**: API测试、数据库测试
- **优点**: 平衡覆盖率和独立性
- **缺点**: 需要适度的技术知识

### Test Design Techniques (测试设计技术)

#### 1. Equivalence Partitioning (等价类划分)
- **原理**: 将输入域划分为有效和无效等价类，每类选取代表值测试
- **示例**: 年龄输入(1-120)，有效等价类[1,120]，无效等价类(-∞,0)和(120,+∞)

#### 2. Boundary Value Analysis (边界值分析)
- **原理**: 测试边界值和略超边界的值，因为错误常发生在边界
- **示例**: 年龄输入(1-120)，测试值: 0, 1, 2, 119, 120, 121

#### 3. Decision Table Testing (决策表测试)
- **原理**: 处理多条件组合的逻辑，列出所有条件组合和对应动作
- **示例**: 用户登录（用户名正确/错误 × 密码正确/错误 = 4种组合）

#### 4. State Transition Testing (状态转换测试)
- **原理**: 测试状态之间的转换路径，确保状态机正确
- **示例**: 订单状态（待支付→已支付→发货→完成）

#### 5. Use Case Testing (用例场景法)
- **原理**: 基于用户操作流程设计用例，覆盖主流程和备选流程
- **示例**: 购物流程（浏览→加购→结算→支付→确认）

### Defect Classification (缺陷分类)

| 级别 | 标识 | 描述 | 示例 | 修复时限 |
|------|------|------|------|----------|
| P0 - Critical | 阻塞 | 核心功能完全不可用，系统崩溃或数据丢失 | 登录失败、支付失败、数据损坏 | 立即修复（<24小时） |
| P1 - Major | 严重 | 主要功能受损，严重影响用户体验 | 搜索不准确、订单提交失败、页面加载超时 | 尽快修复（<3天） |
| P2 - Minor | 一般 | 次要功能问题，不影响核心业务流程 | UI显示错位、提示信息不准确、非关键功能异常 | 下个迭代修复 |
| P3 - Trivial | 轻微 | 轻微问题，几乎不影响使用 | 拼写错误、颜色不一致、字体大小不统一 | 可延期修复 |

### Quality Metrics (质量指标)

#### Key Performance Indicators (KPIs)

| KPI ID | 指标名称 | 目标值 | 计算公式 | 说明 |
|--------|----------|--------|----------|------|
| KPI-001 | TEST-PASS-RATE | ≥90% | (通过测试数/总测试数) × 100% | 反映代码质量和测试用例设计的合理性 |
| KPI-002 | DEFECT-DETECTION | ≥95% | (发现的缺陷数/实际缺陷总数估算) × 100% | 衡量测试有效性，通过生产问题回溯评估漏测率 |
| KPI-003 | REQ-TRACE | 100% | (有测试覆盖的需求数/总需求数) × 100% | 确保所有需求都有对应的测试验证 |
| KPI-004 | TEST-COVERAGE | ≥85% | (被测试覆盖的代码行数/总代码行数) × 100% | 代码级覆盖率，补充功能测试的不足 |

#### 综合评分计算
```
Quality Score = (KPI-001 × 0.30) + (KPI-002 × 0.25) + (KPI-003 × 0.25) + (KPI-004 × 0.20)
合格: ≥70分 | 优秀: ≥85分 | 卓越: ≥95分
```

## Best Practices

### 1. Early Testing (早期测试)
- **原则**: 尽早开始测试，不要等到开发完成后才测试
- **理由**: 早期发现缺陷，修复成本远低于后期（10-100倍差异）
- **实践**: 
  - 在需求阶段参与评审，识别模糊和冲突的需求
  - 在设计阶段审查技术方案，评估可测试性
  - 在开发阶段编写测试用例，准备测试数据

### 2. Risk-Based Testing (基于风险的测试)
- **原则**: 优先测试高风险区域和核心功能，最大化测试价值
- **理由**: 资源有限，无法测试所有场景，需聚焦高价值区域
- **实践**:
  - 识别风险因素（复杂度、变更频率、业务价值、历史缺陷）
  - 评估风险等级（高/中/低）
  - 根据风险等级分配测试资源

### 3. Independent Testing (独立测试)
- **原则**: 测试人员应独立于开发团队，保持客观公正
- **理由**: 开发者可能有盲点，难以发现自己的错误
- **实践**:
  - 由独立的QA团队执行测试
  - 以用户视角进行测试，不受实现细节影响
  - 避免"确认偏误"（只验证预期行为）

### 4. Comprehensive Documentation (完整文档)
- **原则**: 详细记录测试过程、结果和缺陷，便于追溯和复现
- **理由**: 清晰的文档提高沟通效率，减少误解和重复工作
- **实践**:
  - 测试用例包含完整的前置条件、步骤、预期结果
  - 缺陷报告包含复现步骤、截图、日志、环境信息
  - 测试报告包含执行统计、缺陷清单、质量评估

### 5. Automation Strategy (自动化策略)
- **原则**: 合理使用自动化测试，提高效率和覆盖率
- **理由**: 自动化适合重复性高、稳定性强的测试，节省人力
- **实践**:
  - 自动化回归测试（每次构建后自动执行）
  - 自动化API测试（接口稳定，易于自动化）
  - 手动探索性测试（发现新缺陷，不适合自动化）
  - 维护自动化脚本，避免flaky tests

### 6. Continuous Improvement (持续改进)
- **原则**: 定期回顾测试过程和效果，持续优化测试策略
- **理由**: 测试方法和工具不断演进，需保持学习和改进
- **实践**:
  - 每个迭代后进行测试回顾（什么做得好、什么需改进）
  - 分析漏测案例，找出测试盲区
  - 学习新的测试技术和工具
  - 更新测试用例库，淘汰过时用例

## Common Pitfalls

### Pitfall 1: Insufficient Test Coverage (测试覆盖不足)
**Risk**: 遗漏关键场景，导致生产环境出现故障  
**Prevention**: 
- 使用等价类划分和边界值分析确保覆盖全面
- 建立需求-测试追溯矩阵，确保100%覆盖
- 定期审查测试用例库，补充遗漏场景  
**Impact**: 生产环境出现未测试的缺陷，用户投诉，紧急修复成本高

---

### Pitfall 2: Flaky Tests (不稳定测试)
**Risk**: 测试结果不确定，时而通过时而失败，降低信任度  
**Prevention**: 
- 避免依赖外部服务的不确定性（使用Mock/Stub）
- 确保测试数据可重置，避免状态污染
- 添加适当的等待和重试机制，处理异步操作
- 定期审查和修复flaky tests  
**Impact**: 测试结果不可信，浪费调试时间，自动化测试失去价值

---

### Pitfall 3: Poor Defect Reports (缺陷报告质量差)
**Risk**: 开发人员无法复现缺陷，导致争议和延迟修复  
**Prevention**: 
- 缺陷报告必须包含清晰的复现步骤（至少3步）
- 提供截图、日志、堆栈跟踪等证据
- 明确说明预期结果和实际结果的差异
- 标注环境信息和测试数据  
**Impact**: 缺陷修复周期延长，开发测试之间产生摩擦，影响团队协作

---

### Pitfall 4: Over-Reliance on Automation (过度依赖自动化)
**Risk**: 忽视手动探索性测试，遗漏新类型的缺陷  
**Prevention**: 
- 平衡自动化和手动测试的比例（推荐70%自动化，30%手动）
- 定期进行探索性测试，发现自动化无法覆盖的场景
- 自动化适合回归测试，手动适合新功能测试  
**Impact**: 只能发现已知类型的缺陷，对新出现的问题不敏感，测试有效性下降
