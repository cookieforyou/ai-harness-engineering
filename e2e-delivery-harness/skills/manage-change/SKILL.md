# Change Management Skill

## Skill Overview

变更管理是确保项目变更可控、可追溯的过程。本技能提供变更评估、决策和实施的方法论。

## Prerequisites

1. 理解软件开发流程
2. 理解需求管理
3. 理解项目管理基础知识

## Knowledge Base

### 变更类型

| 类型 | 描述 | 影响程度 |
|------|------|----------|
| 新增 | 添加新功能 | 高 |
| 修改 | 更改现有功能 | 中-高 |
| 删除 | 移除功能 | 中 |
| 优化 | 性能或体验改进 | 低-中 |

### 影响分析维度

1. **功能影响**
   - 新增/修改/删除的功能
   - 对已有功能的影响
   - 对用户体验的影响

2. **技术影响**
   - 代码变更范围
   - 数据库变更
   - API 变更
   - 第三方依赖

3. **测试影响**
   - 新增测试用例
   - 回归测试范围
   - 测试环境变更

4. **文档影响**
   - 用户文档
   - 技术文档
   - 培训材料

### Decision框架

```
变更决策 = f(价值, 成本, 风险, 时间)

接受条件: 价值 > 成本 + 风险
```

### 变更优先级

| 优先级 | 条件 | 处理时间 |
|--------|------|----------|
| P0 | 影响核心功能，紧急 | 24小时内 |
| P1 | 影响重要功能 | 3天内 |
| P2 | 影响一般功能 | 1周内 |
| P3 | 影响小，可延迟 | 计划迭代 |

## Procedures

### 影响评估流程

1. 理解变更请求
2. 分解变更范围
3. 逐项分析影响
4. 评估影响程度
5. 汇总评估结果
6. 制定决策建议

### 变更评审流程

1. 准备评审材料
2. 组织评审会议
3. 讨论变更内容
4. 达成变更决策
5. 记录决策结果

## Examples

### Example：新增功能变更

**变更内容**：在用户管理模块新增批量导入功能

**影响分析**：
- 功能影响：新增批量导入功能
- 技术影响：新增导入接口、导入服务、数据验证
- 测试影响：新增导入测试用例、边界测试
- 文档影响：更新用户文档

- 工作量：5 人天
- 影响程度：中
- 建议：接受


## Core Knowledge

> Essential knowledge domain for manage-change execution.

### Domain Fundamentals

#### 变更管理基本概念

变更管理 (Change Management) 是 ITIL 框架中的核心流程之一，目标是确保所有变更有标准化的评估、审批、实施和验证流程，最小化变更对业务的负面影响。

**核心目标**:
1. **风险控制**: 评估和降低变更带来的风险
2. **标准化流程**: 确保所有变更遵循统一的流程
3. **可追溯性**: 全程记录变更的每个环节
4. **业务连续性**: 最小化变更对业务的干扰

#### 变更类型 (ITIL 分类)

| 变更类型 | 定义 | 风险等级 | 审批流程 | 示例 |
|----------|------|----------|----------|------|
| **Standard (标准变更)** | 预授权、低风险、有明确步骤的常规变更 | 低 | 无需单独审批，遵循预定义流程 | 扩缩容、重启服务、日常备份 |
| **Normal (正常变更)** | 需要经过完整评估和审批流程的变更 | 中-高 | 需变更经理审批或 CAB 评审 | 新功能上线、数据库迁移、架构变更 |
| **Emergency (紧急变更)** | 必须立即实施以修复严重故障的变更 | 高-严重 | 紧急审批通道，事后补录 | 安全漏洞修复、紧急hotfix、回滚 |

#### 风险矩阵

```
风险等级 = 影响程度 × 发生概率

影响程度:
  1 - 微小: 几乎无用户感知
  2 - 小: 影响少数用户，可快速恢复
  3 - 中: 影响部分功能，需一定时间恢复
  4 - 大: 影响核心功能，恢复时间较长
  5 - 严重: 全站不可用，严重影响业务

发生概率:
  1 - 极低: < 5%
  2 - 低: 5-20%
  3 - 中: 20-50%
  4 - 高: 50-80%
  5 - 极高: > 80%

风险等级判定:
  1-4:  低风险 (Low)
  5-9:  中风险 (Medium)
  10-16: 高风险 (High)
  17-25: 严重风险 (Critical)
```

### Key Principles

1. **风险导向**: 变更管理的力度应与变更的风险等级匹配，高风险变更需要更严格的评估和审批
2. **标准化先行**: 对于经常执行的变更，优先将其自动化或标准化为 Standard Change，减少审批开销
3. **可回滚为王**: 每一个变更都必须有可执行的回滚方案，回滚是最后一道安全网
4. **变更窗口**: 变更应在业务低峰期执行，减少对用户的影响
5. **持续改进**: 定期分析变更数据（成功率、事件关联率、回滚率），优化变更流程

## Best Practices

> Proven practices for manage-change excellence.

### 1. 变更类型分类矩阵

**做法**: 根据变更的目的和紧急程度，使用分类矩阵快速判定变更类型

```yaml
change_type_classification:
  标准变更 (Standard Change):
    conditions:
      - 已预先评估和授权
      - 风险等级为低
      - 有标准操作流程 (SOP)
      - 执行频率高
    examples:
      - "Kubernetes 服务扩缩容"
      - "日常备份任务调整"
      - "低风险配置变更"
    approval: "无需审批，遵循 SOP"

  正常变更 (Normal Change):
    conditions:
      - 需要通过标准审批流程
      - 风险等级为中到高
      - 需要 CAB 评审（重大变更）
    sub_types:
      - "重大变更: 需要 CAB 评审"
      - "一般变更: 变更经理审批"
    examples:
      - "新功能版本发布"
      - "数据库 Schema 变更"
      - "基础设施架构变更"

  紧急变更 (Emergency Change):
    conditions:
      - 需要立即实施
      - 用于修复生产故障或安全漏洞
      - 可以绕过标准审批
    constraints:
      - 必须有紧急审批人授权
      - 实施完成后 24 小时内补录完整信息
      - 紧急变更后需进行复盘
    examples:
      - "安全漏洞紧急修复"
      - "P0/P1 故障的 hotfix 部署"
```

**理由**: 清晰的分类标准避免变更类型判断的主观性和不一致性，确保每种变更得到适当的处理。

### 2. 风险矩阵评估方法

**做法**: 使用标准化的风险矩阵评估变更风险，确保评估结果客观、可重复

```yaml
risk_assessment_matrix:
  dimensions:
    technical_risk:
      factors:
        - "变更复杂度（代码量、影响模块数）"
        - "依赖关系（外部依赖、下游系统）"
        - "数据变更（Schema 变更、数据迁移）"
        - "回滚复杂度"
      scoring: "1-5 分制"
      
    business_impact:
      factors:
        - "用户感知度（面向用户/内部系统）"
        - "业务关键性（核心功能/辅助功能）"
        - "合规要求（安全审计、数据保护）"
        - "时间敏感度（业务高峰期/低谷期）"
      scoring: "1-5 分制"
      
    rollback_risk:
      factors:
        - "回滚复杂度（代码回滚/数据回滚）"
        - "回滚时间（分钟/小时）"
        - "数据兼容性（向前兼容/不兼容）"
      scoring: "1-5 分制"

  composite_score: "technical_risk × 0.4 + business_impact × 0.4 + rollback_risk × 0.2"
  
  risk_levels:
    low: "1-2 分，标准变更流程"
    medium: "3-5 分，正常变更流程"
    high: "6-8 分，需要 CAB 评审"
    critical: "9-15 分，需要管理层审批"
```

**理由**: 量化风险矩阵消除主观臆断，确保不同变更经理的评估结果一致，为审批决策提供客观依据。

### 3. 审批链配置规则

**做法**: 根据变更类型和风险等级，自动匹配审批路由

```yaml
approval_routing:
  standard_change:
    - "无需审批，自动批准"
    
  normal_change_low_risk:
    - "技术负责人 → 变更经理"
    
  normal_change_medium_risk:
    - "技术负责人 → 变更经理 → 部门主管"
    
  normal_change_high_risk:
    - "技术负责人 → 变更经理 → CAB 评审 → CTO"
    
  emergency_change:
    - "紧急审批人（值班经理/CTO）→ 事后补录"
    
  cab_composition:
    members:
      - "变更经理"
      - "技术架构师"
      - "运维负责人"
      - "安全代表"
      - "业务代表"
    quorum: "≥ 3 人"
    meeting_frequency: "每周一次 / 紧急会议随时召开"
```

**理由**: 路由规则避免审批流转到错误的人或层级，确保审批效率和合规性。

### 4. 变更窗口规划

**做法**: 根据业务特点规划变更窗口，平衡变更效率和业务风险

```yaml
change_window_planning:
  windows:
    - window: "周二 20:00-24:00"
      type: "常规变更窗口"
      suitable_for: "标准变更、一般正常变更"
      
    - window: "周四 22:00-04:00"
      type: "重大变更窗口"
      suitable_for: "高风险变更、重大架构变更"
      
    - window: "周六 02:00-06:00"
      type: "周末变更窗口"
      suitable_for: "数据库迁移、重构等耗时较长变更"
      
  restrictions:
    - "周五下午及周末原则上不安排重大变更"
    - "业务高峰期（如大促、节假日）冻结变更"
    - "紧急变更不受窗口限制，但需紧急审批"
    
  blackout_periods:
    - "双十一/黑五大促期间"
    - "季度末财报期间"
    - "重大业务活动期间"
```

**理由**: 合理的变更窗口分配减少变更对业务的影响，为变更实施创造安全的时间空间。

### 5. CAB (Change Advisory Board) 流程

**做法**: 建立标准化的 CAB 会议和评审流程

```yaml
cab_process:
  meeting_schedule:
    frequency: "每周一次"
    duration: "60 分钟"
    agenda:
      - "变更说明（5min/项）"
      - "风险评估（5min/项）"
      - "影响分析（5min/项）"
      - "讨论和决策（10min/项）"
  
  submission_requirements:
    - "变更说明文档"
    - "风险评估报告"
    - "实施计划"
    - "回滚方案"
    - "测试验证报告"

  decision_outcomes:
    - "批准 (Approved): 可按计划实施"
    - "有条件批准 (Approved with Conditions): 需满足附加条件"
    - "推迟 (Deferred): 需要更多信息或调整"
    - "拒绝 (Rejected): 变更不可行或风险过高"
    
  post_cab_actions:
    - "记录决策结果"
    - "通知变更发起人"
    - "跟踪有条件批准的完成情况"
```

**理由**: 标准化的 CAB 流程确保重大变更得到充分的集体评审，降低变更风险。

### 6. 回滚方案要求

**做法**: 每个变更都必须包含可验证的回滚方案

```yaml
rollback_plan_template:
  回滚触发条件:
    - "变更后核心功能不可用"
    - "错误率上升超过 5%"
    - "响应时间增加超过 30%"
    - "数据一致性校验失败"
    
  回滚步骤:
    - step_1: "停止变更操作"
    - step_2: "执行代码回滚到上一版本"
    - step_3: "数据回滚（如涉及）"
    - step_4: "确认服务恢复"
    - step_5: "验证核心功能正常"
    
  回滚验证:
    - "错误率恢复至变更前水平"
    - "响应时间恢复至变更前水平"
    - "核心功能回归测试通过"
    
  回滚风险:
    - "数据回滚可能导致部分数据丢失"
    - "回滚过程中服务可能短暂不可用"
```

**理由**: 充分的回滚准备是变更安全的最后一道防线，能让团队在发现问题时果断回滚而不犹豫。

## Anti-patterns (反模式)

> 与 Common Pitfalls 同义，执行时合并检查。

## Common Pitfalls

> Frequent mistakes to avoid during manage-change execution.

### Pitfall 1: 变更流程过重导致应急变通

**Risk**: 标准变更流程过于繁琐（如普通配置更改也需要多级审批），导致团队在紧急时选择绕过流程、"先改后补"，结果造成变更失控、未记录、不可追溯。

**Prevention**:
- 建立 Standard Change 清单，低风险变更自动化审批
- 简化低风险变更的审批流程（如确认制而非审批制）
- 为常见变更创建标准操作流程 (SOP)
- 紧急变更设置清晰的紧急通道，让团队不需要"绕路"
- 定期审查变更流程，根据反馈持续优化

**Impact**: 如果未避免，团队形成"先改后补"的坏习惯，大量未记录变更混入系统，发生故障时无法定位根因，审计无法通过。

### Pitfall 2: 风险评分主观导致不一致

**Risk**: 缺乏标准化的风险评分标准，不同变更经理对相同变更给出不同风险评估结果，导致变更处理的"人治"而非"法治"。

**Prevention**:
- 建立量化风险评分矩阵（技术风险、业务影响、回滚风险）
- 定义每个评分数值对应的具体条件
- 对高风险项设置强制 CAB 评审
- 定期审核风险评估的一致性
- 培训所有变更经理使用统一评估标准

**Impact**: 如果未避免，同类型变更的处理方式因评审人而异，团队无法预测变更处理结果，降低对流程的信任。

### Pitfall 3: 回滚方案流于形式

**Risk**: 变更单中的回滚方案只是"回滚到上一个版本"一句带过，没有考虑数据兼容性、回滚时间、服务依赖等实际情况，导致实际需要回滚时无法快速执行。

**Prevention**:
- 回滚方案必须包含详细的回滚步骤和验证方法
- 区分代码回滚和数据回滚的不同场景
- 回滚方案由实施人编写，至少 1 人 review
- 重大变更的回滚方案需要在预发环境验证
- 回滚方案纳入 CAB 评审的必查项

**Impact**: 如果未避免，回滚时发现方案不可行，团队在高压下临时设计回滚方案，极易出错，延长故障时间。

### Pitfall 4: 变更窗口管理混乱

**Risk**: 多个变更在同一窗口无协调地并行实施，变更间相互干扰，故障时无法确定是哪个变更导致的问题。

**Prevention**:
- 建立变更日历，可视化展示所有计划中的变更
- 同一窗口的变更不能影响同一服务/模块
- 设立变更协调角色，在窗口开始前确认变更计划
- 重大变更独占窗口，不与其他变更并行
- 变更窗口结束后检查是否有冲突或异常

**Impact**: 如果未避免，变更冲突导致系统不稳定，故障时变更过多无法定位根因，大量回滚浪费资源。

### Pitfall 5: 紧急变更事后不补录

**Risk**: 紧急变更通过快速通道实施了修复，但事后没有补录变更记录、没有进行复盘，导致变更管理出现"后门"。

**Prevention**:
- 紧急变更必须在24小时内补录完整的变更记录
- 紧急变更7天内必须进行复盘
- 紧急变更计数纳入月度变更统计
- 定期审计紧急变更的补录完成率
- 分析紧急变更趋势，识别需要改进的流程环节

**Impact**: 如果未避免，紧急变更成为管理盲区，无法统计变更关联的事件，也无法从紧急变更中学习改进。
