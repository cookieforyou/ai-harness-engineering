## Core Knowledge

> Essential knowledge domain for review-design execution.

### Domain Fundamentals

#### 技术方案评审概述

技术方案评审 (Design Review) 是软件开发流程中的关键质量关口，在方案正式实施之前，通过系统化的评审流程发现设计缺陷、提升方案质量、降低实施风险。

**评审的核心价值**:
1. **早期发现问题**: 在设计阶段发现问题的修复成本远低于实施阶段
2. **知识共享**: 评审过程是团队知识传递和经验交流的重要途径
3. **质量把关**: 确保设计方案达到进入开发阶段的质量标准
4. **风险缓解**: 在设计阶段识别和缓解技术和业务风险
5. **标准对齐**: 确保设计方案符合团队和组织的技术标准

#### 架构评审方法论

| 方法论 | 适用场景 | 核心特点 | 输出 |
|--------|----------|----------|------|
| **ATAM** (Architecture Tradeoff Analysis Method) | 大型系统架构评审 | 关注质量属性间的权衡分析，识别架构决策的敏感性点和权衡点 | 架构风险评估报告、敏感度分析 |
| **SAAM** (Software Architecture Analysis Method) | 软件架构可维护性评估 | 关注架构的可修改性和功能覆盖 | 场景分析、架构修改评估 |
| **CBAM** (Cost Benefit Analysis Method) | 架构决策的经济效益分析 | 结合 ATAM 结果进行成本和收益量化分析 | ROI 分析、投资优先级 |
| **ADR 评审** (Architecture Decision Record Review) | 单个架构决策评审 | 评审决策的上下文、备选方案和理由 | ADR 审批结果 |

#### 设计模式评估

评审设计中使用的设计模式是否恰当:

| 设计模式 | 适用场景 | 评审要点 |
|----------|----------|----------|
| **分层架构** | 企业应用 | 层次职责是否清晰，是否遵循依赖倒置原则 |
| **微服务架构** | 大型分布式系统 | 服务粒度是否合理，服务间通信方式是否恰当 |
| **事件驱动架构** | 异步处理、解耦 | 事件设计是否合理，一致性保证机制是否到位 |
| **CQRS** | 读写分离场景 | 命令和查询的分离是否合理，一致性模型是否明确 |
| **Event Sourcing** | 审计、溯源场景 | 事件存储和重放机制是否完备 |
| **Strangler Fig** | 系统迁移 | 迁移策略是否渐进式，新旧系统共存期的兼容性 |

### Key Principles

1. **分离关注点**: 评审应逐维度进行，避免将需求、技术、安全等混在一起评审
2. **层级递进**: 先评审高层架构，再评审详细设计，确保每层设计在上一层约束下进行
3. **权衡分析**: 每个架构决策都有 trade-off，评审要识别并记录这些权衡
4. **证据优先**: 以数据和事实为依据评审设计决策，避免基于"我觉得"的主观判断
5. **风险导向**: 优先关注高风险的决策和设计，合理分配评审精力
6. **渐进式确认**: 设计不需要一开始就是完美的，但需要满足当前阶段的质量要求

## Best Practices

> Proven practices for review-design excellence.

### 1. ATAM 架构评审法

**做法**: 采用 ATAM 结构化方法进行系统架构评审

```yaml
atam_review_process:
  阶段一: "场景收集"
    - "收集业务驱动因素和架构驱动因素"
    - "识别关键质量属性（性能、可用性、安全性、可修改性）"
    - "定义具体场景来验证每个质量属性"
    
  阶段二: "架构展示"
    - "架构师展示架构设计方案"
    - "解释架构决策和权衡"
    - "展示关键的架构视图"
    
  阶段三: "质量属性分析"
    - "逐个分析架构决策对关键质量属性的影响"
    - "识别敏感度点 (Sensitivity Points): 对特定质量属性有显著影响的决策"
    - "识别权衡点 (Tradeoff Points): 影响多个质量属性的决策"
    - "识别风险点 (Risk Points): 未明确或有潜在问题的决策"
    
  阶段四: "优先级排序"
    - "按业务价值和技术风险对场景排序"
    - "确认关键质量属性的优先级"
    - "识别架构调整方向"
    
  output:
    - "架构风险评估报告"
    - "敏感度点和权衡点清单"
    - "架构改进建议（按优先级排序）"
```

**理由**: ATAM 提供了系统化的架构评估框架，通过场景驱动和质量属性分析，确保架构评审不是随意发挥而是有方法论支撑的结构化过程。

### 2. SOLID 原则检查清单

**做法**: 使用 SOLID 原则检查设计方案的面向对象设计质量

| 原则 | 检查点 | 常见违规场景 |
|------|--------|--------------|
| **S**ingle Responsibility | 每个类/模块是否只有一个变更理由？ | "上帝类"包含多个职责 |
| **O**pen-Closed | 是否可以通过扩展而非修改来增加功能？ | 需要修改已有代码来增加新功能 |
| **L**iskov Substitution | 子类是否可以完全替代父类？ | 子类抛出父类未定义的异常 |
| **I**nterface Segregation | 接口是否足够小，客户端不需要依赖不需要的方法？ | "胖接口"包含多个不相关的方法 |
| **D**ependency Inversion | 是否依赖抽象而非具体实现？ | 高层模块直接依赖低层模块 |

**理由**: SOLID 原则是面向对象设计的基石，在评审中使用可以快速发现设计违反基本设计原则的问题，确保代码的可维护性和可扩展性。

### 3. ADR (架构决策记录) 评审标准

**做法**: 对每个 ADR 进行结构化评审

```yaml
adr_review_criteria:
  完整性检查:
    - [ ] "标题清晰描述决策内容"
    - [ ] "状态明确（Proposed/Accepted/Deprecated/Superseded）"
    - [ ] "上下文 (Context) 说明了决策背景和驱动力"
    - [ ] "决策 (Decision) 明确表述了最终的决策内容"
    - [ ] "理由 (Rationale) 详细说明了决策的理由"
    - [ ] "后果 (Consequences) 列出了正反两面的影响"
    - [ ] "备选方案 (Alternatives) 至少包含 2 个"
    
  合理性检查:
    - [ ] "决策有充分的数据或实验支持"
    - [ ] "备选方案被客观评估，非预设立场"
    - [ ] "决策后果被充分理解"
    - [ ] "与已有 ADR 一致，无矛盾"
    - [ ] "团队对决策有共识"
    
  时效性检查:
    - [ ] "ADR 创建时间合理"
    - [ ] "如果状态是 Superseded，记录了替代的 ADR"
```

**理由**: ADR 是架构知识的核心载体，标准化的评审确保每个架构决策都有充分的理由和记录，新成员可以快速理解架构演变过程。

### 4. 评审报告的严重程度分级

**做法**: 按严重程度分级报告问题，便于负责人排序处理

```yaml
issue_severity_classification:
  P0 - Critical (阻塞):
    definition: "导致方案不可行或产生严重安全风险的缺陷"
    examples:
      - "设计不满足核心业务需求"
      - "存在严重安全漏洞"
      - "技术选型不可行"
    action: "必须修复，修复后需重新评审"
    timeline: "阻塞方案进展"
    
  P1 - Major (严重):
    definition: "对系统质量有重大影响的问题"
    examples:
      - "性能设计无法满足目标"
      - "存在数据一致性问题"
      - "关键模块缺少设计"
    action: "必须修复，修复后变更确认"
    timeline: "实施前必须修复"
    
  P2 - Minor (一般):
    definition: "影响可维护性或建议改进"
    examples:
      - "接口设计可优化"
      - "缺少异常处理设计"
      - "文档不完整"
    action: "建议修复或记录待办"
    timeline: "可根据排期安排"
    
  P3 - Suggestion (建议):
    definition: "非必需但有助于提升质量的建议"
    examples:
      - "可以考虑使用更新的技术方案"
      - "可以增加更多监控指标"
      - "代码组织方式可以优化"
    action: "可选择性采纳"
    timeline: "无强制要求"
```

**理由**: 标准化的问题严重程度分级帮助团队快速识别哪些问题是必须立即修复的，哪些可以后续处理，避免关键问题被淹没在大量建议中。

### 5. 评审会议结构

**做法**: 采用高效的评审会议结构，提升评审质量和效率

```yaml
review_meeting_agenda:
  会议类型:
    - "架构评审 (Architecture Review): 60-90 分钟"
    - "详细设计评审 (Detailed Design Review): 60 分钟"
    - "接口评审 (API Review): 30-45 分钟"
    
  标准议程 (60 分钟):
    0:00-0:05  "介绍评审目标和范围"
    0:05-0:20  "设计方讲解设计方案"
    0:20-0:45  "讨论和问题"
              - "评审人员按维度提问"
              - "记录发现的问题"
              - "确认问题的严重程度"
    0:45-0:55  "总结评审结论"
              - "通过 / 有条件通过 / 不通过"
              - "确认待办项和责任人"
    0:55-1:00  "结束"
              - "确认评审纪要发布时间"
              - "确认下一轮评审计划（如有）"
              
  评审角色:
    - "主持人 (Moderator): 控制会议节奏，确保议程执行"
    - "设计方 (Presenter): 讲解设计方案"
    - "评审员 (Reviewer): 提出问题和建议"
    - "记录员 (Recorder): 记录讨论要点和决定"
```

**理由**: 高效的会议结构确保评审在有限时间内完成，所有角色各司其职，避免评审变成漫无边际的讨论。

## Anti-patterns (反模式)

> 与 Common Pitfalls 同义，执行时合并检查。

## Common Pitfalls

> Frequent mistakes to avoid during review-design execution.

### Pitfall 1: 评审范围过大导致失效

**Risk**: 试图在一次评审中覆盖所有设计内容（架构、接口、数据库、部署方案等），导致评审深度不足，关键问题被遗漏，参与者疲劳。

**Prevention**:
- 将大型评审拆分为多个专题评审（架构评审、接口评审、数据设计评审）
- 每个评审聚焦于 1-2 个核心维度
- 控制单次评审的设计量，不超过 2 小时的讲解量
- 提前分发设计文档，要求评审员提前阅读
- 使用分层评审策略：先高层后细节

**Impact**: 如果未避免，评审浮于表面，大量设计缺陷流到开发阶段才发现，返工成本剧增。

### Pitfall 2: 评审变成"走过场"

**Risk**: 评审流于形式，评审员没有提前阅读文档，会议上临时阅读，无法发现深层问题，最终草草通过评审。

**Prevention**:
- 设计文档必须在评审会议 48 小时前分发
- 评审员需要回复"已阅读"确认
- 设定明确的评审门槛：未提前阅读的评审员不参加会议
- 使用评审检查清单引导系统化评审
- 记录评审中发现的真实问题数量作为评审质量指标

**Impact**: 如果未避免，评审失去质量把关作用，设计问题流入开发阶段，项目后期才暴露，造成大量返工和延误。

### Pitfall 3: 忽视非功能需求评审

**Risk**: 评审只关注功能需求的满足情况（"功能对不对"），忽略了性能、安全、可扩展性等非功能需求的评审（"好不好"）。

**Prevention**:
- 在评审议程中为每个非功能维度分配专门的讨论时间
- 使用质量属性场景来具体化非功能需求
- 将非功能需求的验收标准作为评审检查项
- 引入安全、性能等领域的专家参与评审
- 建立非功能需求评审专项 checklist

**Impact**: 如果未避免，系统上线后出现性能瓶颈、安全隐患、扩展困难等问题，需要付出高昂的改造成本。

### Pitfall 4: 评审意见模糊不具体

**Risk**: 提出"这个设计不够好""可以优化一下"等笼统意见，没有具体的问题描述和改进建议，设计方无法理解要改什么。

**Prevention**:
- 每个问题必须包含：问题描述 + 具体位置 + 改进建议 + 严重程度
- 使用标准格式记录评审意见
- 示例模版："P2 | 订单服务接口缺少幂等性设计 | 第3章第2节 | 建议：在请求中添加 idempotency_key，服务端实现幂等性检查"
- 主持人确保每项意见具体可操作

**Impact**: 如果未避免，设计方收到笼统意见后无处下手，反复沟通确认问题点，浪费大量时间，甚至问题被搁置不理。

### Pitfall 5: 评审结论拖延导致交付阻塞

**Risk**: 评审中发现中等程度的问题后，不给出明确结论而是"等修改完再看"，导致设计一直处于 pending 状态，下游任务被阻塞。

**Prevention**:
- 明确评审结论只有三种：通过 / 有条件通过 / 不通过
- "有条件通过"需要明确列出条件和验收时间
- 设定评审结论的时效（评审结束后 24 小时内公布）
- 建立评审 SLA 跟踪机制
- 对于非关键问题，允许"记录待办，有条件通过"而非等待修复

**Impact**: 如果未避免，评审成为交付瓶颈，团队在等待中浪费时间，交付节奏被打乱。
