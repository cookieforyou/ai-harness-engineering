# System Design Scenario

## Purpose

将需求规格说明书转换为技术架构设计方案，为开发实现提供技术指导。

## Chain of Thought (思维链)

> AI 执行时的思维引导，帮助逐步完成系统设计工作

### Think-Aloud Protocol

```
THINK: 理解需求约束和技术选型
   ↓
THINK: 设计系统架构风格
   ↓
THINK: 划分组件和职责
   ↓
THINK: 设计数据模型和接口
   ↓
THINK: 评估风险和替代方案
   ↓
THINK: 验证设计的可行性和完整性
```

### Step-by-Step Reasoning

**Step 1: 约束分析**
- 问：有哪些技术约束和资源限制？
- 验证：需求对性能、安全、可用性的要求
- 检查：团队技术能力是否匹配

**Step 2: 架构选型**
- 问：哪种架构风格最适合当前需求？
- 验证： monolith vs microservices vs event-driven
- 检查：扩展性、可靠性、成本是否平衡

**Step 3: 组件设计**
- 问：组件边界是否清晰、职责是否单一？
- 验证：组件间的依赖关系是否合理
- 检查：接口设计是否满足需求

**Step 4: 数据设计**
- 问：数据模型是否满足业务需求？
- 验证：读写模式、数据量、一致性要求
- 检查：数据迁移和演化策略

**Step 5: 风险评估**
- 问：有哪些技术风险？如何缓解？
- 验证：风险概率和影响
- 检查：是否有备选方案

## Error Handling (错误处理)

### EH-1: 需求与设计不匹配

- **识别信号**：需求无法通过设计实现
- **处理方式**：
  1. 明确指出不匹配的需求
  2. 分析原因
  3. 提出替代方案
  4. 标记为 `[设计冲突-需确认]`
- **升级条件**：影响核心功能

### EH-2: 技术选型不确定

- **识别信号**：多个技术选项都可接受
- **处理方式**：
  1. 列出各选项优缺点
  2. 根据约束给出建议
  3. 选择并说明理由
- **升级条件**：涉及关键技术决策

### EH-3: 组件边界不清晰

- **识别信号**：组件职责重叠或划分不合理
- **处理方式**：
  1. 重新分析业务边界
  2. 按单一职责原则重新划分
  3. 更新架构图
- **升级条件**：影响多个组件

## Decision Checkpoints (决策检查点)

| 检查点 | 触发条件 | 等待决策 | 下一步 |
|--------|----------|----------|--------|
| **DC-1: 架构选型确认** | 完成架构风格分析后 | 选择哪种架构风格？技术依据？ | 继续组件设计 |
| **DC-2: 技术选型确认** | 完成技术栈分析后 | 技术栈是否合适？团队能力匹配？ | 继续详细设计 |
| **DC-3: 方案评审** | 完成架构设计后 | 方案是否通过技术评审？ | 进入下一阶段 |

### 决策检查点执行规范

```
执行流程:
1. 到达检查点 → 暂停执行
2. 生成决策材料 → 总结要点
3. 等待反馈 → 标注 [待确认]
4. 获取决策 → 继续或修正
5. 记录决策 → 归档到输出文档
```

## Handover Criteria (交接标准)

| 条件项 | 状态 | 说明 |
|--------|------|------|
| 架构设计文档 | ☐ | 完整且评审通过 |

## Workflow

```
1. 启动 → 理解需求规格
2. 架构选型 → 选择架构风格
3. 组件设计 → 划分组件职责
4. 数据设计 → 设计数据模型
5. 接口设计 → 定义接口规范
6. 风险分析 → 识别技术风险
7. 方案评审 → 技术评审通过
8. 完成 → 输出架构设计文档
```
