# 用户故事格式标准

## Overview

本文件定义了 E2E Delivery Harness 体系中用户故事的标准化格式和编写规范。统一的用户故事模板确保需求表达清晰、可测、可追溯，验收标准的 Given-When-Then 格式保证自动化验证能力，INVEST 原则提供故事质量自检框架。

## User Story Template（用户故事模板）

### 标准格式

```
As a <角色>,
I want <功能/能力>,
so that <业务价值>.
```

**字段说明**：

| 字段 | 英文 | 要求 | 示例 |
|------|------|------|------|
| `<角色>` | Role | 真实的用户角色或系统角色；使用业务术语 | `As a 订单管理员` |
| `<功能/能力>` | Feature / Capability | 用户期望的功能描述，使用主动语态 | `I want 批量导出当月订单` |
| `<业务价值>` | Business Value | 可衡量的业务收益，建议引用 MET-* 指标 | `so that 月报准备时间减少 50% (MET-012)` |

### 格式约束

1. 三个从句各占一行，以逗号或句号结束
2. `<角色>` 使用中文业务角色名，如有英文术语须在括号注明
3. `<功能>` 使用主动语态，避免「能够」「可以」等冗余词
4. `<价值>` 应可量化或可观测，避免「更好」「更高效」等无度量描述
5. 每条用户故事必须有唯一编号 `REQ-{NNN}`

### 完整故事结构

```markdown
### REQ-042: 订单支付
**Story**:
As a 买家,
I want 使用微信或支付宝完成支付,
so that 我可以在线完成购买.

**Acceptance Criteria**:
AC-042-1: ...
AC-042-2: ...

**Non-functional Constraints**:
NFR-042-1: ...

**Labels**: payment, checkout, user-facing
**Story Points**: 3 (Fibonacci: 1, 2, 3, 5, 8, 13, 21)
**Dependencies**: REQ-041 (购物车结算)
```

## Acceptance Criteria（验收标准 — Given-When-Then）

### 格式规范

每条验收标准（AC）采用 Gherkin 风格的 Given-When-Then 格式：

```gherkin
AC-{REQ#}-{seq}: {简短标题}
Given {前置条件}    — 场景的初始状态 / 上下文设置
When {动作事件}     — 用户或系统的触发动作
Then {预期结果}     — 可观测、可验证的结果
```

### 子句编写规范

#### Given（前置条件）

| 规范 | 说明 | 示例 |
|------|------|------|
| 使用完成时态或状态描述 | 表示场景开始前的已具备条件 | `Given 购物车已结算且金额 > 0` |
| 可包含多个条件 | 用 `且` / `and` 连接 | `Given 用户已登录 且 商品库存 > 0` |
| 避免逻辑分支 | 一个 AC 只描述一条路径 | 不要写成 `Given A or B` |
| 引用已有数据 | 使用数据编号加速测试 | `Given 订单 ORD-20240601-001 状态为 pending_payment` |

#### When（动作事件）

| 规范 | 说明 | 示例 |
|------|------|------|
| 使用一般现在时主动语态 | 描述触发动作 | `When 用户选择微信支付并点击确认` |
| 单一触发动作 | 一个 When 只描述一个动作 | 不要写成 `When 用户支付 且 系统发送通知` |
| 明确操作主体 | 标明谁执行动作 | `When 审批人点击「通过」按钮` |

#### Then（预期结果）

| 规范 | 说明 | 示例 |
|------|------|------|
| 必须是可观测结果 | HTTP 状态码、DB 记录、UI 元素、消息队列 | `Then 订单状态变为 paid` |
| 必须使用量化描述 | 包含具体值或阈值 | `Then 响应时间 ≤ 200ms` |
| 禁止主观词汇 | 不出现「快速」「友好」「稳定」 | 用 `MET-001 p95 latency ≤ 200ms @ 500 RPS` |
| 可引用指标编号 | 关联 MET-* 指标 | `Then p95 API latency 符合 MET-001` |

### 验收标准数量要求

| 故事复杂度 | 最少 AC 数 | 说明 |
|-----------|-----------|------|
| 简单（1 SP） | 1 | 主路径 |
| 中等（3 SP） | 3 | 主路径 + 1 异常 + 1 边界 |
| 复杂（5+ SP） | 5 | 主路径 + 多异常 + 边界 + 权限 |
| 建议上限 | 8 | 超过 8 个考虑拆分故事 |

### AC 编号规则

```
AC-{REQ#}-{seq}

示例：
REQ-042 的第 1 条验收标准 → AC-042-1
REQ-042 的第 2 条验收标准 → AC-042-2
```

## INVEST Principle Checklist（INVEST 原则检查清单）

每个用户故事在进入迭代前应通过 INVEST 检查：

| 原则 | 英文 | 定义 | 检查问题 | 反例 |
|------|------|------|---------|------|
| **I**ndependent | 独立性 | 故事可独立开发和交付，不依赖其他故事 | 该故事是否不阻塞也不被其他故事阻塞？ | 需要先完成故事 B 才能开始故事 A |
| **N**egotiable | 可协商 | 故事细节可通过讨论达成共识，非契约 | 团队是否可以在实现方式上有协商空间？ | 故事直接指定了技术实现方案 |
| **V**aluable | 有价值 | 故事交付了对用户或业务有明确价值的功能 | 最终用户是否能感知到这个故事的价值？ | 「重构数据库连接池」无用户可见价值 |
| **E**stimable | 可估算 | 团队能合理估算故事工作量 | 团队是否对该故事的工作量有共识估算？ | 故事描述过于模糊无法估算 |
| **S**mall | 小型 | 故事够小，可在单个迭代内完成 | 是否能在 5 个 Story Point 内完成？ | 故事需要 3 个迭代才能完成 |
| **T**estable | 可测试 | 故事有明确的验收标准，可通过测试验证 | 是否有至少 1 条 Given-When-Then 验收标准？ | 「系统应该运行良好」无法验证 |

### INVEST 检查清单表

```
INVEST Checklist for REQ-{NNN}:
- [ ] Independent: 该故事可独立交付，无硬性前置依赖
- [ ] Negotiable: 实现细节未在故事中硬编码
- [ ] Valuable: 业务价值字段描述清晰，用户可感知
- [ ] Estimable: 团队可给出 Story Point 估算
- [ ] Small: ≤ 5 SP，可在单迭代内完成
- [ ] Testable: 至少 1 条可验证的 AC（Given-When-Then）
```

## Story Splitting Techniques（故事拆分技术）

当故事太大（> 5 SP 或 8 条 AC）时，按以下技术拆分：

### 1. Split by Data（按数据维度拆分）

根据数据特征或边界值将大故事拆分为小故事：

```markdown
大故事: As a 管理员, I want 导出报表.

拆分后:
- As a 管理员, I want 导出 CSV 格式报表 (处理标准量数据 ≤ 10000 行)
- As a 管理员, I want 导出 Excel 格式报表 (含格式化)
- As a 管理员, I want 导出超大报表 (数据量 > 10000 行，异步生成)
- As a 管理员, I want 筛选字段后导出定制报表
```

### 2. Split by Operation（按操作维度拆分）

根据 CRUD 或业务流程步骤拆分：

```markdown
大故事: As a 运维, I want 管理用户账户.

拆分后:
- As a 运维, I want 创建新用户账户 (Create)
- As a 运维, I want 查看用户账户列表 (Read / List)
- As a 运维, I want 编辑用户账户信息 (Update)
- As a 运维, I want 停用/删除用户账户 (Delete)
```

### 3. Split by Role（按角色维度拆分）

根据不同的用户角色和权限拆分：

```markdown
大故事: As a 用户, I want 审批工单.

拆分后:
- As a 普通员工, I want 提交审批工单
- As a 部门主管, I want 审批本部门工单
- As a 财务经理, I want 审批涉及预算变动的工单
- As a 系统管理员, I want 查看所有工单的审批状态
```

### 4. Split by Rule（按规则/业务逻辑拆分）

根据业务规则、异常处理路径或边界条件拆分：

```markdown
大故事: As a 用户, I want 申请年假.

拆分后:
- As a 用户, I want 申请年假 (剩余额度充足，标准流程)
- As a 用户, I want 申请年假 (余额不足时提示并阻止提交)
- As a 用户, I want 申请年假 (跨年度时自动拆分)
- As a 用户, I want 申请年假 (与已审批假期冲突时提示)
```

### 拆分决策流程

```
故事太大？
  ├─ 按数据拆分 → 是否有明确的数据边界？(文件格式/数据量/数据类型)
  ├─ 按操作拆分 → 是否包含多个 CRUD 或流程步骤？
  ├─ 按角色拆分 → 涉及多个用户角色或权限等级？
  └─ 按规则拆分 → 有多个业务规则或异常路径？

拆分后每个子故事须满足:
  1. INVEST 全部通过
  2. 至少 1 条 AC
  3. ≤ 5 SP
  4. 子故事之间保留依赖关系标注
```

## Good vs Bad Examples

### 示例 1: 简单功能

| 维度 | Bad（不良） | Good（良好） |
|------|------------|-------------|
| **Story** | `As a 用户, I want 登录系统.` | `As a 注册用户, I want 使用邮箱和密码登录系统, so that 我可以访问个人工作台.` |
| **问题** | 缺少「so that」价值描述；角色不够具体 | 角色具体（注册用户）、动作用邮箱和密码）、价值明确（访问个人工作台） |
| **AC** | 无 | `AC-001-1: Given 用户已注册且邮箱已验证; When 用户输入正确邮箱和密码并点击登录; Then 系统返回 200 且跳转到个人工作台` |

### 示例 2: 权限控制

| 维度 | Bad（不良） | Good（良好） |
|------|------------|-------------|
| **Story** | `As a 管理员, I want 管理权限.` | `As a 系统管理员, I want 为项目角色分配读写权限, so that 成员只能访问其授权范围内的资源.` |
| **问题** | 角色不精确（管理员太泛）；价值不清晰 | 角色精确（系统管理员）；动作为分配读写权限；价值为最小权限原则 |
| **AC** | 无 | `AC-002-1: Given 系统管理员在项目设置页面; When 为「访客」角色取消「删除资源」权限并保存; Then 该角色的所有成员收到 403 当尝试删除资源` |

### 示例 3: 批量操作

| 维度 | Bad（不良） | Good（良好） |
|------|------------|-------------|
| **Story** | `As a 运营, I want 批量处理订单.` | `As a 订单运营专员, I want 按条件筛选订单后批量退款, so that 售后处理效率从每天 50 单提升至 200 单 (MET-015).` |
| **问题** | 无批量范围说明；无验收标准；价值无法衡量 | 角色明确（订单运营专员）；批量前有筛选动作；价值关联量化指标 MET-015 |
| **AC** | 无 | `AC-003-1: Given 订单运营专员筛选了 10 笔「已发货-退款中」订单; When 选择「批量退款」并确认; Then 10 笔订单状态批量更新为 refunded` |

### 示例 4: 非功能需求

| 维度 | Bad（不良） | Good（良好） |
|------|------------|-------------|
| **Story** | `As a 用户, I want 系统响应快.` | `As a 前端用户, I want 页面列表查询响应在 2 秒内, so that 日常操作不中断工作流 (MET-001: p95 < 2000ms @ 100 并发).` |
| **问题** | 「快」无法衡量；无指标引用；无并发说明 | 量化阈值（2 秒 / 2000ms）+ 并发量（100）+ 指标编号（MET-001） |
| **AC** | 无 | `NFR-004-1: Given 100 个并发用户同时发起列表查询; When 系统处理所有请求; Then p95 响应时间 ≤ 2000ms (引用 MET-001)` |

### 示例 5: 复杂业务规则

| 维度 | Bad（不良） | Good（良好） |
|------|------------|-------------|
| **Story** | `As a 财务, I want 处理报销, so that 员工能收到钱.` | `As a 财务审核员, I want 按公司差旅政策自动审批标准报销单, so that 报销周期从 7 天缩短至 2 天 (MET-023).` |
| **问题** | 太粗（一个故事覆盖整个流程）；角色泛；价值空泛 | 范围聚焦（标准报销单自动审批）；角色精确（财务审核员）；价值量化（报销周期 MET-023） |
| **AC** | 无 | `AC-005-1: Given 员工提交差旅报销单且所有项目在政策允许范围内; When 系统执行自动审核; Then 报销单状态变为 approved_pending_payment` |
| | | `AC-005-2: Given 员工提交差旅报销单但住宿费超出标准 50%; When 系统执行自动审核; Then 报销单状态变为 pending_manual_review 且触发通知` |
| | | `AC-005-3: Given 员工提交的报销单包含未在差旅政策中定义的费用类型; When 系统执行自动审核; Then 报销单状态变为 pending_clarification 且要求补充说明` |

## Definition of Ready（就绪定义检查表）

故事进入 Sprint 或迭代前，须通过以下 DoR 检查：

### 必备检查项

- [ ] DoR-001: 故事有唯一编号（REQ-{NNN}）
- [ ] DoR-002: 三个从句完整（As a / I want / so that）
- [ ] DoR-003: 业务价值明确且可衡量
- [ ] DoR-004: 至少 1 条 Given-When-Then 验收标准
- [ ] DoR-005: 验收标准全部可测试（有量化结果）
- [ ] DoR-006: INVEST 六项全部通过
- [ ] DoR-007: Story Point 已估算（1/2/3/5/8/13/21）
- [ ] DoR-008: 无主观词（如「快速」「友好」「稳定」）
- [ ] DoR-009: 已知前置依赖已标注
- [ ] DoR-010: 非功能约束已记录（如适用）

### 建议检查项

- [ ] DoR-011: 验收标准覆盖主路径 + 至少 1 条异常路径
- [ ] DoR-012: 验收标准引用了 MET-* 指标（如适用）
- [ ] DoR-013: UI 设计稿或原型已准备（如适用）
- [ ] DoR-014: 故事大小 ≤ 5 SP（否则已拆分）
- [ ] DoR-015: 验收标准可在自动化测试框架中执行

### DoR 通过规则

- **必须**: 10 项必备检查项全部通过
- **非必须**: 建议检查项鼓励通过，但允许缺失（记录原因）
- **否决**: 任何必备项不通过 → 故事退回产品待办列表（Backlog）

## Compliance Checklist

- [ ] 用户故事格式为完整的 `As a / I want / so that` 三从句
- [ ] 角色使用具体业务角色名（非泛称「用户」）
- [ ] 验收标准使用 Given-When-Then 格式
- [ ] Then 子句可观测、可验证、可量化
- [ ] 每条 AC 有唯一编号（AC-{REQ#}-{seq}）
- [ ] 故事通过 INVEST 全部 6 项检查
- [ ] 故事 ≤ 5 SP（否则已按规范拆分）
- [ ] 拆分技术明确标注（按数据/操作/角色/规则）
- [ ] 无主观词（「快速」「友好」「稳定」等）
- [ ] 已关联指标编号（MET-*）和依赖编号（REQ-*）
