# 缺陷分类标准

## Overview (概述)

本标准旨在规范所有项目团队的缺陷分类流程，确保缺陷严重级别 (Severity) 的分配、优先级 (Priority) 的处理以及缺陷生命周期管理在全组织范围内保持一致。本标准适用于开发工程师、质量保障 (QA)、项目经理 (PM) 及运维 (Ops) 人员。通过统一的定义和可操作的检查清单，降低因分类不一致导致的沟通成本，提升缺陷修复效率和产品质量可预测性。

## Core Content (核心内容)

### 缺陷严重级别 (P0-P4) 详细定义

| 级别 | 标签 | 定义 | 响应时间 | 处理原则 | 典型示例 |
|------|------|------|---------|---------|---------|
| P0 | Critical | 核心功能不可用、数据丢失、安全漏洞 | 15分钟 | 立即修复/回滚 | 登录崩溃、数据库损坏、XSS漏洞 |
| P1 | High | 重要功能受损、SLO突破阈值 | 2小时 | 优先处理 | 支付失败、核心API报错 |
| P2 | Medium | 非核心功能受影响、有Workaround | 24小时 | 排入迭代修复 | 非核心页面样式错乱 |
| P3 | Low | 小问题、优化建议 | 下一迭代 | 排入Backlog | UI文字错位、日志级别不当 |
| P4 | Info | 观察项、趋势跟踪 | 无需处理 | 记录跟踪 | 性能轻微退化、技术债务 |

**P0 处理细则**：P0 缺陷触发紧急响应流程，需立即通知 On-Call 工程师并建立临时修复群组。修复后须在 24 小时内完成根因分析 (RCA) 报告并归档。在此期间，所有非紧急发布活动暂停。

**P1 处理细则**：P1 缺陷应在响应时间内评估影响并分配修复资源。如 2 小时内无法完成修复，需升级至技术负责人决策是否回滚或暂缓发布。修复完成后需在迭代内完成 RCA。

### 优先级 vs 严重性矩阵 (Priority vs Severity Matrix)

| | P0 严重 | P1 严重 | P2 严重 | P3 严重 |
|---|---|---|---|---|
| **P-high** | 立即修复 | 紧急修复 | 快速修复 | 常规 |
| **P-medium** | 紧急修复 | 快速修复 | 常规 | 低优先 |
| **P-low** | 快速修复 | 常规 | 低优先 | Backlog |

**解释**：
- **严重性 (Severity)** 衡量缺陷的技术影响程度——系统崩溃、数据丢失、功能失效、界面瑕疵等，由 QA 或技术负责人评估。
- **优先级 (Priority)** 衡量业务紧迫程度——用户面影响面、发布阻塞、客户投诉、合规要求等，由 PM 或产品负责人评估。
- **示例**：首页的一个文字拼写错误，技术上是 P3 严重（界面小问题），但如果该页面是正在进行的市场营销活动入口，业务优先级应为 P-high，需要在活动开始前快速修复。同理，一个冷门管理后台的功能完全不可用可能是 P0 严重但 P-low 优先，因为影响用户数为零且目前无业务诉求。

### 缺陷生命周期状态流转

缺陷从发现到关闭经历明确的状态变更，每种状态变更需记录操作人和时间戳。

**正常修复路径**：
```
New → Triaged → Assigned → In Progress → Fixed → Verified → Closed
```

**关闭路径（无需修复）**：
```
New → Triaged → Won't Fix / Duplicate / Not Reproducible → Closed
```

**回归路径**：
```
Verified → Reopened → In Progress → Fixed → Verified → Closed
```

**各状态定义**：

| 状态 | 定义 | 负责人 |
|------|------|--------|
| New | 缺陷已提交，等待确认 | 报告人 |
| Triaged | 已确认，已分配合适的严重级别和优先级 | QA/Tech Lead |
| Assigned | 已指定修复责任人 | PM/Tech Lead |
| In Progress | 正在排查和修复中 | 开发工程师 |
| Fixed | 修复已完成，代码已合入，等待验证 | 开发工程师 |
| Verified | 验证通过，确认修复正确 | QA |
| Reopened | 验证不通过，或问题在生产环境复现 | QA |
| Closed | 缺陷处理终结 | QA/Tech Lead |
| Won't Fix | 经评估决定不修复（需注明原因） | Tech Lead |
| Duplicate | 与存量缺陷 ID #xxx 重复 | QA/Tech Lead |
| Not Reproducible | 按报告步骤无法复现（需注明尝试方式） | QA/Tech Lead |

**状态流转规则**：
- New → Triaged 须在缺陷提交后 1 个工作日内完成（P0/P1 在响应时间内完成）。
- Fixed → Verified 须在修复合入后 2 个工作日内完成测试验证。
- Verified → Closed 确认无回归问题后关闭。P0/P1 缺陷需 Tech Lead 或以上角色审批后方可关闭。
- 任何状态变更均须在缺陷管理系统中添加备注说明原因。

### 缺陷报告必填字段

提交缺陷报告时，以下字段为必填项，缺少任一字段的缺陷报告将被退回补充：

```
- 标题: [模块名] 简洁描述缺陷现象（例如 "[支付] 支付宝扫码支付回调后页面白屏"）
- 环境: 生产/预发布/测试 + 浏览器/设备/版本号（例如 "生产环境 / Chrome 120 / macOS 14.2"）
- 严重级别: P0 / P1 / P2 / P3 / P4
- 优先级: High / Medium / Low
- 重现步骤: 1. 2. 3. ...（精确到每次操作，确保可独立复现）
- 实际结果: 当前系统表现的客观描述
- 期望结果: 系统应表现的正确行为描述
- 附件: 截图 / 日志 / 录屏 / 接口请求响应（P0/P1 缺陷必须提供）
- 影响范围: 影响的用户量级 / 功能模块数 / 是否阻塞发布
```

**字段填写规范**：
- **标题**：不超过 80 字符，采用 `[模块] 现象` 格式。避免使用模糊表述（如"系统报错"、"页面打不开"）。
- **环境**：区分生产/预发布/测试三套环境。浏览器需精确到主版本号，移动端需注明设备型号和 OS 版本。
- **重现步骤**：使用编号列表，每一步描述一个原子操作。必须从空白/初始状态开始描述。避免跳过中间步骤。
- **影响范围**：P0/P1 缺陷需估计影响用户数（绝对数量或百分比），并说明是否阻塞版本发布。

### 缺陷报告注意事项

- **一个缺陷一个报告**：不要将多个独立的缺陷合并写入同一个报告。如果发现相互关联的多个问题，应分别提交并标注关联关系。
- **重现步骤必须精确可重现**：提交前至少按步骤完整复现一遍。如果无法稳定复现，应在标题或描述中标注"偶现"及出现频率。
- **P0/P1 必须附加环境日志和截图**：P0/P1 缺陷报告必须在附件中包含环境日志（应用日志、浏览器 DevTools Console 输出或网络请求记录）、截图或录屏。缺乏附件的 P0/P1 报告将被退回要求补充。
- **避免主观判断**：描述实际结果和期望结果时使用客观语言，避免"我觉得"、"应该是"等主观表述。例如"用户点击提交按钮后页面无响应，持续显示 loading 超过 30 秒"优于"系统好像卡住了"。
- **标注重复关系**：提交前搜索是否已有相似缺陷。如果确实重复，在标题或描述中引用原始缺陷 ID，不要重复提交。

## Examples (示例)

### 优秀缺陷报告示例

```
标题: [支付] 支付宝扫码支付回调后页面白屏

环境: 生产环境 / Chrome 120.0.6099.109 / macOS 14.2.1

严重级别: P1
优先级: High

重现步骤:
1. 在商品详情页选择商品 A (SKU: PRD-001)，点击"立即购买"
2. 在收银台页面选择"支付宝支付"
3. 使用支付宝 App 扫码完成支付
4. 浏览器自动跳转回订单确认页
5. 观察页面行为

实际结果: 步骤 4 跳转后浏览器标签页标题显示为"订单确认"，但页面内容区域为纯白色，无任何 UI 元素渲染。Chrome DevTools 控制台无报错，Network 面板显示 order/confirm 接口返回 200 且响应体完整（见附件截图）。页面刷新后恢复正常，显示已支付成功状态。

期望结果: 支付宝回调跳转后正常展示订单确认页，显示"支付成功"状态和订单详情信息。

附件: chrome-console-screenshot.png、network-response-order-confirm.json、screen-recording.mp4

影响范围: 影响所有使用支付宝支付的已登录用户，约占总支付用户的 35%。阻塞 v3.2.1 版本发布。
```

### 不合格缺陷报告示例（存在多个问题）

```
标题: 系统出错了
环境: 生产
严重级别: P3
优先级: Low

重现步骤: 点了按钮然后报错。

实际结果: 报错。
期望结果: 不报错。
```

**该报告的问题清单**：
1. 标题过于模糊，缺少模块前缀和具体现象描述。
2. 环境信息不完整，未指定浏览器和设备。
3. 重现步骤无法复现——"点了按钮"未指定哪个页面的哪个按钮。
4. 实际结果和期望结果过于笼统。"报错"无法判断是接口 500、前端异常还是业务提示。
5. 严重级别应为 P1（支付功能受损），误评为 P3。
6. 缺少附件（日志/截图）。
7. 缺少影响范围评估。

## Compliance Checklist (合规检查清单)

每个缺陷在提交、评审和关闭环节应使用以下清单进行合规检查：

- [ ] 缺陷严重级别是否与影响范围匹配？
- [ ] 优先级是否同时考虑了严重性和业务价值？
- [ ] 缺陷报告的 8 个必填字段是否完整？
- [ ] 标题是否包含模块前缀和具体描述？
- [ ] 重现步骤是否精确可执行？
- [ ] P0/P1 缺陷是否附加了日志或截图？
- [ ] 缺陷关闭前是否经过验证确认？
- [ ] 重复缺陷是否已标注关联关系？

**使用方式**：
- **提交环节**：缺陷报告人自查前 5 项。
- **Triaged 环节**：QA/Tech Lead 检查全部 8 项，不通过的退回补充。
- **关闭环节**：QA/Tech Lead 检查第 7-8 项，确认验证通过且无重复或重复关系已标注。
