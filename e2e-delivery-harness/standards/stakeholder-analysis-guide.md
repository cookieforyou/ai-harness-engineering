# 干系人分析指南标准

## Overview

**目的**: 标准化项目全生命周期中的干系人识别、分析、参与和沟通管理流程，确保所有干系人被正确识别、分类和有效管理，最小化项目风险，最大化支持度。

**范围**: 适用于所有需要干系人管理的项目阶段，包括但不限于项目启动、需求收集、方案设计、实施部署和收尾交接。项目经理、产品负责人和技术负责人应在本标准指导下完成干系人分析。

**相关性**: 干系人管理是项目成功的关键因素。本指南确保所有声音被倾听、管理得当，并转化为可执行的沟通策略与行动计划，避免因干系人遗漏或管理不当导致的项目延误、范围蔓延或交付失败。

## Core Content

### 干系人识别方法

干系人识别应在项目启动阶段完成，并在关键里程碑进行更新。以下方法应组合使用以确保全面覆盖：

| 方法 | 描述 | 最佳时机 | 产出物 |
|------|------|----------|--------|
| 头脑风暴 | 项目团队共同识别所有受影响或对项目有影响的个人/组织 | 项目启动会 | 干系人初稿清单 |
| 组织架构图分析 | 审查组织结构图，识别所有可能受影响的部门、层级和职能 | 项目启动阶段 | 部门级干系人清单 |
| 访谈 | 向已知干系人提问"还有谁应该参与？"，滚雪球式扩展 | 初步识别后 | 扩展干系人列表 |
| 文档分析 | 审查项目章程、历史项目文档、组织图表、合同文件 | 项目启动阶段 | 历史干系人记录 |

**分类维度**:
- **Internal vs External**: 内部干系人（团队成员、部门同事）与外部干系人（客户、供应商、监管机构）
- **Direct vs Indirect**: 直接干系人（直接影响或受影响的个人）与间接干系人（通过其他途径受影响的群体）
- **Supporters vs Detractors**: 支持者（积极推动项目）与抵制者（对项目持怀疑或反对态度）

**识别清单**:
- 项目发起人、产品负责人是否已确认？
- 所有受影响的业务部门是否已纳入？
- 最终用户代表是否已确定？
- 技术团队（开发、测试、运维）是否已纳入？
- 合规、法务、安全等监管角色是否已识别？
- 供应商或第三方合作伙伴是否已考虑？

### 四类关键角色（必须覆盖）

每类项目必须识别并覆盖以下四个关键角色类型。缺少任一类型均视为干系人分析不完整。

| 类型 | 英文 | 说明 | 示例 | 如何识别 |
|------|------|------|------|----------|
| 决策者 | Decision Maker | 预算、范围、优先级拍板 | 产品总监、发起人、CTO | 谁有权批准变更、分配资源、确认范围？ |
| 使用者 | User | 直接操作系统/产品的人 | 终端用户、运营团队 | 项目交付物最终由谁日常使用？ |
| 影响者 | Influencer | 无决策权但影响方案 | 架构师、合规、技术顾问 | 谁的意见会影响决策但无权最终批准？ |
| 监管者 | Regulator | 合规、审计、法务 | 安全团队、法务、审计 | 哪些角色有审批/合规审核的职责？ |

**角色识别注意事项**:
- 一个人可能同时承担多个角色（例如架构师既是影响者也可能参与决策），应在分析中标注主要角色
- 角色可能在项目不同阶段发生变化，建议在每个里程碑重新审视
- 如果某一角色类型不明，应通过访谈项目发起人或现有干系人进一步确认

### 干系人矩阵（Power vs Interest）

干系人矩阵将干系人按"影响力（Power）"和"利益相关度（Interest）"两个维度分类，帮助制定差异化的沟通和管理策略。

| 利益相关度 \ 影响力 | 低 | 高 |
||---|---|---|
| **高** | **Keep Satisfied（随时告知）** <br>策略：确保需求被满足，主动提供透明信息 <br>沟通频率：每月或里程碑 | **Manage Closely（密切合作）** <br>策略：深度参与决策，持续沟通对齐 <br>沟通频率：每周或更频繁 |
| **低** | **Monitor（最低关注）** <br>策略：定期检查无重大变化即可 <br>沟通频率：每季度或按需 | **Keep Informed（满足期望）** <br>策略：保持信息透明，避免意外 <br>沟通频率：每月或里程碑 |

**Power 评估标准**（H / M / L）:
| 等级 | 描述 |
|------|------|
| H | 拥有资源分配、项目终止、重大变更批准权 |
| M | 拥有部分决策权或对决策有显著影响力 |
| L | 对项目决策几乎没有直接影响 |

**Interest 评估标准**（H / M / L）:
| 等级 | 描述 |
|------|------|
| H | 项目结果直接影响其日常工作或核心利益 |
| M | 项目结果间接影响其工作或有一定利益关系 |
| L | 项目结果对其工作几乎没有影响 |

**模板使用说明**: 用以下表格记录评估结果，每个干系人一行。

| 干系人 | 角色 | 影响力 (H/M/L) | 利益相关度 (H/M/L) | 象限 | 策略 | 沟通频率 | 沟通渠道 |
|--------|------|----------------|--------------------|------|------|----------|----------|
| {name} | Decision Maker | H | H | manage-closely | 密切合作 | 每周 | 周会、日报 |
| {name} | Regulator | H | L | keep-satisfied | 满足期望 | 里程碑 | 评审会 |
| {name} | User | L | H | keep-informed | 随时告知 | 双周 | 邮件、workshop |
| {name} | Influencer | L | L | monitor | 最低关注 | 按需 | 邮件 |

### RACI 矩阵模板

RACI 矩阵定义了关键活动中的角色和责任，确保责任无遗漏、无重叠。

**图例**:
- **R** = Responsible（执行者）: 实际完成工作的人
- **A** = Accountable（问责人）: 对结果负责，每项活动必须有且仅有一个 A
- **C** = Consulted（咨询者）: 提供意见和输入的人，双向沟通
- **I** = Informed（被告知者）: 需要知晓结果的人，单向沟通

| 活动/决策 | PM | Dev Lead | QA | Product Owner | Ops |
|-----------|----|----------|-----|---------------|-----|
| 需求定义 | A | C | I | R | I |
| 技术设计 | I | R | C | A | C |
| 代码评审 | I | R | C | I | - |
| 测试执行 | I | C | R | A | I |
| 部署上线 | I | C | I | A | R |
| 用户验收 | A | I | C | R | - |
| 项目复盘 | R | C | I | A | I |

**RACI 编制原则**:
1. 每项活动有且仅有一个 **A**（Accountable），问责权不可共享
2. **R** 可以有多人共同执行
3. 避免过多的 **C**，仅对确实需要双向输入的角色标记为 C
4. 避免过多的 **I**，仅对确实需要知情的角色标记为 I
5. 如果某个角色在某活动中不参与，标注 `-`，不要让格子空着（歧义）

**RACI 与干系人矩阵的联动**: RACI 中的 A 角色通常对应干系人矩阵中的高影响力干系人（manage-closely 或 keep-satisfied），因为问责人需要对结果负责。

### 沟通计划模板

沟通计划是干系人管理的核心执行文档，确保信息在正确的时间以正确的形式传达给正确的人。

```yaml
communication_plan:
  - name: "{name}"
    role: "{role}"
    stakeholder_type: Decision Maker|User|Influencer|Regulator
    power_interest_quadrant: manage-closely|keep-satisfied|keep-informed|monitor
    frequency: daily|weekly|biweekly|monthly|per-milestone|ad-hoc
    channel: daily-standup|sprint-review|email|workshop|slack|status-report
    format: presentation|document|dashboard|verbal
    content: [项目进度|风险|决策事项|技术方案|验收结果]
    key_concerns: []
    escalation_path: "{直接升级联系人}"
```

**字段说明**:

| 字段 | 说明 | 必填 |
|------|------|------|
| name | 干系人姓名 | 是 |
| role | 在项目中的角色 | 是 |
| stakeholder_type | 四类角色类型之一 | 是 |
| power_interest_quadrant | 干系人矩阵象限 | 是 |
| frequency | 沟通频率 | 是 |
| channel | 沟通渠道 | 是 |
| format | 信息呈现形式 | 是 |
| content | 沟通内容范围，至少选择一项 | 是 |
| key_concerns | 该干系人关注的特定问题列表 | 否 |
| escalation_path | 当需要升级问题时的联系人 | 否 |

**沟通计划与干系人矩阵的映射**:

| 象限 | 推荐频率 | 推荐渠道 | 推荐内容 |
|------|----------|----------|----------|
| manage-closely | 每周/每日 | 周会、日报、Slack | 项目进度、风险、决策事项 |
| keep-satisfied | 每月/里程碑 | 评审会、邮件 | 验收结果、重大变更 |
| keep-informed | 双周/每月 | 邮件、dashboard | 项目进展、里程碑通知 |
| monitor | 每季度/按需 | 邮件 | 重大里程碑、最终交付 |

### 冲突处理流程

干系人之间的冲突是项目过程中的常态，标准化的冲突处理流程可确保冲突得到建设性解决。

**流程步骤**:

1. **记录冲突双方诉求与背后的 OBJ-***
   - 记录冲突双方名称、角色
   - 记录各方核心诉求
   - 关联对应的项目目标（OBJ-*）
   - 记录冲突背景和上下文

2. **为每方提供至少 2 个折中方案**（DC-003）
   - 方案必须体现双方核心诉求的平衡
   - 每个方案需注明利弊和影响
   - 方案需与项目目标对齐

3. **2 轮协商无果 → 升级决策者**
   - 第一轮协商：项目经理/产品负责人主持
   - 第二轮协商：尝试不同方案组合
   - 升级：将双方方案、分析报告提交至有权决策者

**冲突文档模板**:

```yaml
conflict_record:
  id: CONF-{序号}
  date: "{日期}"
  parties:
    - name: "{干系人A}"
      role: "{角色}"
     诉求: ["{诉求1}", "{诉求2}"]
    - name: "{干系人B}"
      role: "{角色}"
     诉求: ["{诉求1}", "{诉求2}"]
  related_objectives: ["OBJ-{序号}"]
  proposed_solutions:
    -方案1: "{描述}"
    -方案2: "{描述}"
 协商轮次: 1
  status: pending|resolved|escalated
```

**升级标准**:
| 条件 | 升级目标 |
|------|----------|
| 影响项目关键路径或交付时间 | 项目发起人 |
| 涉及预算或资源变更 | 项目发起人 / PMO |
| 涉及合规、安全、法务问题 | 法务 / 安全负责人 |
| 双方团队无法达成一致 | 产品负责人 / CTO |

### 干系人注册表（Stakeholder Register）字段

干系人注册表是干系人管理的统一数据源，以下字段应作为最低标准纳入:

| 字段 | 说明 | 示例 | 必填 |
|------|------|------|------|
| ID | 唯一标识 | SH-001 | 是 |
| Name | 姓名 | 张三 | 是 |
| Organization | 所属组织/部门 | 产品部 | 是 |
| Role | 项目角色 | Product Owner | 是 |
| Contact | 联系方式 | zhang.san@company.com | 是 |
| Stakeholder Type | 干系人类型 | Decision Maker | 是 |
| Power (H/M/L) | 影响力等级 | H | 是 |
| Interest (H/M/L) | 利益相关度等级 | H | 是 |
| Influence Strategy | 影响策略 | manage-closely | 是 |
| Engagement Level | 当前参与度（unaware/resistant/neutral/supportive/leading） | supportive | 是 |
| Notes | 备注 | 关注预算和 timeline | 否 |

## Examples

### 示例一（良好实践）: 完整的干系人分析

**项目**: 某电商平台支付系统升级

1. **干系人识别清单**:覆盖了全部四类角色（产品VP为Decision Maker，运营团队为User，技术架构师为Influencer，安全团队为Regulator），并通过访谈扩展了供应商联系人。

2. **干系人矩阵**:
   | 干系人 | Power | Interest | 象限 | 策略 |
   |--------|-------|----------|------|------|
   | 产品VP | H | H | manage-closely | 每周汇报进度和风险 |
   | 安全团队 | H | L | keep-satisfied | 评审方案，确保合规 |
   | 运营团队 | L | H | keep-informed | 双周沟通了解影响 |
   | 技术架构师 | L | L | monitor | 按需邮件 |

3. **RACI 矩阵**: 为需求定义、技术设计、测试、部署等关键活动分配了清晰的 R/A/C/I。

4. **沟通计划**: 每个干系人的频率、渠道、内容和格式均明确配置，与矩阵策略对齐。

5. **冲突处理**: 记录了一次运营团队与技术团队的就迁移时间窗口的冲突，提供了2个折中方案，经过1轮协商达成一致。

**结果**: 项目按时交付，所有干系人满意度达标，无升级事件。

### 示例二（不良实践）: 不完整分析导致的项目风险

**项目**: 某内部 HR 系统替换

**问题**:
- 仅识别了项目发起人和技术团队，未识别法务（Regulator）和最终用户（User）
- 缺乏 Power vs Interest 矩阵，所有干系人同样对待，无差异化策略
- 无 RACI 矩阵，导致部署上线时运维团队未被告知
- 沟通计划仅包含邮件，未根据干系人类型配置渠道和频率
- 冲突发生时无处理流程，导致两次升级到项目发起人

**后果**: 项目延误2周，法务合规审核重新返工，用户培训时间不足导致上线后大量工单。

## Compliance Checklist

```
- [ ] 是否覆盖了四类关键角色（决策者/使用者/影响者/监管者）？
- [ ] 是否绘制了 Power vs Interest 矩阵并为每个象限制定了策略？
- [ ] 是否为每个关键活动定义了 RACI 矩阵（每行一个 A）？
- [ ] 沟通计划是否包含频率、渠道和内容三要素？
- [ ] 是否有冲突升级路径和协商流程（提供至少 2 个方案）？
- [ ] 干系人注册表是否包含所有必要字段（ID/Name/Role/Power/Interest/Strategy）？
- [ ] 产出物 `docs/stakeholder-analysis.md` 是否已生成并纳入版本管理？
- [ ] Handover 的 `confirmed_stakeholder_needs` 字段是否已填充？
```

## Key Metrics (关键指标)

| 指标 | 目标值 | 测量方法 |
|------|--------|----------|
| 干系人识别覆盖率 | 100% | 项目启动阶段覆盖全部四类关键角色（决策者/使用者/影响者/监管者），缺一不可 |
| RACI 责任完整性 | 100% | 每项关键活动有且仅有一个 A（问责人），无空白 RACI 单元格 |
| 冲突升级率 | ≤ 20% | 2 轮协商内解决冲突的比例，超过该阈值需审查沟通计划有效性 |
