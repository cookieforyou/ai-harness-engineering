# 应急响应标准

## Overview

生产环境的突发事件可能对用户、数据和业务连续性造成严重影响。本标准定义了统一的应急响应框架，确保在故障发生时团队能够快速响应、有序协作、有效恢复，并从中汲取经验。

**目的**：建立覆盖事件生命周期（发现 -> 响应 -> 恢复 -> 复盘）的标准化流程，降低 MTTR（平均恢复时间），防止事件升级。

**适用范围**：所有级别（P0 / P1 / P2）的生产环境突发事件。

**适用对象**：值班工程师（On-Call IC）、SRE、研发负责人、项目经理及应急指挥官（Incident Commander）。

## 核心内容

### 应急响应 SLA

| 级别 | 定义 | 响应时间 | 通报时间 | 恢复目标(MTTR) | 更新频率 |
|------|------|---------|---------|---------------|---------|
| P0 | 核心功能完全不可用 / 数据丢失 / 安全事件 | ≤5 分钟 | 15 分钟 | ≤1 小时 | 每 30 分钟 |
| P1 | 重要功能受损 / 大量用户受影响 | ≤15 分钟 | 30 分钟 | ≤4 小时 | 每 60 分钟 |
| P2 | 非核心功能异常 / 小范围用户受影响 | ≤1 小时 | 2 小时 | ≤24 小时 | 每日 |

**说明**：
- **响应时间**：从告警触发或事件被确认到第一人介入处理之间的时间窗口。
- **通报时间**：从事件确认到通知相关干系人（管理层、客户支持、受影响团队）之间的时间窗口。
- **恢复目标**：服务恢复至可接受运行状态的目标时间（MTTR），包含临时止血措施。
- **更新频率**：更新沟通状态的最低频率要求。

### 升级路径 (Escalation Path)

```
P0: On-Call IC ──→ Incident Commander(IC) ──→ 技术负责人(Tech Lead) ──→ 工程总监
     (≤5 min)         (≤15 min)                   (≤30 min)                (≤60 min)

P1: On-Call IC ──→ Tech Lead ──→ 项目经理
     (≤15 min)        (≤30 min)     (≤60 min，可选)

P2: On-Call IC ──→ Tech Lead
     (≤1 hr)          (按需，不升级到管理层)
```

**升级条件与各步骤定义**：

1. **On-Call IC -> Incident Commander（P0）**：事件确认为 P0 后，第一响应人自动承担 IC 角色；若 5 分钟内未能控制局面或主动要求交接，即时向更高级别 IC 升级。
2. **IC -> Tech Lead（P0/P1）**：当问题原因超出 IC 技术判断范围，或 15 分钟（P0）/ 30 分钟（P1）内未定位根因，升级至 Tech Lead 介入排查。
3. **Tech Lead -> 工程总监（P0）**：当事件导致业务重大损失、跨团队协调受阻、或 MTTR 已超 SLA 上限，升级至工程总监进行资源调配和业务决策。
4. **Tech Lead -> 项目经理（P1）**：当事件对用户侧交付承诺产生影响，需项目经理介入客户沟通和进度协调时触发的可选升级。

**预期响应时间**：每一级升级后的目标响应时间与对应级别 SLA 响应时间一致。

### 应急角色定义

| 角色 | 缩写 | 职责 | P0 要求 | P1/P2 要求 |
|------|------|------|---------|------------|
| Incident Commander | IC | 全局把控事件处理，协调资源，做战术决策，管理时间线。第一响应人在确认事件后自动承担该角色，可后续交接。 | 专职，不可兼任 | 可与 TL 重合 |
| Tech Lead | TL | 主导技术排查，指挥故障定位方向，提出修复方案并推动实施。向 IC 汇报技术状态。 | 专职，不可兼任 | 可与 IC 重合 |
| Communications Lead | Comms | 管理干系人通报，编写状态报告，维护对外沟通模板的更新与发布。处理外部问题升级。 | 专职，不可兼任 | 可由 Scribe 兼任 |
| Scribe | — | 实时记录所有操作、关键决策、排查路径和时间节点，维护事件时间线，确保事后复盘有据可查。 | 必须 | 建议设置 |

> **注**：P1 / P2 事件允许一人承担多个角色（IC + TL 或 Comms + Scribe）。P0 事件要求四个角色至少由两人或以上担任，IC 和 TL 必须分离。

### 战时沟通模板

**内部沟通模板（Slack / 钉钉频道）**：

```
## Incident Update #{N}
- 时间: {ISO8601}
- 严重级别: P0/P1
- 状态: Investigating / Mitigating / Resolved / Monitoring
- 影响范围: {受影响的服务/用户/功能}
- 当前操作: {正在采取的行动}
- 下个更新: {预计时间}
```

**对外沟通模板（Status Page / 客户通知）**：

```
[{时间}] {受影响系统} - {状态}
我们已意识到{问题描述}，正在积极排查。
- 影响：{用户可见影响}
- 预计修复时间：{ETA or TBD}
```

**沟通原则**：
- 内部沟通按 SLA 更新频率严格执行。
- 对外沟通由 Comms 统一发布，IC 审核，禁止其他成员自行对外披露。
- 状态变化（Investigating -> Mitigating -> Resolved -> Monitoring）应立即发布一次更新。

### 事后复盘 (Postmortem) 触发条件

- **P0 事件**：强制要求进行事后复盘，无论恢复时间长短。
- **P1 事件**：满足以下任一条件时必须复盘：
  - MTTR > 4 小时（超出 SLA）
  - 有数据丢失（含部分丢失或损坏）
  - 同类型事件在 30 天内重复发生
  - 有用户投诉升级或客户 SLA 违约
- **P2 事件**：选择性复盘，由团队负责人根据影响判断是否开展。

**Postmortem 模板要素**：

```
- 标题: [事件日期] [事件标题]
- 概述: 事件摘要（一句话概括）
- 时间线: 关键时间节点（发现 -> 响应 -> 定位 -> 恢复 -> 完成）
- 根因分析: 使用 5 Whys 或 Fishbone 方法分析
- 影响评估: 用户影响 / 数据影响 / 财务影响（量化）
- 行动项: Owner + Deadline（每项必须明确）
- 预防措施: 如何从系统层面避免再次发生
```

**复盘时间要求**：P0 复盘在事件恢复后 5 个工作日内完成；P1 复盘在 10 个工作日内完成。

### 战时原则

1. **安全优先**：先止血，后排查。恢复服务是第一优先级。不可在故障中尝试探查根因而延误恢复。
2. **沟通通道**：P0/P1 事件确认后 5 分钟内建立专属沟通频道（Slack 频道或钉钉群）。频道内包含所有相关干系人。
3. **操作记录**：Scribe 实时记录所有排查操作、配置变更、命令执行和决策理由。禁止依赖口头沟通或事后回忆。
4. **变更管理**：恢复期间的紧急变更仍需在变更管理系统（或频道内）记录完整操作内容，事后 24 小时内补办审批流程。
5. **决策记录**：所有战术决策（回滚、降级、扩缩容、切换路由）必须由 IC 发布明确指令，Scribe 记录决策人和决策时间。
6. **禁止单兵作战**：即使 IC 自认可以独立解决，P0 事件也必须至少召集一名搭档（TL 或 Scribe）。

## 示例

### 良好实践示例

某 P0 事件（支付核心服务宕机）：
- On-Call IC 在告警后 2 分钟内响应，确认 P0 并建立专属频道，15 秒内声明担任 IC 角色。
- IC 指定 Scribe 开始记录，通知 Comms 撰写首次对外公告。
- TL 入场后 20 分钟定位为数据库连接池耗尽，IC 决策立即扩容并重启连接池。
- 恢复时间 40 分钟（≤SLA 1 小时），Comms 每 25 分钟更新一次状态页。
- 复盘在 3 个工作日内完成，输出 5 项行动项，每项有 Owner 和 Deadline。
- 事后通过限流配置和连接池告警从根本上预防复现。

### 不良实践示例

某 P1 事件（商品搜索服务延迟）：
- On-Call 工程师未确认级别，个人排查 40 分钟未升级。
- 没有建立专属沟通频道，多个团队通过私信零散沟通，信息分裂。
- 没有 Scribe，事后复盘时关键操作时间无法还原。
- 没有进行干系人通报，用户侧投诉升级后管理层才得知问题。
- MTTR 达 5 小时超出 SLA，但团队未触发复盘流程。
- 两周后同类事件再次发生，根因相同但未采取预防措施。

### 示例对比总结

| 维度 | 良好实践 | 不良实践 |
|------|---------|---------|
| 响应 | 2 分钟内确认并声明角色 | 未定义角色，个人排查 40 分钟无升级 |
| 沟通 | 专属频道 + 定期通报 | 零散私信，无干系人更新 |
| 记录 | Scribe 实时记录 | 无记录，依赖记忆 |
| 恢复 | 40 分钟恢复，≤SLA | 5 小时恢复，超出 SLA |
| 复盘 | ≤3 天完成，行动项可追踪 | 未复盘，同类事件重复发生 |

## Compliance Checklist

```
- [ ] P0/P1 是否在 SLA 时间内响应？
- [ ] 是否明确了 Incident Commander 和 Tech Lead 角色？
- [ ] 战时沟通模板是否按频率更新？
- [ ] P0 事件是否建立了专属沟通频道？
- [ ] 所有操作是否由 Scribe 记录？
- [ ] 是否满足事后复盘触发条件时进行了复盘？
- [ ] 紧急变更是否在事后补办了审批？
- [ ] Postmortem 行动项是否指定了 Owner 和 Deadline？
```
